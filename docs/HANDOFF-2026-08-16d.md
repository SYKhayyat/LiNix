### One thing this round learned that is not in any of the above

and `git ls-remote` fail here with a socket-permission error; the same requests work through

```sh

wsl -- bash -c "curl -s -H 'Authorization: Bearer $TOKEN' \
  'https://api.github.com/repos/SYKhayyat/Shall/actions/runs?per_page=12' | python3 -c '...'"
```

Job logs come from `.../actions/jobs/<id>/logs` the same way. **Do not conclude CI is unreachable
because `gh` fails** — that assumption would have left this round's blocker unfound.

   sibling, `V.188`, and the one item on `-16c.md`'s list this round did **not** close. It was
   investigated far enough to rule out the cheap fix, which is the useful part:

   **The `setting:` precedent does not carry.** `J2` was closed by putting the discriminating
   option in the ledger key (`setting:x@scope=system`), and the obvious move is the same thing
   for `@cron=`/`@run=`. It is wrong here. A `setting:`'s scope makes two *different* subjects, so
   the old key's teardown resets a different value. A schedule's subject **is** its OS-level
   identity: `schedule:nightly@cron=old` and `schedule:nightly@cron=new` are one cron entry, so
   `reconcile` would deprovision — by name — the entry `Schedules::apply` had just provisioned
   one phase earlier. Editing a schedule would silently delete it.

   Making that safe means teaching `reconcile` that a drift key whose *name half* is still
   declared is a change and not a teardown, which is a rule about every kind and not about
   schedules. So the handoff before this one was right: the honest fix is reading a cron line
   back out of cron, systemd timers and `schtasks` — three adapters and a design.

   **It is a reporting defect, not a drift one.** Provisioning is idempotent and the machine
   converges; `plan` files it under *Shall cannot read back* instead of under *work*.

## What this round finished

### `main` was RED, and it was a file mode

Not on the previous handoff's list, because that handoff could not read CI. Run `31974113499` on
`a5d5517`:

```text
./scripts/nix-validate.sh: Permission denied
##[error]Process completed with exit code 126.
```

The script was committed from Windows, where the filesystem carries no executable bit, so git
recorded `100644`. Every local invocation spells it `sh scripts/nix-validate.sh`; the workflow
spells it `./scripts/nix-validate.sh`. **`main` red on a mode bit, on a commit whose own diff was
documentation.**

**And the reported symptom was one of fourteen.** Every tracked `.sh` in the tree was `100644` —
the container entrypoints, `install.sh`, `unix-check.sh`, `release-check.sh`, and the three whose
own headers tell the reader to run them as `./scripts/<name>.sh`. Only the one line that used
`./` failed, so thirteen siblings were live and invisible: a clone on Linux following the
documentation gets `Permission denied` from all of them.

All fourteen are `100755` now, and `every_shipped_script_is_executable_tests` asks **git**, not
the working tree, whether every file with a shebang carries the bit. Self-tested: reverting
`scripts/nix-validate.sh` to `100644` makes it fail by name.

### `service:` and `firewall:` reach the NixOS system configuration

`-16c.md` called this *"the largest known gap against a ruling"* and it was. `J5`'s fourth answer
was **everything**, the renderer took `services` and `ports` from its first commit, and nothing
ever passed it any — because packages arrive through `Installable` and a `service:` line does
not. The half that shipped was the half whose interface already fitted, and the signature made
the ruling read as built.

What that cost on the real OS: `systemctl enable` writes into a tree `nixos-rebuild switch`
regenerates — **including the rebuild Shall itself runs one line later for a `nixos:` package** —
and `ufw` is not on a NixOS box at all, so `Firewall::apply` found no adapter and failed the
whole sync by name. A machine declaring `firewall:22/tcp` could not sync.

Both are attributes now, written by one function into one file and applied by one rebuild:
`services.<name>.enable`, `networking.firewall.enable`, `allowedTCPPorts`, `allowedUDPPorts`.

Four decisions inside it worth carrying forward:

- **State is declared; a transition is performed.** `@status=restarted` is not a state any
  attribute can express, so it still goes to the init — with the enablement trimmed off, because
  two owners of one enablement is the defect being removed.
- **The file is read back, never remembered.** Two writers own it and each knows half; a package
  install that could not see the services would have silently disabled every one of them. That is
  V.190's rollback defect one layer up.
- **The whole safety story is repeated, not inherited.** The SSH lockout check, `enforce_ports`
  and `enforce_additions` all run on this path against the same functions, because a port dropped
  from `allowedTCPPorts` closes on rebuild exactly as `ufw delete` closes it. `session_port` and
  the lockout predicate moved into `model::firewall` so one perimeter cannot ask a question the
  other cannot.
- **A rebuild is skipped when the file would be unchanged.** The package path only gets there
  when the engine has work; this projection runs every sync, so without the skip a NixOS machine
  would rebuild itself once per run for ever. The import must be present for the skip to fire.

`V.191` in `why.md`, the rules beside `II.30` in `target-state.md`, `J5` in `decisions.md`, the
CHANGELOG and the README all carry it. Every new shape — services true *and* false, both port
lists, the firewall enabled *and* disabled — is in `target/nix-fixtures/` and was parsed by
`nix-instantiate --parse` in `nixos/nix`, self-test included.

**The removal-guard enumeration gate caught the new file before any human did**, which is exactly
what it is for: `apply/nixos.rs` reached a removal and was in no ledger entry. It has an entry now
that says which guard stands in front of it.

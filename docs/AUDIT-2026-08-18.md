# Shall — independent code audit

**Commit audited:** `ad550f3` (branch `main`, clean tree)
**Date:** 2026-08-18
**Scope:** `src/` — 374 Rust source files, ~162,000 lines
**Method:** structured reading of the code, with targeted dynamic proofs (standalone Rust
reproductions and live PowerShell) for every finding where a claim could be checked rather
than argued.

---

## 0. Summary

Shall is unusually well-built. The comment density is high and load-bearing: most modules
record *why* a rule exists and what bug it prevents, and the repository's own stated
discipline — one parser, one guard, one writer, fix the family — is visibly followed in
`core/ledger.rs`, `core/dry_run.rs`, `core/blocking.rs`, `app/sync/guard.rs` and
`config/grammar/`. Several checks that would be the obvious findings of an audit like this
(dry-run leaking writes, unvalidated grammar options, lost-update races on the `locks/`
ledgers, a scheme downgrade across a redirect chain) have already been found and closed here,
with tests naming the exact defect.

That raises the bar for what counts as a finding, and the findings below are what survived it.
They cluster in one recognisable place: **rules this codebase learned once and applied
everywhere except at the edge of the process** — the download backends, the Windows launch
path, the two script-execution doors that never adopted `supervise`, and the three ad-hoc state
files that never adopted the `LockFile` trait. In almost every case the *reason* for the rule is
written down in this repository, in a comment, a few hundred lines from the site that does not
follow it. That is the pattern worth acting on: the thinking is right and the reach is short.

## F1 — `@bin=` confinement is bypassable on Windows {#f1}

**Severity: High.** Security control defeated on a first-class supported platform.
**Site:** `src/utils/file.rs:321-355` (`bin_destination`)

The function's own doc states the requirement plainly:

> `@bin=` is user text, and text a user pastes from somewhere else. Joined blindly,
> `@bin=../../.bashrc` resolves to a file in the home directory, and the deploy that follows
> replaces it with a symlink to a freshly downloaded, attacker-chosen file — one pasted line,
> code on the next shell start. **The traversal is in the destination, so HTTPS and a matching
> checksum do not touch it.**

The confinement is four checks: non-empty, no `/` or `\`, not `.`/`..`, and
`!Path::new(name).is_absolute()`. A **drive-relative** Windows path — `C:evil`, `x:evil`,
`C:Windows` — passes all four, because `is_absolute()` is `false` for a path with a drive
letter but no root. `Path::join` then sees a path with a prefix and **discards the base
entirely**.

Reproduction (run on this Windows host):

```text
        fd -> is_absolute=false dest=Some("C:\\bin\\fd")
    C:evil -> is_absolute=false dest=Some("C:evil")        <-- bin_dir gone
    x:evil -> is_absolute=false dest=Some("x:evil")        <-- bin_dir gone
 C:Windows -> is_absolute=false dest=Some("C:Windows")     <-- bin_dir gone
```

`C:evil` resolves against the *current directory on drive C*, so a `web:`/`github:`/`appimage:`
line carrying `@bin=C:evil` writes a downloaded, executable file outside the bin directory —
which is exactly the class the function exists to refuse, and exactly the class a checksum does
not cover.

**Why the existing tests miss it.** They exercise `..`, absolute paths and separators. Nothing
exercises the drive-relative form, because on Unix `"C:evil"` is an ordinary filename and the
check is correct there. This is a Windows-only hole in a Windows-only path syntax.

**Fix.** Reject any name whose `Path::new(name).components()` yields a `Component::Prefix`, or
more simply refuse `:` in the name on Windows. Then extend the test to the full family — `..`,
`/`, `\`, absolute, **drive-relative**, and the reserved device names (`CON`, `NUL`, `COM1`),
which currently also pass and produce a write to a device rather than a file.

**Siblings checked.** `deploy_executable` / `is_ours` (`file.rs:374-455`) are sound:
`Path::starts_with` is component-wise, so a sibling directory named `appimage-evil` does not
satisfy `starts_with(".../appimage")`, and a relative symlink target fails the check and refuses.
`force_remove` / `remove_by_kind` correctly delete the link and never the target. The
`RESOURCE_BACKENDS` and declarability refusals in `guard::protection_of` are likewise sound.

## F2 — `--temp` with a non-ASCII unit aborts the process {#f2}

**Severity: Medium.** Reachable from CLI input; `panic = "abort"` in the release profile means
no unwinding and no message the user can act on.
**Site:** `src/core/state.rs:456-470` (`StateRegistry::parse_duration`)

```rust
let unit = duration_str.chars().last()?;                // by char
let val_part = &duration_str[..duration_str.len() - 1]; // by byte
```

The unit is taken as a `char` and the remainder is sliced by **bytes**. Any multi-byte final
character makes `len() - 1` land mid-codepoint.

Proven with a standalone build of the exact function body:

```text
Some(604800)                       # parse_duration("7d")
thread 'main' panicked at pd.rs:4:33:
end byte index 2 is not a char boundary; it is inside 'д' (bytes 1..3 of string)
```

The function is `pub` precisely so a malformed `--temp` can be refused up front — its own doc
says *"a malformed `--temp` must fail loudly, never silently degrade"* — and the one caller
(`state.rs:364`, `suspend`) is written to turn `None` into a clean
`Error::Validation("Invalid duration format…")`. That message is unreachable for this input
class: the process aborts before it can be produced. Reached by
`shall uninstall <pkg> --temp=7д`, or any duration whose trailing character is non-ASCII — a
typo on a non-Latin keyboard layout gets there.

**Second defect, same function.** `value * 60 / 3600 / 86400` is unchecked `u64` arithmetic.
`[profile.release]` sets no `overflow-checks`, so `--temp 99999999999999999d` **wraps silently**
and produces a near-term (or already-past) restore timestamp instead of the far-future one the
user asked for — a package that comes back at the wrong time, with no error.

**Fix.** `duration_str.split_at(duration_str.len() - unit.len_utf8())`, and
`value.checked_mul(..)` returning `None` on overflow.

**Family swept — the two siblings are already correct**, which is what makes this one an
outlier rather than a pattern:

- `src/model/dated.rs:81-82` uses `raw[..raw.len() - unit.len_utf8()]` — correct.
- `src/model/schedule.rs:139-142` matches on ASCII `'s'|'m'|'h'` *before* slicing, so `len()-1`
  is provably a boundary — correct.
- `src/parsers/apt.rs:42` slices a `Vec`, not a `str` — not applicable.

## F3 — A corrupt backend state file reads as empty, and the emptiness is then persisted {#f3}

**Severity: Medium.** Silent, permanent loss of the record of deployed artifacts.
**Sites:** `src/backends/github.rs:300`, `src/backends/web.rs:99`, `src/backends/appimage.rs:98`

All three are byte-identical:

```rust
let data = tokio::fs::read_to_string(state_file).await.unwrap_or_default();
serde_json::from_str(&data).unwrap_or_default()
```

A truncated, half-written or hand-edited state file parses as an **empty map**, with no error
and no log line. The damage is not the read — it is the write that follows. `commit_state`
merges the run's delta into the (now empty) map and `persist`s the result, so the second run
after the corruption makes the loss permanent: every previously recorded artifact is forgotten,
its `symlink_path` / `bin_link` is no longer known, and `list_installed` reports nothing. The
artifacts stay on disk and on `PATH`, unowned — which the next reconcile sees as undeclared
drift.

**This rule is already written down in this repository, one directory over.** `core/ledger.rs`
implements exactly the opposite policy for the six `locks/` files, with a test named for it:

> **A missing file is the correct starting state, never an error** […] a file that exists and
> cannot be parsed is a fact the user needs told, and swallowing it would silently discard every
> recorded expansion, approval and pin.
> — `fn a_corrupt_file_is_an_error_and_not_an_empty_ledger`

`core/state.rs:135` (the main registry) also does it correctly, with `map_err`. So four of seven
state readers in the tree get this right and three — the three that never adopted the `LockFile`
trait — get it wrong.

**Fix.** Distinguish absent from unparseable in all three, as `LockFile::load` does. The cleanest
form is to make these three `LockFile` implementors (or a JSON sibling of it) so the seventh one
inherits the rule instead of remembering it — which is `ledger.rs`'s own stated argument for
existing.

## F4 — A truncated download leaves a partial file at the live artifact path {#f4}

**Severity: Medium.** A failed upgrade can replace a working binary on `PATH` with a truncated
one.
**Sites:** `src/core/download.rs:88-107` (`write_capped_to`), `src/backends/appimage.rs:187,223`

`write_capped_to` has four ways out after the file is created. One of them cleans up:

```rust
if written > cap {
    drop(file);
    let _ = tokio::fs::remove_file(dest).await;   // <-- and the comment says why
    return Err(refused_size(what, written, cap));
}
```

with the reasoning stated explicitly:

> Take the partial file with it. A half-downloaded artifact left on disk is one a later run can
> find and treat as complete, and the checksum that would have caught that is the one
> `@unverified` is allowed to turn off.

The other three exits — `chunk.map_err(Error::from)?` (a dropped connection), `write_all(..)?`
(a full disk), `flush()?` — **leave the partial file exactly where the comment says it must not
be left.** One reason written down, one of four exits honouring it.

This is contained for two of the three callers and not for the third:

| Backend | Destination | Exposure |
|---|---|---|
| `web:` (`web.rs:232-234`) | `tempfile::tempdir()` | Contained — the tempdir cleans up |
| `github:` (`github.rs:719-724`) | `tempfile::tempdir()` | Contained |
| `appimage:` (`appimage.rs:187`) | **`install_dir.join(filename)`** | **Not contained** |

`appimage:` streams directly onto the final artifact path. On a *re-install or upgrade* of an
already-deployed AppImage, the `PATH` symlink from the previous successful install already points
at that path, so a connection that drops at 60% replaces a working binary with a truncated one
and the symlink follows it. The run reports an error, but the machine is left worse than before
it started — and the checksum path cannot save it: `verify_checksum` is only reached on a
successful write, and `appimage.rs:228-231` (which *does* remove the file on a hash mismatch)
proves the author had this exact concern in view for the other failure mode.

**Fix, two halves — both needed.**

1. In `write_capped_to`, remove the partial file on **every** error exit, not just the cap.
   Wrapping the loop so one cleanup covers all of them is what stops a fifth exit inheriting the
   bug.
2. In `appimage.rs`, download to a temp path and rename into `install_dir` after verification, as
   `web:` and `github:` already do. Two of three doing it right is the signal.

**Related, same function.** A body that ends early is accepted as complete: nothing compares
`written` against `response.content_length()`. For a spec carrying `@sha256` the hash catches it;
for `@unverified` and for every `github:` line (which VIII.2 exempts from `@sha256`) nothing does.

## F5 — PowerShell-shimmed managers report failure as success {#f5}

**Severity: Medium.** A failed install can be recorded as an install.
**Site:** `src/core/launch.rs:136-145` (`windows_shim_wrap`, `ps1` arm)

```rust
"$o = ({} | Out-String -Width 4096); Write-Output $o; exit $LASTEXITCODE"
```

`$LASTEXITCODE` is set only by a **native** process. If the failure happens at the PowerShell
level — a cmdlet error, a thrown exception, command-not-found, the `.ps1` itself missing — the
variable is `$null` and `exit $null` exits **0**.

Verified live on this host:

```text
$ powershell -NoProfile -Command '$o = (Get-Item C:\nope-xyz | Out-String -Width 4096); Write-Output $o; exit $LASTEXITCODE'
EXIT=0
```

`CommandExecutor::ensure_status` then reads 0 as success, and for a `scoop install` that means a
package recorded as installed that is not on the machine.

**This is the same defect the file was written to fix, one arm over.** `preferred_shim`'s doc
records the measurement:

> `cmd /C ...\scoop.cmd install <bad>   -> exit 0`
> the `.ps1` branch                     -> exit 1
> […] every scoop verdict fell back to string-matching stdout — one upstream wording change away
> from reporting a failed install as a success.

The `.ps1` branch was chosen *because* it returns a real exit code. It does — for native
failures. For PowerShell-level failures it returns the same 0 the `.cmd` arm was rejected for.

**Fix.** Make the wrapper's exit code a function of both signals:

```powershell
$ErrorActionPreference = 'Stop'
$o = (<invocation> | Out-String -Width 4096)
Write-Output $o
exit $(if ($null -ne $LASTEXITCODE) { $LASTEXITCODE } elseif ($?) { 0 } else { 1 })
```

and add a case to the Windows shim tests for a `.ps1` that fails without setting
`$LASTEXITCODE` — the shape no current test covers.

## F6 — `StateRegistry` is a linear `Vec`, and `managed_index()` reaches 2 of 7 call sites {#f6}

**Severity: Low** (efficiency, no incorrectness).
**Sites:** `src/core/state.rs:63,254-276,432-444`, and five callers

`StateRegistry::managed_index()` exists because the linear scan was measured and found wanting:

> `installed_but_undeclared` asked it once per *installed* package against every *managed* one —
> on a stock Ubuntu that is ~476 × ~301, or about 143,000 double string comparisons, to answer a
> question a set answers in one hash each.

Two callers took the fix (`app/adopt.rs:332`, `app/inventory.rs:405`). Five kept the scan:

| Site | Shape | When it runs |
|---|---|---|
| `app/sync/mod.rs:896` | `declared × managed` | **every sync** (`reconcile_ownership`) |
| `verbs/declare.rs:557` | `installed × managed`, in a loop that also calls `add` | every `declare`/adopt |
| `verbs/sync.rs:513` | closure invoked per package | per sync |
| `verbs/packages.rs:740` | per named package | per uninstall |
| `verbs/packages.rs:754` | `packages × backends × managed` | per bare-name uninstall |

`sync/mod.rs:896` is the hot one — it is the same ~300 × ~300 shape, on the default path.

**The root cause is one level below the band-aid.** `packages` is `Vec<ManagedPackage>`
(`state.rs:63`), so `is_managed` (`state.rs:428`) is `O(n)` and `add` (`state.rs:276`) is a full
`retain` — an `O(n)` scan **and a reallocation of the whole vector** per package added. In
`declare.rs`'s loop those compose: adopting N packages into a registry of M is `O(N·M)` twice,
plus N vector rewrites. `managed_index()` treats the symptom at two sites; a
`BTreeMap<(backend, name), ManagedPackage>` behind the same public API removes the class.

Per this repo's own rule — *prefer deleting to fixing; two of everything is how this repo got
into trouble* — the structural change is the one that closes it, and it deletes
`managed_index()` rather than spreading it to five more sites.

## F7 — `usable()` is re-probed once per package {#f7}

**Severity: Low.**
**Site:** `src/verbs/packages.rs:727-765` (`unmanaged_targets`)

`let usable = backends.usable()?;` sits **inside** `for pkg in packages`. The comment beside it
records a fix to an adjacent duplication:

> asked once rather than twice, which the two calls here were not: the same fan-out ran to decide
> whether to widen and again to widen, and after W4 each of those is a PATH walk per manager.

The duplicate call was removed; the call was not lifted out of the loop. `shall uninstall a b c d`
runs the whole `priority()` + `is_available()` fan-out four times. `launch::PATH_LOOKUP` memoises
the PATH walk itself, so the cost is now bounded rather than linear in managers-on-disk — but it
is still N× the work for a value that cannot change inside the loop.

**Fix.** Hoist it above the `for`. One line.

## F8 — Aborting the pre-sync snapshot does not stop the snapshot on Unix {#f8}

**Severity: Low** (confidence: high on the mechanism, medium on the practical impact).
**Sites:** `src/app/sync/mod.rs:96-106,171-250`, `src/core/executor.rs:560-563`

`begin_snapshot` spawns the snapshot concurrently, and the refusal path calls
`taking_snapshot.abort()` under this promise:

> Gathered into one block so a refusal can stop the snapshot it was overlapping. A sync that is
> refused must not leave a half-taken restore point behind it.

`abort()` cancels the *task* at its next `.await`, which drops the future holding the child
process. Whether that stops the child is decided in `executor.rs`:

```rust
#[cfg(windows)] command.kill_on_drop(true);
#[cfg(unix)]    command.kill_on_drop(false);   // SIGKILL is not a way to stop a package manager
```

On Unix the child is **detached, not killed**. So a refused `sync` on a btrfs/zfs host leaves the
`btrfs subvolume snapshot` running to completion after the refusal, and the restore point exists —
the opposite of what the comment promises. (`core/blocking.rs` names this hazard in as many
words: *"`core::executor`'s two are for `tokio` children, whose hazard is that dropping the future
detaches the process."*)

On Windows the child *is* killed — which for `Checkpoint-Computer` is arguably the literal
"half-taken restore point" the comment is trying to avoid, though VSS is transactional enough
that this is probably benign.

**The honest reading is that the guarantee is one-platform, and nothing says so.** Either route
the abort through the `Stopping` path that exists for exactly this reason, or amend the comment
to state what actually holds where — this codebase's standing rule is that a promise nothing
enforces is worse than no promise.

## F9 — Artifact filenames are taken from the raw URL tail {#f9}

**Severity: Low.**
**Sites:** `src/backends/appimage.rs:186`, `src/backends/web.rs:211`

```rust
let filename = url.split('/').next_back().unwrap_or("app.AppImage");
let dest_path = self.core.install_dir.join(filename);
```

The last path segment is used verbatim as a filename. It still contains any **query string** or
**fragment**, which CDN-signed and redirect-generated asset URLs routinely carry:

- `https://host/tool.AppImage?token=abc` → filename `tool.AppImage?token=abc`.
  On Windows `?` is an illegal filename character, so `File::create` fails and the install dies
  with an I/O error that says nothing about the real cause. On Unix it succeeds and produces a
  file with a token in its name — which then also becomes the `@bin` link name.
- A URL ending in `/` yields `""` → `join("")` is the install directory itself → create fails.
- A URL ending in `..` yields the parent directory → create fails.

No traversal is possible (a `/` cannot survive the split), so this is a robustness and
diagnosability defect rather than a security one.

**Fix.** Parse the URL and take the last path segment of the parsed path, discarding query and
fragment; refuse an empty or `.`/`..` result with a message that names the URL. Both sites, and
`strip_archive_suffixes`'s caller in `web.rs` inherits the same input.

## F10 — 39 user-facing strings carry a broken line continuation {#f10}

**Severity: Low** (quality; several are refusal messages users are meant to act on).
**Sites:** 24 files in `src/`, 6 in `tests/`

A multi-line Rust string literal needs a trailing `\` to swallow the newline and the next line's
indentation. Thirty-nine literals in the tree are missing it, so the indentation is emitted as
10–40 consecutive spaces mid-sentence:

```text
src/config/grammar/statement.rs:1607
"a declared port is open — that is what declaring it means. To close one,                  delete the line; …"
```

The adjacent literals in the same files do it correctly, which is what makes these typos rather
than a convention.

Affected files include `config/grammar/statement.rs` (3 refusal messages),
`backends/onboarder.rs`, `backends/registry/mod.rs`, `backends/shared_database.rs`,
`backends/generic.rs`, `core/transaction.rs` (2, including a `Reaped::for_reason` justification
string), `app/sync/mod.rs`, `app/adopt.rs`, `app/apply/dependents.rs`, `app/apply/execs.rs`,
`core/git.rs`, `verbs/cleanup.rs`, `verbs/setup.rs`, `main.rs`.

**Fix.** Mechanical — add the `\`. Worth a lint: a `clippy`-adjacent grep in CI for
`[a-zA-Z,.-] {10,}[a-zA-Z]` inside a string literal would keep the fortieth from being written,
which is the point.

**Also spotted while reading these:** `core/transaction.rs:1533` cites `transaction.rs:993` in a
justification string; the code it names is now around line 1500. A line-number citation in a
string is a comment that rots silently.

## F11 — `@sha256` is the one security-critical option with no duplicate-value refusal {#f11}

**Severity: Low.**
**Sites:** `src/config/grammar/statement.rs:1836-1864` vs the `sha256` handling

`Options::one()` returns `first()`. The grammar explicitly refuses a repeated value for the
options where ambiguity matters:

- `@channel` twice → refused, *"there is no fallback across version streams — trying `edge` and
  settling for `stable` would silently downgrade the machine."*
- `@asset` twice → refused, *"`@asset` takes one pattern."*

`@sha256` twice is accepted, and the **first** value silently wins. A line reading
`@sha256=<old> @sha256=<new>` — the natural shape of a hand-edited hash bump — verifies against
the stale hash and refuses the correct file, or (with the order reversed) verifies against a hash
the author meant to replace.

It fails safe in both directions — nothing is *skipped*, and `verify_checksum` correctly
`eq_ignore_ascii_case`s a full-length hex string — so this is a consistency gap, not a hole. But
the argument for refusing a duplicate `@channel` applies with more force to the one option that
decides whether arbitrary downloaded bytes become an executable on `PATH`.

**Fix.** Same refusal as `@asset`, in the same function, with the same shape of message.

## F12 — `windows_shim_wrap` interpolates the program name unquoted {#f12}

**Severity: Informational** (not exploitable at this commit).
**Site:** `src/core/launch.rs:136-139`

```rust
let esc = |s: &str| format!("'{}'", s.replace('\'', "''"));
let mut invocation = cmd.to_string();      // <-- not escaped
for a in args { invocation.push(' '); invocation.push_str(&esc(a)); }
```

Every **argument** is single-quote-escaped, and the comment claims the result outright:
*"a crafted package name cannot break out of the string — no command-injection surface."* The
claim is true of the arguments and not of `cmd`, which is concatenated raw into a
`powershell -Command` string.

I traced `cmd`'s provenance and it is not user-reachable at this commit: backend program names
come from the compiled registry and `managers.toml`, `Config` exposes no user-defined manager
command, and `ScheduleConfig::command` is a different path that never reaches here. So this is a
latent hazard, not a live one.

It is worth closing anyway, for the reason this file exists: B-1 was a shell-metacharacter escape
that survived because *"the validator's doc comment carried the safety argument for the whole
program […] True everywhere except this file."* An unescaped interpolation sitting under a comment
that says there is no injection surface is that same shape — the invariant is real, and the only
thing enforcing it is that nobody has yet added a config key for a manager's binary name.

**Fix.** Escape `cmd` with the same `esc` and invoke via `& '<cmd>'`, or assert at the boundary
that `cmd` matches `[A-Za-z0-9._-]+`.

## F13 — The download backends do not consult `dry_run` themselves {#f13}

**Severity: Informational** (defence in depth; **no live defect found**).
**Sites:** `src/backends/{appimage,web,github}.rs` — `install()`

`core/dry_run.rs` states the design rule and the failure it was written for:

> The check moves to where the *write* happens. A verb added tomorrow inherits it by calling the
> writer everything else calls, rather than by remembering a convention.

The three download backends do their file writing outside that funnel: `write_capped` calls
`tokio::fs::File::create` directly, and `deploy_executable` symlinks/copies directly. Neither
consults `dry_run::active()`. The only `dry_run` check in these three files is in `commit_state`,
guarding the in-memory memo.

**I checked whether this is currently reachable and it is not.** Every verb that could reach
`install()` returns before it under `--dry-run`: `sync` (`verbs/sync.rs:220`), `install`/`add`
(`verbs/packages.rs:76`), `uninstall` (`:448`), `move` (`:16`), `rebuild`
(`verbs/sync.rs:559`). So a preview does not download today.

It is listed because the protection is currently the *verb-level* check that `dry_run.rs`
deliberately moved away from — *"one rule ('remember to check the flag') enforced by nothing"* —
and because `tests/dry_run_every_verb_tests.rs` excuses `rebuild`, `install`, `uninstall` and
`restore` from coverage on the grounds that they need a real manager. Those are precisely the
verbs whose guard is unasserted. A `web:`-only fixture would let `install` and `rebuild` join the
enumerated set without a real manager, and a `dry_run` check inside `write_capped` and
`deploy_executable` would make the rule structural again.

## F14 — `shall.gen` is written non-atomically and a torn read parses as `0` {#f14}

**Severity: Informational.**
**Site:** `src/core/datalock.rs:59-70,244-258`

The writer generation is the mechanism that lets a reader prove its multi-file read saw one
moment. It is written with a plain `std::fs::write` in `DataLock::drop`, and read with
`.parse::<u64>().ok().unwrap_or(0)`. A torn or empty file therefore reads as generation **0** — a
*lower* number than before, not an error — so two observations straddling a crashed writer can
compare equal and `spans_one_moment` returns `true` for a read that did not span one moment.

The window is small (the file holds ≤20 bytes and a crash must land inside the write), and this
is a read-consistency hint rather than a lock, so the impact is a stale report rather than a bad
write. Worth using `utils::file::persist` — the atomic writer this repo already owns and requires
everywhere else — rather than the one raw `fs::write` that skipped it.

**The rest of `datalock.rs` I read closely and found sound**, including the parts most likely to
be wrong: the `HELD` counter correctly prevents the same process from `flock`-ing itself into a
permanent self-wait; the owner stamp is written *after* the lock is taken so it cannot name a
loser; `Generation`'s `PartialEq` covers `writer_active` so a reader that saw a writer at either
end cannot conclude one moment; and the drop order (bump → unstamp → unlock) is the correct one.
The one structural note is that `for_one_step` and `try_for_one_step` do **not** consult `held()`
the way `for_this_write` does, so a future caller that nests them inside a lock-holding command
would self-deadlock for `WAIT_SECS` (or, for the `try_` form, silently skip its work believing
another process holds the lock). No such nesting exists today; `LockScope::Deferred` is what keeps
it true.

## F15 — Two of the three script-execution doors have no timeout {#f15}

**Severity: Medium.** An unattended `shall` can hang indefinitely before it does any work.
**Sites:** `src/model/vars_provider.rs:144`, `src/core/rhai_stdlib.rs:64,81`

Shall runs user-authored code from three places. They use three different execution doors, and
only one of them is bounded:

| Door | Call | Bound |
|---|---|---|
| Lua/Rhai package hook (`app/hooks.rs:195`) | `supervise::supervised_output` | **Bounded** — supervised, idle-timed |
| Shall's own event hooks (`app/events.rs:244`) | `supervise::supervised_output_fed` | **Bounded** |
| External `vars.<ext>` provider (`model/vars_provider.rs:144`) | `blocking::command_output` | **None** |
| `sh()` / `sh_ok()` in the Rhai stdlib (`core/rhai_stdlib.rs:64,81`) | `blocking::command_output` | **None** |

`blocking::command_output` is `on_the_terminal(|| command.output())` — it returns when the child
does, and never before. There is no whole-command timeout, no idle timeout, and no cancellation
point; the run cannot even be interrupted by the `node_timeout` / `total_timeout` that bound the
transaction, because none of this is inside a transaction.

**What makes this more than a theoretical hang is where these two sit.** Both run at *step 0 of
resolution*, before any package manager is asked and before any plan exists — so they are on the
path of every command, including the read-only ones. `shall check`, `shall plan`, `shall list`
and a scheduled `shall sync` all block on them. A `vars.py` that reads from a network mount that
went away, or a `vars.shall` containing `sh("git fetch")` against an unreachable remote, hangs
Shall forever with no output and no way out but Ctrl-C — and for the scheduled run there is
nobody to press it.

**The reasoning for the bound is already written in this tree, twice**, and both times about
exactly this situation:

- `events.rs:240` — *"an event hook is arbitrary code fired by a timer or a package-manager hook,
  with nobody at the terminal. Unowned and unbounded, one that waited on something waited
  forever, and one abandoned by whatever fired it kept running."*
- `rhai_stdlib.rs:18` — the `set_max_operations(10_000_000)` cap exists so *"a runaway script
  must not hang every `plan` and `sync`"*, and its own comment concedes the gap: *"It counts Rhai
  operations, not seconds — a hook whose `sh()` runs for ten minutes is one."* The gap is named
  and left open.

`vars_provider.rs` goes furthest: it wraps the call in `timing::begin`/`end` specifically because
*"an external provider runs on every resolution, before any manager is asked — so a slow one looks
like Shall being slow to start until the breakdown names it."* The author measured the problem and
reported it; nothing bounds it.

**Fix.** Route both through `supervise`, as the two hook doors already do, with the configured
`command_idle_timeout_secs`. That deletes a third way of spawning user code rather than adding a
fourth — which is this repo's own stated preference. If `vars` genuinely needs a different bound
from a hook (it runs before the user has seen anything, so arguably a *shorter* one), make that a
named constant with the reason beside it rather than the absence of one.

**Note this is not a sandbox finding.** `sh()` exposes a full platform shell and `read_file` reads
anything the user can, but every one of these scripts is gated by the `locks/hooks.toml` approval
ledger before it runs — see the section below. The trust model is deliberate and correct; the
missing bound is a liveness defect inside it, not an escape from it.

## F16 — `http_get` accepts a plain-`http://` seed URL {#f16}

**Severity: Informational.**
**Site:** `src/core/rhai_stdlib.rs:158-160`

`http_get` correctly uses the pooled `http::api` client, so it is timed out and it **refuses a
redirect that leaves HTTPS**. What it does not do is check the scheme of the URL it was *handed*:
the redirect policy only inspects redirect attempts, and `download::check_scheme` — the function
that owns this rule — is not applied here.

So `http_get("http://internal/config")` from a `vars.shall` fetches in clear, and its answer
becomes a resolved variable that can decide which packages get declared. `download.rs`'s doc for
`check_scheme` states the principle in terms that cover this case: the value crossing the network
decides what runs on the machine.

The mitigation is real — the script is ledger-approved, so a plain-HTTP URL is something the user
reviewed and signed — which is why this is informational rather than a finding against the trust
model. But `@allow_http` exists precisely so that "I know this host is HTTP-only" is a written,
per-line decision rather than an unremarked default, and this is the one network door in the tree
where that decision is not asked for at all.

**Fix.** Call `download::check_scheme(url, false, "an http_get from a vars script")`, and if a
plain-HTTP escape hatch is wanted, spell it as a second builtin whose name says so.

## Areas examined and found sound

Stated so the negative space is legible. These were read with the same intent and produced no
finding:

- **`core/ledger.rs`** — the `LockFile` trait. The `update()` read-modify-write under the data
  lock is the correct answer to the lost-update problem, and the dry-run and missing-file rules
  are stated once and inherited. This is the model F3 should be folded into.
- **`app/sync/guard.rs`** — the removal guard. `protection_of`'s ordering (resource → declarable
  → explicit unprotect → protection rule → OS-essential) is right, the mass flags clear the count
  objection and nothing else, `max_total_changes` is assembled at every gate rather than some,
  and `Reaping` records only after a set is cleared. The `Reaping` counters are `Relaxed` and
  check-then-act, which would be a TOCTOU under concurrency — I traced all 12 `enforce*` call
  sites and every one is on a sequential phase path, so it is not one today.
- **`core/transaction.rs`** — rollback. The `Prior::{Present,Absent,Unknown}` trichotomy is
  exactly right: a failed query is not an absent package, `Absent` is not permission to remove,
  and both arms consult `plan_intends_present` so a rollback cannot hand the next sync the same
  work. `LockBudget` correctly spends one budget across the retry loop rather than per attempt.
- **`core/http.rs` / `core/download.rs`** — the redirect policy checks the scheme on **every hop**
  rather than the typed string, the client pool is keyed on the whole policy so a
  downgrade-tolerant client can never be handed to a caller that refuses one, `api()` raises a 0
  timeout to 1s, and `@allow_http` and `@unverified` are correctly kept from implying each other.
- **`config/grammar/`** — the option allowlist is closed (`is_package_option_key`), and the
  deferred backend-option validation genuinely happens: a bare-name line skipped at parse time is
  re-validated at `model/resolve.rs:997` once the backend is known, and `priority` bodies at
  `model/priority.rs:89`. I checked this because "we'll check it later" is usually a lie; here it
  is not. `SCOPED_OPTIONS`/`INSTALLS_FROM_SOURCE` are asserted equal to the grammar's list by
  test, so no backend reads a key the grammar refuses.
- **`core/dry_run.rs`, `core/blocking.rs`, `core/exec_lock.rs`** — each states one rule and
  enforces it structurally. `ExecLedger::departed` keying on *path* rather than content hash is
  subtle and correct (an edited script has not departed).
- **`core/hook_lock.rs` and its enforcement — the code-execution boundary.** This is the most
  security-sensitive design in the tree and I found nothing wrong with it. The identity functions
  (`hook_id`, `vars_id`, `exec_id`, `health_id`, `generate_id`, `event_id`, `adapter_id`) each
  make the right distinction, and the reasoning for each is stated: `adapter_id` is per *file*
  rather than per definition because *"a per-definition identity would let an edit that adds one
  go unnoticed, and adding one is the whole attack"*; `event_id` keys on event **and** origin so
  approving the shared policy cannot rubber-stamp the local file; `exec_id` keys on path while
  `locks/exec.toml` keys on content, so a changed script is both unapproved and un-run.
  Critically, **there is no TOCTOU between hashing and executing**: `events.rs:207-231` hashes
  `hook.script`, then writes *that same string* to a fresh 0700 tempfile and runs the tempfile —
  it never re-reads the path it hashed. `sync/mod.rs:108-111` re-reads the hook files at fire time
  rather than holding them, so a hook edited during a long sync cannot run on its old approval.
  Approval is write-only through `shall lock` (`approve_all_hooks` is the sole writer), an
  unreadable ledger counts everything as unapproved rather than approved, and `-y` cannot approve.
  All of that holds.
- **Dead-code sweep** — all 53 `Config` fields are read outside `config.rs`; no inert config keys.
  No `TODO`/`FIXME`/`unimplemented!` in production code. `unwrap`/`expect` outside tests is 60
  sites and every one I sampled is provably infallible or documented as such.

## Scope and limits

- **Method.** Reading was primary, as asked, and it is the right primary for this target: the
  behaviour that matters lives in decision logic, not in a running UI. CDP is not applicable —
  Shall is a Rust CLI with no browser surface — so the dynamic component was standalone Rust
  reproductions (F1, F2) and live PowerShell (F5) instead. Each is shown above.
- **Not executed.** I did not run `cargo test`, `cargo clippy`, the container harness, or
  `cargo mutants` as part of this audit. Every finding is from source plus the targeted
  reproductions shown; none depends on a suite result.
- **Not covered in depth.** `src/backends/generic.rs` (3,680 lines) and
  `src/config/grammar/statement.rs` (3,573) were read selectively around the specific questions
  above rather than end to end. `src/app/scheduler/`, `src/app/fleet.rs`, `src/backends/nixos.rs`,
  `src/backends/btrfs.rs` and `src/app/pm_hooks.rs` were not audited. Of these, `pm_hooks.rs` is
  the one I would do next: it installs Shall into a package manager's own transaction
  (`DPkg::Post-Invoke` and siblings), which means code Shall writes runs on every `apt install`
  the user types, under the manager's lock — a re-entrancy surface with a different shape from
  everything examined here.
- **Cross-platform.** F1, F5 and half of F9 are Windows-only, and the local verification chain
  compiles one platform of two. Findings F3, F4, F6, F7, F8 apply to both.

## 1. Bugs — **B**

The safety-critical machinery is genuinely strong. The defects are all in one place: **the boundary
between what Shall owns and what the things it calls own** — exactly where you said it hurts. Three
of the five findings are that boundary, and two of them are *the same family a previous round
already fixed for half its members*.

### B1 — Shall deadlocks against its own package-manager hook (HIGH)

`main.rs:143` stands down when a reconcile is fired by a Shall-driven manager:

```rust
if matches!(cli.command, Commands::HookReconcile { .. })
    && env::var_os(shall::core::executor::INSIDE_SHALL).is_some()
{ return Ok(()); }
```

The comment above it states the hazard exactly: *"it holds the lock this process would wait two
minutes for."* Correct — and it covers **one of the three hook subcommands**.

- `HookReconcile` — guarded. This is what apt, dnf, zypper, apk, xbps, portage and eopkg invoke.
- `HookRecord` — **not guarded.** This is what **pacman** invokes (`pm_hooks.rs:88`, a
  `PostTransaction` hook), and `handle_hook_record` writes state and git-commits
  (`verbs/declare.rs:470-472`), so `writes()` is `true` (`cli/args.rs:1003`) and it takes the
  120-second exclusive `DataLock`.
- `HookObserve` — **not guarded.** The shell wrappers (`pm_hooks.rs:352`). Same `writes()` list.

So on any Arch/Manjaro box where `shall hooks` has been installed:

```
shall sync  (holds DataLock)
  └─ pacman -S foo                       ← spawned with SHALL_INSIDE set
       └─ PostTransaction hook
            └─ shall hook-record …       ← ignores SHALL_INSIDE, blocks on DataLock
                                           for the full 120s, then fails
```

pacman waits on its hook the whole time. Nothing kills it — `node_timeout` is 300s × batch and
`command_idle_timeout` is 900s — so it is not a crash. It is **+120 seconds per pacman transaction,
silently, and the record is lost anyway.**

*Family checked:* three hook subcommands, one guard. `INSIDE_SHALL` appears in exactly four places
in the tree (`executor.rs:21`, `:1511`, `:2481`, `main.rs:144`), and the only test on it asserts the
env var is *set*, never that a child stands down. The fix is the same `matches!` widened to all
three, plus a test that a hook subcommand under `SHALL_INSIDE` exits without taking the lock.

### B2 — `watch`, `shell` and `run` hold the exclusive data lock for unbounded time (HIGH)

`writes()` (`cli/args.rs:926`) decides who takes the 120s exclusive `DataLock` for the whole
process. Its own doc comment records this bug being found and fixed **three times**:

> `$EDITOR` … once stopped every other Shall on the machine for as long as somebody read a manifest
> in vim (AU6).
> **`fleet` was a writer by omission** … it took the 120-second exclusive lock for a purely remote
> report.
> **`history` is a reader at this level and a writer inside.** It opens a TUI a person reads for as
> long as they like.

`edit`, `fleet` and `history` were fixed. Three siblings with the identical shape were not:

| command | how long it holds the lock | what it is |
|---|---|---|
| `watch` | **forever** | `verbs/sync.rs:694` — an unbounded `loop`. "Ctrl-C to stop." |
| `shell` | the length of an interactive session | `app/shell/mod.rs:81` — launches `$SHELL` and awaits it |
| `run` | the length of an arbitrary user command | `app/run.rs` — "run a command within an ephemeral environment" |

`watch` is the sharp one. It is the GitOps daemon: the intended deployment is *leave it running*.
While it runs, **every writing Shall command on that machine blocks 120 seconds and then fails** —
including `shall install`, and including the `hook-reconcile` that a manual `apt install` fires
(which does *not* stand down, because a hand-typed `apt` is not `INSIDE_SHALL`). A user who follows
the documented GitOps workflow has bricked their own CLI.

The `history` fix is the template and it is the right one: take the lock *at the mutating action*,
not around the session.

### B3 — a resolver failure is reported to the user as "not installed on this machine" (MEDIUM)

`app/context.rs:745` carries a comment that is exactly right:

> A manager that could not be asked has not said no. Dropping the error here made `info` print "is
> not installed on this machine" — a claim about the user's machine — whenever a manager fell over
> … Absence and unavailability are different answers and only one of them is knowable.

Thirteen lines above it, in the same function:

```rust
let specs = self.resolve_spec(package_name).await.unwrap_or_default();   // context.rs:732
for spec in &specs { … }                    // never runs when the resolve failed
if named_backend.is_some() { return Ok(None); }   // → "is not installed on this machine"
```

When the user named the backend (`info luarocks:luafilesystem`) and the resolve fails, Shall never
asks luarocks anything and then makes a confident claim about the machine. Same category error, same
function, still live.

The planner gets this right and says so — `installed_sets` (`sync/planner.rs:566`) documents
*"Unknown means yes… Not knowing must never turn into 'so skip it'"*. The rule is understood in the
codebase; it just is not applied at this one call.

### B4 — the suite is red on clean `main`, and the red is nondeterministic (MEDIUM)

```
test result: FAILED. 497 passed; 1 failed; 0 ignored; finished in 374.53s
---- grade2_info_tests::info_agrees_with_list_about_every_backend_not_only_the_first ----
  `info luarocks:luafilesystem` denies a row `list` just printed under `luarocks`
```

Run alone it passes in 41s. Run inside the full suite it fails. By hand both commands agree:

```
$ shall list | grep luarocks
luarocks     luafilesystem                    1.9.0-1
$ shall info luarocks:luafilesystem
Package:  luafilesystem   Backend: luarocks   Version: 1.9.0-1     (exit 0)
```

So this is not a false alarm — it is B3 firing under contention. The suite drives *real* package
managers on the host at `cargo test`'s default parallelism; under that load the resolve fails, B3
swallows it, and `info` denies a package that exists. **The test is correct and the product is
wrong**, which is the good ending, but it means the ship gate is currently a coin toss.

Two things follow: fix B3, and separately decide whether a suite that shells out to the developer's
real `luarocks` under N-way parallelism can ever be a gate. Right now `--test-threads` is the
difference between green and red.

### B5 — ANSI escapes are written to a non-terminal (LOW)

```
$ shall install nosuchpkg-zzz 2>&1 | grep -c $'\033'   → 1     (piped, still coloured)
$ NO_COLOR=1 …                                          → 0     (respected)
$ TERM=dumb …                                           → 1     (ignored)
```

`main.rs:66-77` builds the subscriber without `.with_ansi(…)`. Logs redirected to a file get escape
codes. One line to fix; `is_terminal` is already imported elsewhere in the tree.

### What is genuinely strong, and was checked rather than assumed

- **The removal guard holds up under enumeration from the code**, which is the check `GRADER.md`
  demands. `Installable::remove` cannot be called without a `Reaped` token, and the token can only
  be minted by `Reaped::for_reason`. Stripping `#[cfg(test)]` bodies, there are **three** production
  mint sites in the whole tree: `sync/mod.rs:1187` (heal), `transaction.rs:1210` (rollback), and the
  definition — each carrying a `file:line` justification for why the guard already ran. Every other
  `for_reason` in the tree is inside a unit test of an effector. That is a type-level proof, not a
  convention, and it is the single best piece of design in the repo.
- **Zero `TODO`/`FIXME`/`HACK` in 108k lines**, and `core/argv.rs:676` is a test that asserts no
  user-facing string contains "not yet" or "todo".
- **91 non-test panic sites in 48.6k lines of code**, and I read all of them. They are compiled-in
  TOML, regex literals, and `split_first()` on argv vectors that are non-empty by construction. The
  two that look data-driven (`snapshot_restore.rs:341`, `transaction.rs:469`) are both inside
  branches that already proved the value present. One caveat worth stating: `panic = "abort"` in the
  release profile means any panic is a hard abort with no unwinding — so no `Stopping` guard runs and
  no rollback fires. That is a deliberate trade, but it raises the cost of the 91.
- The `--dry-run`, `-y`/`max_removals`, and WAL-before-mutation properties all have live tests that
  passed in this run (`dry_run_every_verb_tests`, `wal_enumeration_tests`).

**Why B and not higher:** no crashes, no data loss, and the scary paths are well defended. But three
of five findings are the *same* ownership-boundary family, two of them are half-fixed versions of
bugs this repo already wrote down, and the suite is red. **Why not lower:** every finding is a
bounded stall or a wrong sentence, not a lost package.

## 2. Performance — **A−**

I expected to find the usual Rust-project self-deception here and did not. The parallelism is real
and it is measured.

### 2.1 The measurement

`shall --timings list`, debug build, 24 ready backends on this host:

```
Timings: 5.73s wall · 23 child command(s) summing to 32.62s · 5.7x overlap · 2 wave(s)
    0.96s    4.76s   scoop export
    1.03s    4.38s   winget list
    0.74s    3.43s   choco list
    0.84s    2.94s   npm list
    …
```

**32.6 seconds of subprocess work in 5.73 seconds of wall clock.** The critical path is `scoop
export`, which runs 0.96→5.72s. The wall clock is 5.73s. **Shall's own share of that run is within
rounding error of zero** — it finishes ten milliseconds after the slowest thing it was waiting on.

That is the whole performance story and it reframes the brief. Shall is a program that spends its
life waiting on other people's processes. There is no amount of blazing Rust that makes `winget
list` faster. There are only three levers — *don't ask*, *ask fewer*, *ask concurrently* — and the
third is done well.

The release build says the same thing more sharply — `shall --timings list`, release, same host:

```
Timings: 3.75s wall · 23 child command(s) summing to 23.67s · 6.3x overlap · 2 wave(s)
```

Other numbers, this host:

| command | debug | release |
|---|---|---|
| `--version` | 204 ms | **106 ms** |
| `path` | 230 ms | **83 ms** |
| `eval` | 206 ms | **110 ms** |
| `list` | 5.7 s | **3.98 s** |
| `check health` | 4.4 s | — |
| `check` | 6.1 s | — |

Release binary: **16.1 MB**, stripped.

Read the `list` row carefully, because it is the point. Release halves Shall's own work
(204→106 ms on the commands that ask nobody anything) and moves `list` by 30%, all of which is the
child commands being scheduled sooner rather than Shall computing faster. **Optimising the Rust
further would be measurable in the first three rows and invisible in the fourth**, and the fourth is
the one users wait on. The remaining lever is not the compiler; it is asking less.

### 2.2 The engineering is real, and it is documented with measurements

This is not hand-waving — the tree carries the numbers that justify each choice:

- `App::new` overlaps four independent startup futures, and the comment explains that
  `build_registry` is polled **last** because it is an `async fn` with no `.await` in it, so placing
  it first made the "overlap" decorative — *"the instrumented run reported four futures all
  finishing at 213.6ms, which was one future's cost wearing four labels (AU7)."*
- `governor` is pinned off `quanta` because its TSC calibration cost *"200ms, once, on whichever
  thread got there first — a fifth of a second on `shall path`."*
- The DAG dep-counting was O(V·(V+E)) — *"~100k redundant edge checks for 300 packages"* — and is now
  incremental.
- `installed_sets` asks each backend **once** rather than once per spec, because *"a manifest with
  256 winget lines puts 256 futures into a queue `max_parallel` slots wide, every one of them waiting
  on the same `winget list`."*
- Windows `launch_path` is memoised because a PATH scan plus a `.ps1` stat *"ran on every single
  spawn — synchronously, inside an `async fn`."*
- `run_exclusive` moves the `flock` wait to `spawn_blocking` so a second `shall` holding it does not
  park a runtime worker for the length of an `apt dist-upgrade`.
- Batching is real: up to 100 packages / 6000 bytes per manager command line, so N packages is one
  `apt install`, not N.

I went looking for a livelock in the DAG dispatch loop (`transaction.rs:356-518`) and did not find
one: the `else if in_progress.is_empty()` arm at :514 catches the stall case, `in_progress` is
drained on both the success and failure branches, and the semaphore permit is released by an
independently-spawned task so the dispatch loop cannot starve itself. The pipe handling in
`wait_watched` drains stdout and stderr concurrently with the wait — the classic
fill-the-pipe-buffer deadlock is explicitly defended, including the *"child exited but something
still holds its output open"* case, which is measured (*"a 20s bound, a 64s wall, and the install
reported as a success"*).

### 2.3 The one real gap: the commands users run most are the ones nothing measures

`core/latency.rs` defines four classes and gives budgets to two:

```rust
Class::ConfigOnly => Some(5s),
Class::OneBackend => Some(15s),
Class::EveryBackend | Class::Mutating => None,      // ← list, search, check, adopt
```

The reasoning is stated and is half right: *"A command that asks every manager costs whatever the
managers cost, and that is a fact about the host rather than about Shall."* True of the **wall
clock**. Not true of **Shall's share of it** — and you already compute that share, in the same
binary, in `--timings`: the overlap ratio and the wave count.

So the regression that this cannot see is the important one: a change that serialises a fan-out
drops overlap from 5.7× to 1.2× and the wall clock stays inside a budget of `None`, for ever.
`GRADER.md` §9 asked for a latency gate and got one for the two cheap classes; the expensive class
is still unmeasured, which is where the 98-second `info` came from in the first place.

**Recommendation:** gate `EveryBackend` on `overlap ≥ N×` and `waves ≤ 2`, not on seconds. The
instrument exists; nothing reads it.

*(One correction against myself: I first read the 2-wave report on `list` as an instrument bug,
because two commands were plainly still running at the moment it claimed the run "went quiet". I was
anchored on the wrong row. `waves()` is a correct interval-union count, and the gap is real — a
`powershell Get-InstalledPSResource` probe runs 0.35→0.58s, then the main fan-out starts at 0.73s.
A ~150ms serialisation, worth closing, and the instrument was right.)*

### 2.4 Two costs that are not measured because they are not runtime

- **`installed_cache_secs` defaults to `0`**, so nothing is reused across runs. The doc comment
  argues this honestly (*"the honest default for a tool whose job is to be right about the
  machine"*) and I agree with the default. But it means `list`, `check` and `sync` each pay the full
  ~30s of subprocess work every time, and there is no middle setting suggested anywhere in the
  first-run path.
- **The release profile is expensive.** `lto = true`, `codegen-units = 1`, `panic = "abort"` over a
  108k-line crate with a vendored C Lua, ratatui and reqwest. The final `rustc` link on this machine
  held **1.3 GB resident** and ran for over fifteen minutes. That is fine for a CI job that publishes
  a binary — and it is *not* fine as the thing a user runs, which is exactly what happens today
  because of R1 in §6.

**Why A− and not A:** the parallelism is genuinely good, measured, and defended with numbers, which
is rare. It loses the last step for having built the right instrument and then not gating on it, and
for the ~150ms probe that sits outside the fan-out.

## 3. SOLID / code quality — **B+**

### What is very good

- **Interface segregation, properly.** `core/manager.rs` has eight narrow capability traits —
  `BackendCore`, `Installable`, `Queryable`, `Enumerable`, `Searchable`, `Upgradable`, `RepoManager`,
  `MetadataProvider` — composed onto `BackendCapabilities` and reached through `as_installable()` /
  `as_queryable()`. A backend implements what it can do. There is no fat `Backend` trait with a
  dozen `unimplemented!()` arms, which is the shape almost every tool in this category has.
- **Illegal states made unrepresentable.** The `Reaped` token (§1). This is the correct answer to
  "every removal path calls the guard" — not a rule, a type.
- **One parser for `backend:name`.** `CLAUDE.md` mandates it and the tree honours it; `handle_info`
  goes out of its way to use the grammar rather than `rsplit(':')`, with a comment naming the exact
  bug that would cause (`web:https://…` has three colons).
- **The registry is a `BTreeMap`, deliberately**, with a comment explaining that the `HashMap` it
  replaced made *"two `shall list` runs a second apart differ by 530 lines"*.
- **The comments are the best I have read in a generated codebase.** 16,286 comment lines, 23% of
  non-test code — and they overwhelmingly record *constraints and measurements*, which is what
  `CLAUDE.md` P6 asks for. "This must be polled last or the overlap is decoration, measured at
  213.6ms" is worth more than the code it sits on.
- **1.4:1 test-to-code ratio** (67k test lines against 48.6k code lines), and the tests are pointed
  at properties (`every_test_file_is_in_the_suite`, `every_exempted_verb_still_exists`,
  `every_subcommand_shall_invokes_still_exists_upstream`) rather than at lines.

### What is not

**`App` is a god object and every handler depends on all of it.** `app/context.rs:25` — twelve
`pub` fields (config, registry, executor, metrics, progress, hooks, state, snapshot_manager,
journal, diagnostics, scheduler, reaping) and 46 methods. Every one of the ~67 verb handlers takes
`&App`. Nothing declares what it actually needs, so nothing can be tested against a narrow fake, and
every test that touches a handler constructs the entire world — which is part of why the suite takes
374 seconds. This is the one place the design is *anti*-SOLID: the trait work at the backend layer is
excellent and the application layer has no interfaces at all.

**Modules are organised by file size, not by cohesion.** `verbs/history.rs` contains fifteen
handlers: `snapshot`, `rollback`, `diff`, `git`, **`shell`**, **`run`**, **`adopt`**,
`snapshot_restore`, `history`, `audit`, **`sbom`**, **`export`**, **`bundle`**, **`restore`**,
**`why`**. Eight of those fifteen have nothing to do with history. `verbs/setup.rs` similarly holds
`adapters`, `add`, `try`, `path`, `edit`, `config`, `heal`, `canary`, `policy`, `init`. A reader
looking for `handle_run` will not find it, and a reviewer cannot tell from a diff's file path what
area changed.

**Seven modules named `*_lock`, and six of them are not locks.** `artifact_lock`, `bare_lock`,
`exec_lock`, `extras_lock`, `hook_lock`, `regex_lock` are all *ledger files* — records that pin a
resolution. `datalock` is the only mutex. Individually each is well-written and well-documented; the
naming collision means the one file in that list that can block a process reads like the other six.

**Four files over 3,000 lines** (`registry.rs` 4,210, `grammar/statement.rs` 3,812, `generic.rs`
3,622, `executor.rs` 3,334). Roughly half of each is inline tests, so the bodies are ~2,000 lines,
which is survivable — but `registry.rs` in particular is 52 backend registrations in one file, and
its own header says *"Adding a backend is a localized change"*, which is true of the diff and not of
the file.

**`cargo fmt` was not run before committing.** Four call sites in `src/app/sync/mod.rs` and
`src/verbs/packages.rs` are unformatted on committed `main` (R2). Trivial in itself; the reason it
belongs under code quality is that `CLAUDE.md` names the verify chain, CI rates fmt fatal, and
`release-check.sh` rates it HARD — so the gate exists, is correct, and was skipped. That is the same
shape as the two half-fixed families in §1, one layer down: **the repo's problem is not that it
lacks checks, it is that checks get built and then not run over the last change.**

**Why B+:** the type-level and trait-level design is genuinely better than most hand-written Rust I
see. It loses a full grade for `App`, and a half for module layout — both of which are mechanical to
fix and neither of which is a correctness risk.

## 4. Purpose — is 100k lines justified? — **B**

### First: it is not 100k lines

| | lines | |
|---|---|---|
| all `.rs` | 137,207 | |
| — `tests/` | −28,761 | integration suite |
| — inline `#[cfg(test)]` | −38,323 | 35% of `src/` |
| — comments in non-test `src/` | −16,286 | 23% of what is left |
| — blanks | −5,278 | |
| **executable code** | **48,559** | |

**Two thirds of this repo is tests and comments.** That is the answer to the question as asked, and
it is a defence rather than an excuse: a 1.4:1 test ratio on a tool that uninstalls software is the
right ratio.

### Where the 48.6k goes

| area | lines | share |
|---|---|---|
| 52 backends + parsers | 13,481 | 28% |
| grammar + model + resolver + planner | 11,537 | 24% |
| CLI surface (67 verbs) | 7,832 | 16% |
| executor + transaction + journal + argv | 2,107 | 4% |
| **everything else** | **13,602** | **28%** |

Your framing — *take nouns, match them to verbs, run them, write them down* — is the first two rows,
and they cost **25,000 lines**. That is defensible on inspection:

- **13.5k for 52 package managers is ~260 lines each**, and that is close to irreducible. Each needs
  its own argv, its own parser, its own exit-code policy, its own idea of what "installed" means.
  There is no abstraction that makes `winget`'s ARP identifiers and `luarocks`' Lua-version scoping
  the same code, and the tree already pushes as hard as it reasonably can on the shared `generic.rs`
  path.
- **11.5k for the declarative model** buys `when` conditions, profiles, variables with providers,
  modules with `use`, six lock ledgers, priority resolution, `absent:`, and set arithmetic on
  manifests. That is the product. If you want the file to be the source of truth, this is the price.

So the core is justified. The question is the other 28%.

### The 13.6k of "everything else" is where the scope lives

`insight`, `scheduler` (systemd/launchd/Task Scheduler), `sandbox`, `bundle`/`restore` (air-gapped
packing), `bisect`, `fleet` (SSH multi-machine), `snapshot_restore`, two `ratatui` TUI screens,
`profile_expr` (a hand-written expression language with its own lexer and parser), `sbom`,
`export`, `pm_hooks`, `metrics`. Each is small. Collectively they are 28% of the code, roughly half
the 67 verbs, and — by the coverage ledger in `GRADER.md` and the fixture count below — the large
majority of the surface nobody has ever run.

**The sharpest single instance: three embedded interpreters.**

| engine | what it costs | what it serves |
|---|---|---|
| `mlua` (vendored C Lua 5.4) | a C build in every compile | one arm of `app/hooks.rs` |
| `rhai` | a full scripting engine | the other hook arm, plus `@vars` |
| `tera` | a template engine | dotfile templating in `link.rs` — **one file** |

Three ways to evaluate a user-supplied expression, none of them sandboxed — and `hooks.rs:12` says
so plainly: *"None of the three is sandboxed, and none of them ever was. `Lua::new` loads
`os.execute`."* That honesty is good, and the hook-approval ledger (II.12) is the right boundary. But
`rhai` alone would serve all three roles, and dropping `mlua` would take a vendored C toolchain
dependency out of every build on every platform.

### The verdict

The size is **justified for what it does** and **not obviously justified for what it should do**.
48.6k lines is not bloat for 52 managers and a real declarative model. But 67 top-level commands is
a very large promise for a v1, and the ones with the least coverage are exactly the ones a user is
least likely to need on day one. A smaller v1 — the core loop, the backends, and maybe fifteen verbs
— would be a stronger release than this one, and the rest would lose nothing by shipping at 1.1.

**Why B:** the code is not padded, and the number in the brief was wrong by 2×. It does not score
higher because the surface area is a deliberate choice that has not been paid for in testing, and
§6's blockers are mostly the bill for it.

## 5. Missing features — **B+**

Genuinely hard to find gaps. The competitive position is strong: against `metapac` this is a strict
superset; against `topgrade` it wins on transactions, snapshots and the guard; against
`decman`/`home-manager` it is close on config-content management.

*Sourcing note: the competitive comparisons in this section come from the scan recorded on
2026-07-03 and were **not** re-verified against those projects' current releases in this review. The
gaps below were checked against this tree; the claim that a competitor still lacks something was
not. Re-run the scan before putting any of it in marketing copy.*

### Real gaps, in the order I would close them

1. **No published binaries.** See R1. This is a *feature* gap as much as a release gap: "install
   without a Rust toolchain" is on the README and does not work.
2. **topgrade-style non-package upgrades.** `shall upgrade` upgrades *managed packages*. It does not
   touch firmware (`fwupd`), OS release upgrades, editor/shell plugin managers, tracked git repos, or
   `rustup`/`gcloud` components. This is the one axis where a competitor does something Shall
   cannot, and `upgrade` is the verb where users will expect parity.
3. **Managed-file content drift is not pre-announced.** `link` self-heals content on sync but
   `check` does not report it beforehand, so the one thing a config-management user wants — "what
   will change if I sync" — is incomplete for file contents. Needs `link` to be `Queryable` with a
   content diff.
4. **No self-uninstall verb, and no clean removal path for Shall itself.** `reset` makes Shall
   forget it manages anything, which is the right primitive, but a tool that installs native
   package-manager hooks into `/etc` should be able to take them all back out in one command.
5. **`self-upgrade` requires a Rust toolchain** (its own `--help` says so). Once R1 is fixed this
   should download the published binary like `install.sh` does.

### Deliberately not on this list

Containerised backends (apx/distrobox) is an open architectural thread, not a gap. Wrapping other
meta-managers was rejected for good reasons. Nothing in the decision register is blocking: **189
decisions, 0 open, 0 open-blocking, 0 built-never-ruled, 2 parked** — which is genuinely unusual and
is the strongest single signal that the design is finished.

**Why B+ and not A:** the feature set is complete enough to release. It is held off an A by item 1
being a feature, not just a chore, and by item 2 being a visible gap in the verb users type most.

### R1 — There is no release. There has never been a release. (BLOCKER, ~1 hour)

### R7 — macOS (CORRECTED — it runs; it is red for one real reason)

Also wrong as written. `macos-native` **does** run nightly and is not a stub: last night it executed

The one failure is worth reading closely, because it is this repo's signature defect wearing a

```
FAIL  lock: a run after a killed holder failed (rc=1) instead of taking the free lock
      | Error: `brew` failed (exit 1): No available formula with the name "tokei@14.0.0".
```

**The assertion's name and the assertion's cause are unrelated.** The lock was taken correctly; the

### R8 — CI never finishes, so "CI is green" is not a statement anyone can make (BLOCKER, ~15 min)

will still be queued when the next push adds twenty-five more.

The practical consequence is the one that matters for a release: **you cannot currently answer "is
`main` green?"** — some of `main`'s runs have never started. And the release job (`Create Release`,
`0s`, skipped) sits at the end of that same queue, so R1's fix depends on this one. A standard
`concurrency: { group: ${{ github.workflow }}-${{ github.ref }}, cancel-in-progress: true }` is the
whole fix.

### R9 — the nightly failures nobody is reading

that is the problem: a nightly that is habitually red is a nightly nobody reads.

- `Integration (opensuse)` — image build fails on Tumbleweed mirror 404s and `unzip is required to

- `Integration (tools, nightly)` — lifecycle failure; this also skips the 30-manager argv sweep that

## 8. One page, no green

**What a user can rely on today.** The declarative loop works and is well tested. Write a line, sync,
the package appears; delete it, sync, it goes. The removal guard is a type-level proof rather than a
convention and it holds up when you enumerate the call sites from the code. The first-run experience
is genuinely good — `shall sync` on a bare machine names `shall init`, `init` scaffolds everything
including a starter module, and a typo'd package name is taken back out of your files with an error
that names the file, the line, and distinguishes "no such package" from "that manager could not
answer". The parallelism is real and measured: in the release build, 23.7 seconds of package-manager
work in 3.75 seconds of wall clock, 6.3× overlap.

**What they cannot rely on.** The 14 backends the coverage audit names as having no path to a real
lifecycle (cabal, composer, conda, flatpak, macports, mix, nix, opam, pkg, pkg_add, pkgin, snap,
spack, stack). Any option outside the seven that have been driven through an edit-and-resync.
`shall watch`, which locks the machine's other Shall commands for as long as it runs. And — today —
the install instructions on the README, which resolve to a release that does not exist.

**What I did not look at.** Two thirds of the backends beyond their argv, sudo, ptys, and the
container matrix (CI runs it; I read its output rather than reproducing it).

**The shape of the risk.** This codebase's recurring failure mode is not bad code — it is very good
code with a check pointed slightly to the left of the thing it guards, and three of my five bug
findings are that exact shape: a re-entrancy guard on one of three subcommands, a lock-scope fix
applied to three of six verbs, and an error-swallow fixed thirteen lines below where it still lives.
The repo knows this about itself; `GRADER.md` is 486 lines of nothing but that observation. The
useful conclusion is that the next round of work should be **enumeration, not inspection** — for
every rule this tree states, list its members from the code and check all of them, because the
misses are never the instance somebody looked at.

**Would I release it?** Not this week — but closer than the first draft of this document said. R8 is
fifteen minutes and unblocks the ability to answer "is main green?" at all. R1 and R2 are hours and
must happen regardless. R3 and R4 are small, well-understood fixes in one family. R5 is a real fix
plus a decision about what the suite is for. The platform coverage I had marked unproven is largely
proven — the honest README caveat is not "macOS untested" but "these 14 backends are argv-tested
only". That is a plausible one-to-two-week path to a `0.8.1` that is honestly shippable.

The thing worth saying plainly: this is a better-engineered codebase than the bug list suggests. The
findings are concentrated, they are all in one family, and the family has a name.

## 9. The work order — written to be executed, not read

Ordered. Each item states the file and line, the change, the test that proves it, and how to verify.
Line numbers were re-checked against this tree; if one has moved, the surrounding quoted code is the
real anchor.

**Read `CLAUDE.md` first.** Three of its rules bind every item below: *no legacy* (delete the old
thing in the same change), *fix the whole family* (find the siblings before calling it done), and
*every open question lives in `docs/spec/decisions.md`* (do not answer one in code). Bug fixes are
failing-test-first: write it, watch it fail, then fix.

### Tier 0 — housekeeping, one sitting, no design decisions

**W1. Give CI a concurrency group.** `.github/workflows/ci.yml` has no `concurrency:` key. Add
below `on:`:

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

*Why it is first:* six runs are queued 14–18 hours behind each other, so no statement about `main`
being green is currently true, and the `Create Release` job cannot reach a runner. Every item after
this one is verified through CI.
*Verify:* push, then `gh run list --limit 5` — superseded runs should show `cancelled`, not `queued`.

**W2. `cargo fmt`.** Four sites: `src/app/sync/mod.rs` (~868, ~897, ~928), `src/verbs/packages.rs`
(~632). *Verify:* `cargo fmt -- --check` exits 0. Note it fails on **committed** source, so this is
a fix, not hygiene.

**W3. Cut the first release.** `git tag -a v0.8.0 -m ... && git push origin v0.8.0`. The release job
fires on `refs/tags/v*` (`ci.yml:319`) and has never fired.
*Verify — and this is the whole point of the item:* on a machine with no Rust toolchain, run
`scripts/install.sh` and confirm it downloads a binary rather than falling back to a fifteen-minute
`cargo install`. The bug is not the missing tag; it is that the documented install path resolves to
nothing. Do the same for `scripts/install.ps1`.

**W4. Fix the macOS canary.** `tokei@14.0.0` is not a Homebrew formula, so the pinned-version canary
fails and the harness reports it as a **lock** failure (see R7). Two changes, and the second matters
more: pick a formula/version that exists, **and** make the lock assertion distinguish "the lock was
not taken" from "the run failed for some other reason". A check whose name and cause are unrelated
is the defect `GRADER.md` exists to catch.
*Verify:* `gh run list --workflow=CI` nightly, `macos-native` green.

**W5. Fix the `launchctl` row.** `src/core/argv.rs:446` lists it `false` (does not terminate) with
`Evidence::Unasked`; the probe measures that it does terminate, on macOS and Windows both. Set it
`true` and replace the evidence with the probe's own output. *Family check:* every other
`Evidence::Unasked` row is an untested claim of the same kind — the probe only reaches rows where a
backend built an argv carrying an operand on a host that has the binary. List them and say which
remain unmeasured.

**W6. Unbreak the opensuse and tools images.** Tumbleweed mirror 404s and `unzip is required to
install bun`. Infrastructure. If openSUSE cannot be made reliable, delete the image rather than
leave a habitually-red nightly — a red nightly is a nightly nobody reads, which is worse than no
nightly. The `tools` failure additionally skips the 30-manager argv sweep, which is the only place
`luarocks`, `mix` and `asdf` are ever asked a question.

### Tier 1 — the bug family: a check pointed slightly left of the thing it guards

Do these together. They are one bug wearing three hats, and fixing them one at a time is how the
tree got into this shape.

**W7. The hook re-entrancy guard covers one of three subcommands.** `src/main.rs:143`:

```rust
if matches!(cli.command, Commands::HookReconcile { .. })
    && env::var_os(shall::core::executor::INSIDE_SHALL).is_some()
{ return Ok(()); }
```

`Commands::HookRecord` and `Commands::HookObserve` (dispatched at `main.rs:497` and `:503`) are not
matched, and both are in the `writes() => true` arm of `src/cli/args.rs` — so they take the
exclusive data lock. Shall installs a pacman `PostTransaction` hook that calls `hook-record`
(`src/app/pm_hooks.rs:73-178`), which runs while Shall holds that lock: **+120 seconds per pacman
transaction and the record is lost.**
*The fix is not to add two more arms.* Make the condition a property of the command — "is this a
hook subcommand" — so a fourth hook subcommand cannot be added without inheriting the guard. That is
what makes it a family fix rather than a third patch.
*Test:* set `SHALL_INSIDE`, invoke each hook subcommand, assert none blocks and none waits on the
lock. Assert on **all** hook subcommands by enumeration, not by naming three.

**W8. `watch`, `shell` and `run` hold the exclusive lock for unbounded time.** `src/cli/args.rs`,
the `=> true` arm at ~967-1008. `Self::Watch` holds it **forever** — so the documented GitOps
deployment disables every other Shall command on that machine for as long as it runs. `Self::Shell`
holds it for the length of an interactive subshell.
This is the same fix already applied to `edit`, `history` and `fleet` — whose comments in that
function record the bug being found and fixed three separate times. Apply it to the remaining three:
the long-running verb takes the lock **around each mutation**, not around its lifetime.
*Test:* start `watch`, assert a second Shall command completes. Same for `shell` and `run`. And
extend it: assert that **no** command that can run unbounded is in the whole-lifetime lock set.

**W9. A resolver failure is reported as "not installed on this machine".**
`src/app/context.rs:732`:

```rust
let specs = self.resolve_spec(package_name).await.unwrap_or_default();
```

When resolution fails this yields empty, the loop below never runs, and the caller returns
`Ok(None)` → *"is not installed on this machine"*. **Thirteen lines below it**, at `:739-743`, sits
the comment fixing this exact class:

> *A manager that could not be asked has not said no… Absence and unavailability are different
> answers and only one of them is knowable.*

`src/app/sync/planner.rs:566-606` shows the correct shape (`installed_sets` / "unknown means yes").
This is also the cause of the red test `grade2_info_tests::info_agrees_with_list_about_every_backend_not_only_the_first`,
which passes alone and fails under suite parallelism because `winget list` falls over under
concurrent load.
*Family check — the point of the item:* `unwrap_or_default()` on a fallible query is the bug, not
this line. Grep for it, and for `.ok()` and `unwrap_or(false)`, across every path that turns a query
result into a statement about the user's machine.
*Verify:* `cargo test --no-fail-fast` green, and green **repeatedly** — `--test-threads` currently
decides the outcome, which is the real finding.

### Tier 2 — the coverage that would change what you can honestly claim

**W10. Drive every `PACKAGE_OPTION_KEYS` key through edit-and-resync.**
`src/config/grammar/statement.rs:1801` lists **27 keys**; seven have been driven through the cycle.
An option that is read once when the install argv is built and never again **passes every lifecycle
test forever while doing nothing.** Twenty keys are shipped features that may be inert.
*Test shape:* for each key — declare it, sync, change it, sync again, assert the machine changed.
Table-driven over the constant itself, so key 28 fails until it has a case.
*This is the highest-value item in the document.* It is a whole class of feature nobody has
confirmed exists.

**W11. Close the 14 backends with no real lifecycle.** The macOS audit names them: cabal, composer,
conda, flatpak, macports, mix, nix, opam, pkg, pkg_add, pkgin, snap, spack, stack — and prints
*"Q4: this is the release blocker, not a caption."* Most need a container image that has the
manager; `docker/integration/Dockerfile.tools` already carries thirty. Ratchet
`scripts/lifecycle-floor.txt` down as each lands. Anything still on this list at release time
belongs in the README as argv-tested-only, by name.

**W12. Give the fan-out commands a latency budget.** `src/core/latency.rs:49-55`:

```rust
Class::EveryBackend | Class::Mutating => None,
```

`list`, `search`, `check` and `adopt` — the commands users run most — carry no ceiling, so a change
that serialises the fan-out drops overlap 6.3× → 1.2× and nothing notices. `--timings` already
computes overlap and wave count (`src/core/timing.rs:170-191`, a correct interval-union counter);
nothing gates on them. Assert on **overlap ratio**, not wall clock — wall clock on a CI runner is
noise, and the ratio is the property you actually care about.

**W13.** Before tagging, make the README's claims and the test evidence agree: which backends have a
real lifecycle, which are argv-tested, that `dpkg -i`/`rpm -U` handoff and U30 storage removal have
not been executed. This repo is unusually good at refusing to overclaim in its code and its error
messages. The README should hold the same line.

### The rule that should govern all of it

**Enumerate, do not inspect.** Every finding in §1 is a rule applied to some of its members. For

## 10. Dreams — what this could be, once it ships

Not blockers. Do not let any of it delay `0.8.0`.

**The thing you have already built and may not have noticed.** Shall knows how to ask 52 package
managers a question, hold their answers in one model, and tell you when a manager *could not be
asked* rather than guessing. That machinery is more valuable than the declarative sync sitting on
top of it. The most interesting product here might be *"one honest question, every manager on this
box, in 3.75 seconds"* — and `list`/`search` are already that, today, with 6.3× overlap.

**The reproducibility ladder Nix owns and nobody else climbs.** Nix's real pitch is not declarative
config, it is *this machine and that machine are the same machine*. You have generations, a WAL, and
snapshots. The rung above is a lockfile with resolved versions and hashes, so `shall sync` on a
second machine produces a bit-identical set. You have `sha256` and `version` in
`PACKAGE_OPTION_KEYS` already — the primitives exist; nothing composes them into a machine identity.
That is the feature that would make people leave `metapac`.

**Fleet, taken seriously.** `shall fleet` compares machines over SSH. The version of that which
people would pay for is *"twelve machines, one manifest, tell me which three have drifted and
what"* — the honest-answer machinery is exactly what makes it trustworthy, because a fleet tool that
guesses is worse than no fleet tool.

**Pick one interpreter.** `mlua` (vendored C), `rhai` and `tera` all ship. `rhai` alone would do.
This is the clearest instance of scope in the tree, it costs compile time and binary size on every
build, and deleting two of the three is a *feature* by this repo's own NO LEGACY rule. Needs an
owner ruling because it removes a surface — so it is a `decisions.md` entry, not a code change.

**The thing worth protecting above all of it.** This codebase's distinguishing quality is that it
refuses to state what it does not know. "That manager could not be asked" instead of "not
installed"; a type-level `Reaped` token instead of a comment saying the guard ran; a nightly that
fails by name rather than being edited green. That is rare and it is the actual product. Every
feature above is worth having only if it is built to the same standard — and the fastest way to lose
it is to ship a feature whose honesty was never tested, which is precisely what W10 is about.

# Part VI — Bugs

*[LiNix v7](../SPEC.md) — the map is there; this is one part of it.*

## VI.0 The worst one, at the top because a table row was not enough

**FIXED 2026-07-23 — the line is deleted, not guarded, and the four tests that prove it are
below.** `heal()` no longer removes on any branch of the install path; a `--dry-run` reports the
recovery it would perform and performs none of it, and takes the data lock like every other
writer. What follows is kept as written because the reasoning is the reason for V.64 and for the
rule in II.10, and because the *habit* it indicts is not fixed by a commit.

**S24 — LiNix uninstalls software nobody asked it to uninstall, and no refusal in this document
applies.** Not a design tension, not a deferred trade-off: a package that is installed,
declared, wanted and protected can be removed by a command that was asked to install something
else. It happened on 2026-07-23, on the owner's own machine, to Google Chrome, from
`linix -y install nimble:nimjson`.

**Why it is the worst bug here and not merely a bad one.** Every other removal defect in this
document is a removal that was *wrong*; this is a removal that is **unaccountable**. It does not
appear in `plan`. It does not appear in `--dry-run` — worse, `--dry-run` performs it (**S25**).
It is not counted, so `max_removals` never sees it. It is not checked, so `protected_packages`
and OS-essential never see it. It leaves no history entry. **A user cannot discover it before it
happens, cannot see it while it happens, and cannot find it afterwards.** Every guarantee in
II.10 is expressed as a refusal, and a refusal that is never consulted is not a weak
protection — it is decoration.

**What makes it worse than the sum of its parts.** It is armed by interruption. Any run that
dies mid-install — Ctrl-C, a reboot, a killed process, S26's hour-long sleep hitting a timeout —
writes a record that the *next* run recovers by uninstalling. So the natural response to a hung
LiNix is precisely the action that loads the gun, and the person most likely to fire it is
someone debugging LiNix. That is how a rare fault becomes a reproducible one.

**What it says about this document.** II.10 has claimed "every removal path calls it" through
thirteen sessions and an adversarial audit that existed specifically to find false claims. It
was false the whole time. **S6 looked directly at `heal` and asked the guard question — of the
other branch**, wrote down a careful answer, and moved on; the branch it did not read was four
lines away. A claim that is checked against seven paths and not the eighth reads exactly like a
claim that is true. **The audit habit this document is proud of did not catch this. Running the
thing did.**

**The number that should end any argument about test coverage: `cargo test` is green.** 970
passed, 0 failed, measured on this tree on 2026-07-23 — over a binary that uninstalls declared,
protected software with no guard and no record. The suite is not weak; it is aimed at the paths
somebody thought of, and nobody thought of this one. **IV.1's rule that a check must be able to
fail is satisfied here and still bought nothing**, because no check was pointed at `heal`'s
install branch at all. A test that does not exist cannot be vacuous — it is just absent, and
absence is invisible in a green run.

Filed in full below as **S24**, with **S25**, **S26** and **S27** — the three that stood between
anyone and finding it.

  **(verified)**

  exclusion. **(verified)**

  success. **(verified)**

  **(verified)**

  `prune_stale_snapshots` is deleted; all pruning goes through `prune_with_policy` +
  `Config::snapshot_retention()`. See the Phase 4 "one retention engine" note.

A backslash is a path separator on Windows and an ordinary filename character everywhere else, so `strip_prefix` splits that into components on Windows and treats the whole string as one name on unix — where the assertion returns `C:/repo/modules/x.txt:7` and fails. **The product is right and the test was wrong**: LiNix never sees a `C:\` origin on Linux. Split in two — `sources_are_repo_relative` on platform-native paths everywhere, `windows_sources_come_back_with_forward_slashes` under `#[cfg(windows)]`. **Family checked:** 15 other sites hand a `r"C:\…"` literal to something, and only this one asked `Path` for *path semantics* — the rest (argv quoting, grammar parsing, the `setting` regex, `windows_shim_wrap`'s `.extension()`) treat it as an opaque string and are platform-independent; `config/config.rs:850,864` and `backends/onboarder.rs:1110` already pick their root with `cfg!(windows)`, which is the pattern this now follows. **Verified on Linux, not argued:** the suite was run in the `linix-it-ubuntu` container, which also has no global git identity, so S33 and S34 are both proven fixed on a host that reproduces both. |

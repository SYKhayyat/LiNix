* How this started

A Docker test run reported one failure on Ubuntu and Arch:

: conflicts --json not JSON

The message was false. ~conflicts~ was working and returning valid JSON the whole
time. The test script checks JSON validity by piping output into ~python3~. Earlier
in the same run, LiNix had deleted ~python3~ from the container, so the check could
no longer parse anything and blamed every later command.

The visible failure was a symptom. The real event: a routine test run caused LiNix
to run ~apt-get purge~ on hundreds of system packages.

* Background: the two records

Nearly every problem here lives in the gap between two records.

** Record 1 — the wish list

Text files listing packages you want, one per line, in a folder. The ~-g~ flag
(~--groups-dir~) chooses *which folder*. Its whole definition is one line
(=src/cli/args.rs:34=): "Directory containing package group files (.txt)". Without
~-g~, LiNix uses a default folder in your config directory.

** Record 2 — the ownership record

One file, ~registry.json~, listing every package LiNix manages, at one fixed
location (=src/core/state.rs:176=). There is only ever one.

*=-g= does not affect this file at all.*

** How they interact

~plan~ compares them. Anything in the ownership record but missing from the wish
list is *drift*, and drift is scheduled for deletion (=planner.rs:191-233=).

Change which folder ~-g~ points at, and you have swapped the wish list out from
under an ownership record that did not move.

* Group A — the original bug chain
:PROPERTIES:
:DESCRIPTION: Four confirmed steps from "run the tests" to "python3 is gone"
:END:

** A1 =BUG= =DECIDED= — ~migrate~ adopts every package, not the ones you chose

~migrate~ asks each backend "which packages did the user install?" (=migrate.rs:77=).
For apt, nobody configured an answer, so it fell back to *everything installed*.

Measured on the real Ubuntu image:

| Question                        | Command               | Answer |
|---------------------------------+-----------------------+--------|
| Everything installed            | ~dpkg-query -W~       |    579 |
| What the user actually chose    | ~apt-mark showmanual~ |    103 |
| Pulled in as dependencies       | ~apt-mark showauto~   |    476 |

LiNix claims 579 packages when you chose 103, including ~libperl5.38t64~. Everything
in the ownership record is a deletion candidate, so it has quietly put your whole
dependency tree on a list of things it may delete.

*Fix:* apt has ~apt-mark showmanual~. It is a separate binary from apt's listing tool
(~dpkg-query~), which is why nobody wired it up. Verified: ~libperl5.38t64~ is absent
from its output.

*Note:* the original report also asked to wire ~pacman -Qqe~. Already done
(=registry.rs:276=). Verified on arch: 11 explicit vs 173 installed. A1 is apt-only.

** A2 =BUG= =DECIDED= — when a backend cannot answer, the code guessed "everything"

The fallback conflates two different situations:

- "Listing everything is *correct*" — true for winget, which installs no dependencies.
- "I have no idea" — true for apt and pip, which install dependencies and keep no
  record of what you chose.

For winget the guess is right. For apt it is catastrophic. This is the mechanism
behind A1, and it will reproduce on the next unconfigured backend.

*Decision:* label every backend explicitly — has a command / everything is
user-chosen / cannot tell, adopt nothing and say why.

** A3 =BUG= =DECIDED= — nothing stops a plan from deleting hundreds of packages

~apply~ executes removals with no size check and no content check. Live output shows
it purging ~libpam-modules~, ~libperl5.38t64~, ~libpam0g~ and hundreds more at ~1s
each until ~python3~ was gone and apt's resolver refused to continue. The run blew
its 180s limit and was killed.

*The detail that shapes the fix.* We asked the OS what it considers essential:

: dpkg-query -W -f='${Essential} ${Priority} ${Package}\n'

Only 23 packages are ~Essential: yes~; 34 are ~Priority: required~. *~python3~ is
neither* — it reports ~no optional~. Yet it is in ~apt-mark showmanual~ and deleting
it wrecks the machine.

So the OS flags are useful but *not sufficient* — they would not have saved the exact
package the acceptance criteria name. Protection needs three sources: a count limit,
a list we maintain, and the OS flags.

*Decision:* refuse a plan that is too large or touches an essential package. You can
set the count, add protected names, and un-protect names. ~--allow-mass-removal~
overrides. Plain ~-y~ must *not*, because every script and CI job passes ~-y~, and an
unattended run cannot notice a system being dismantled.

** A4 =BUG= =DECIDED= — the JSON check breaks permanently once ~python3~ disappears

The script picks an interpreter once at startup (=run-in-container.sh:102-108=) and
never re-checks. Test infrastructure only. It does not excuse A1–A3.

I put the safety check in ~apply~. But ~prune~ is the *other* drift-removal command,
with its own separate path (=main.rs:2470=) and no check at all.

The container script runs both:

|------+-----------------------------+--------------------------------------------|

** B2 =BUG= — the check covers one of ten deletion paths (high)

** B3 =BUG= — the un-protect hatch does not work, and the inspector lies (high)

My comment promises "an explicit unprotect entry always wins, including over a

Worse, my ~protected~ command asks the same questions in a *different order* and

$ linix apply                 → refuses, because dash is essential

The feature you asked for is broken, and the inspector contradicts the rules.

** B4 =BUG= — 15 backends changed silently by inheritance (medium)

Your A2 decision was that every backend gets a *deliberate* label. I set a safe
default on the shared helper and let 15 backends inherit it without deciding
anything: composer, opam, luarocks, nimble, pixi, spack, mix, helm, cabal, stack,
asdf, guix, emerge, eopkg, slackpkg.

For guix/emerge "cannot tell" is arguably right. For helm, composer, cabal, stack,
asdf, pixi, luarocks everything installed genuinely *is* user-chosen — so I quietly
broke ~migrate~ for them. This is the inference you rejected, reintroduced as a
"safe default".

** B5 =BUG= — ~conda~ has the identical bug and the fix does not reach it (medium)

~19 backends hand-write their own code instead of using the shared configuration, so
the labels never reach them; their default is the old "everything is user-chosen".
=conda.rs:133= is A1 verbatim. A conda environment is mostly dependencies (~mkl~,
~libgcc-ng~), and conda is registered by default.

** B6 =BUG= — the essential reader can drop a package (medium)

It reads three fields by counting from the *front*. ~Priority~ is optional in dpkg;
if empty, everything shifts and the package is skipped. A package marked
~Essential: yes~ could silently lose protection. This is the safety query — it must
fail closed. Read the name from the *end*.

** B7 =OPEN= — my protected list is too broad (low)

~python3*~ matches ~python3-pip~, ~python3-dev~ and every apt-packaged python
library. Anyone managing ~apt:python3-pip~ could never remove it. ~python3~ must be
protected by name (A3 explains why the OS won't), but the radius should be ~python3~
and ~python3-minimal~ exactly. Same for ~libssl*~/~openssl~.

** B8 =BUG= — multi-architecture names break (low)

~apt-mark showmanual~ prints ~libc6:i386~ on multi-arch hosts. My parser strips
version constraints and repo tags but not ~:i386~, while the listing command prints
the bare name — permanent phantom drift.

** C3 =BUG= =OPEN= — lease and bloatware removals skip the protected list

In the planner (=planner.rs:200-218=) both schedule deletions without checking

** C4 =BUG= =OPEN= — the order wish-list files are read in is undefined

The code lists a directory and takes whatever order the filesystem returns
(=resolver.rs:174=). If ~a.txt~ says ~apt:jq@1.6~ and ~b.txt~ says ~apt:jq@1.7~,
which wins is decided by the filesystem, not a rule. Any precedence rule built later
sits on sand, so this must be fixed before [[*Group D][Group D]].

** C5 =OPEN= — no way to say "stop managing this, but keep it installed"

*You found this.* After ~migrate~ hands you ~100 lines, keeping 15 and deleting the
rest is an instruction to *purge 85 packages*, including ~python3~. Deleting a line
means uninstall. There is no forget command — ~unmanaged~ only *lists*, and
~state.remove()~ is only called when a package is genuinely uninstalled. The
catastrophe returns through the *intended* workflow. You asked to add this to discuss.

** C6 =BUG= =OPEN= — some commands write to your real config folder despite ~-g~

~repo add~ (=run-in-container.sh:622=), ~shim~, and ~doctor --fix~ ignore ~-g~ and
write to the default folder. Harmless today because ~-g~ replaces; becomes
cross-test contamination once ~-g~ is additive — and nastily, a leaked entry is *in*
the wish list, so ~prune~ spares it, inverting test assertions.

** C7 =BUG= =OPEN= — ~-b~ does not scope pruning

~linix --backend cargo prune~ still removes apt drift. The drift loop
(=planner.rs:191-233=) never consults ~is_backend_enabled~; only the separate
system-scope loop does (=planner.rs:243=). Also ~merge_cli_overrides~
(=config.rs:545=) *overwrites* ~enabled_backends~ with ~-b~, silently re-scoping.

** C8 =BUG= =OPEN= — ghost-shell cleanup removes with no checks at all

Transient packages are force-removed on shell exit (=shell/mod.rs:277-300=) by
hand-building a removal graph and calling the engine directly: no ~is_protected~, no
guard, no confirmation.

** C9 =BUG= =OPEN= — lease expiry is implemented twice, with different semantics

=planner.rs:200= checks the wish list first; =context.rs:320= ~sweep_expired_leases~
does *not* — it removes an expired package even if a manifest still declares it.
Neither checks protection. The sweep runs on *every* state-changing command
(=main.rs:4146=).

** C10 =BUG= =OPEN= — the migrate manifest is not atomic, despite claiming to be

=migrate.rs:142= says "Atomically create and write the manifest file". It is
~File::create~ + three sequential writes. A crash mid-write leaves a truncated
manifest. Your own ~atomic_write~ helper (=utils/file.rs:9=) does temp-and-rename and
is used correctly at *10 other sites*. This path claims the property instead of
calling the function.

** C11 =BUG= =OPEN= — ~migrate~ and ~audit~ have drifted apart

Near-duplicate discovery loops (=migrate.rs:52-105= and =:203-222=). ~migrate()~
checks ~is_managed(&pkg.backend, …)~; ~audit()~ checks ~is_managed(backend.name(), …)~.
~audit()~ swallows backend errors (~if let Ok~) while ~migrate()~ warns — so the
*preview* silently hides failures the real run reports.

** C12 =BUG= =OPEN= — the ~orphans~ message is false on both counts

=main.rs:2313= prints "N package(s) would be removed by ~linix sync~/~linix clean~".
~sync~ will not remove them (~prune_on_sync~ defaults false) and ~clean~ removes
*backend-native* orphans, an unrelated set. Only ~linix prune~ removes these.

** C13 =BUG= =OPEN= — five ~backend:name~ parsers; three skip validation

=config/parser.rs:200-217= is canonical and documents *why* the backend-name check
matters ("so package names that legitimately contain a colon aren't misread"). Then:

| Site                | Validates the prefix is a real backend? |
|---------------------+-----------------------------------------|
| =config/parser.rs:211= | yes                                  |
| =main.rs:619=          | yes                                  |
| =main.rs:2836=         | *no*                                 |
| =main.rs:1347=         | *no*                                 |

* Group D — the model problem
:PROPERTIES:
:DESCRIPTION: The root cause, and the design you chose
:END:

** D1 =BUG= =DECIDED= — ~-g~ replaces the wish list, but the ownership record never moves

The root cause is one line (=config.rs:550-551=):

#+BEGIN_SRC rust
if let Some(gd) = groups_dir {
    self.groups_dir = gd;      // REPLACES.
}
#+END_SRC

That field means *two things at once*: the wish-list folder (which ~-g~ was meant to
change) and the *anchor* for everything else (which it was never meant to touch):

| What                 | Where it lives                  |
|----------------------+---------------------------------|
| version pins         | ~<groups_dir>/locks.json~       |
| the keep list        | ~<groups_dir>/keep.txt~         |
| imperative installs  | ~<groups_dir>/local.txt~        |
| profiles             | ~parent(<groups_dir>)/profiles~ |
| generations, bundles | ~parent(<groups_dir>)~          |

The failure:

1. ~migrate -g /A~ writes a protective file into =/A= *and* records ownership globally.
2. ~plan -g /B~ reads =/B=, which says only ~apt:jq~. Ownership still claims 579.
3. 578 are owned but unwished → all drift → all scheduled for deletion.
4. The file that would vouch for them is in =/A=; nothing told this command to look.

*Evidence you were right.* ~protect_imperative~ (=config.rs:179=, default *on*)
exists solely to stop drift-pruning from deleting ~linix install~-ed packages, which
live in ~<groups_dir>/local.txt~ and hit this exact trap. Someone met this before and
patched the symptom.

*Your design:* one *global* folder always read (the *existing* default folder, not a
new concept). ~-g~ becomes *additive* and accepts *multiple* folders. ~--no-global~
opts out. ~locks.json~/~keep.txt~/~local.txt~/profiles always live in global.
~migrate~ writes into global, because adoption is a fact about the machine and
ownership is already global. *That alignment is the actual fix.*

*The one real cost.* ~-g~ can then only *add*, never subtract: ~sync -g /scratch~ on
a machine whose global lists 100 packages installs all 100. That is the safety
property you want, but a ~-g~ folder is no longer an isolated sandbox.
~--no-global~ is the release valve.

*Why it splits cleanly.* Keep ~groups_dir~ meaning "the anchor" and ~60 places that
join ~locks.json~/~keep.txt~ onto it need *no change and become correct for free*.
Only ~10 places mean "the wish list".

** D2 =BUG= =OPEN= — the harness cannot prove any of this

1. ~migrate~ is only checked for exit code 0 (=run-in-container.sh:627=,
   =integration-windows.sh:429=). *Neither harness would have caught the original bug.*
2. The harness deliberately does *not* isolate the config folder ("so the real backend
   settings still apply"). Under the new model that makes global your *real* folder.
   It must isolate it (=LINIX_CONFIG_DIR= already exists) *before* the model changes.

** E1 — there are 16 mechanisms that spare or force a removal

~protected_packages~, ~keep.txt~, ~protect_imperative~, ~remove_bloatware~,
~prune_scope~, ~prune_on_sync~, ~confirm_destructive~, expired leases, transient

the single largest "spare everything" switch — and it is an implicit consequence of a
function argument, not a setting.

No document states how they compose. Several contradict each other.

** E2 — ~keep.txt~ is fully redundant with ~protected_packages~

=config.rs:634-654= literally pushes keep.txt entries *into* ~protected_packages~
before any consumer runs. Zero behavioural difference. But they are *presented* as
two things (=main.rs:1404=, =args.rs:494= say "keep-list and protected packages"),
~linix managed keep~ edits one, ~linix protected~ reads the merged result, and
nothing edits ~protected_packages~. Keep.txt entries also support ~*~ wildcards *by
accident* (inherited), documented nowhere — while =main.rs:2969= claims matching is
"exact, case-insensitive", contradicting =config.rs:231=.

** E3 — "prune" means four unrelated things

Drift removal (=main.rs:2421=, ~PruneScope~, ~prune_on_sync~); snapshot expiry
(=context.rs:517=); retention expiry (=sync/mod.rs:252=); and
~SnapshotSettings::auto_prune~ (=config.rs:51=).

** E4 — snapshot retention is implemented twice, with opposite defaults

~config.snapshots~ (30 days / 10 count / auto_prune on) drives
~prune_stale_snapshots~ from ~perform_maintenance~. ~config.retention.snapshots~
(keep_last/keep_days, *default keeps everything*) drives ~prune_with_policy~ from
~record_generation~. Both run after a sync. Two policies, two engines, opposite
defaults, one target.

** E5 — "orphans" is two concepts, and a dead third name

~linix orphans~ = LiNix drift. ~clean_orphans~/~linix clean~ = backend-native
dangling dependencies. Plus the dead ~purge_orphans~ field naming a third thing.

** E6 — "unmanaged" has two incompatible implementations

~App::get_unmanaged_packages~ (=context.rs:298=) = installed minus state, *no*
protection filter, *no* ~tracks_manual~ gate. ~Migrator::audit~ (=migrate.rs:198=) =
manual minus state, *with* both. Both surface to users (~linix unmanaged~, ~status~)
and will disagree.

** E7 — "protected" means two opposite things

In ~planner~/~guard~ it means "never remove". In =migrate.rs:89,215= it means "never
*adopt*". Same function, opposite domains — which is why protected packages silently
never appear in ~unmanaged~ via ~audit~.

** E8 — four verbs for overlapping ideas: protect / keep / hold / unprotect

~protect~ and ~keep~ are the same thing (E2). ~hold~ (=state.rs:126=,
=planner.rs:358=) *sounds* like protection but blocks *upgrades only* — a held
package is still fully removable by drift pruning. ~unprotect~ negates two of them
plus a fifth source (OS essential).

** E9 — backend allow-listing has three names

~enabled_backends~ (=config.rs:126=), ~hostname_backends~ (=config.rs:142=),
~policy.allow_backends~ (=policy.rs:25=). Only the first two merge (=config.rs:514=);
the policy one is checked separately and only for installs.

** E10 — "keep" is also two concepts

~keep.txt~ = never remove a *package*. ~retention.keep~/~keep_last~/~keep_days~ =
never delete a *history entry*.

** E11 — session-suspension restore is implemented twice

=context.rs:421= and =shell/mod.rs:306=. Same name, same contract, two bodies.

** E12 — ~confirm_destructive~ gates a non-destructive thing

Documented as "destructive operations (removals) require confirmation"
(=config.rs:219=). It also gates a *module file overwrite* prompt (=main.rs:1279=),
and does *not* gate ~prune~ (own prompt, =main.rs:2458=) or ~sync~ (TUI,
=main.rs:425=). Three confirmation designs for one question.

** H1 =BUG= =OPEN= — signed lockfiles fail open exactly where they're sold

=locksig.rs:3-9= advertises tamper-evidence. =resolver.rs:66-76= correctly fails
closed on a *mismatch* — then =:78-84= undoes it:

#+BEGIN_SRC rust
// No local key (e.g. a fresh machine restoring a bundle): we
// can't verify, but refusing would break reproducibility, so
// proceed with a clear notice.
None => warn!("...Proceeding unverified."),
#+END_SRC

~read_key~ returns ~None~ when the key file is *absent*. So *deleting the key file
bypasses verification entirely* — and anyone who can edit ~locks.json~ can also
~rm~ the sibling key, because =locksig.rs:38= puts the key in the same directory.

Worse, =bundle.rs:71= *deliberately strips the key* from bundles — so every
air-gapped bundle restore, the headline use case, takes the unverified path by
construction.

The one integration test (=run-in-container.sh:815-822=) flips a signature byte. It
never tests the delete-the-key bypass.

Minor, same file: ~sign()~ is a hand-rolled ~sha256(key || "|" || text)~ prefix-MAC
rather than HMAC, and ~verify()~ uses non-constant-time ~==~.

*Credit where due:* excluding the key from bundles and from git (=core/git.rs:122=)
shows someone *did* think about key leakage — which is what makes the fail-open read
as unreviewed rather than naive.

** I0 =IMPORTANT= — Stage 1 caps the blast radius; it does NOT fix the root cause

Measured on the real alpine image. ~migrate~ correctly adopts 14 packages (the world
file's user-chosen set, minus protected ones). A ~prune~ under a *different* ~-g~ then
schedules *all 14 for removal* — git, nodejs, npm, ruby, rustup, perl, curl, build-base —
and *the guard does not fire*, because 14 is under ~max_removals~ (20) and none are on the
protected list.

This is correct by today's rules and still the D1 bug. The guard is a backstop against
*mass* removal; the ~-g~/global-state split is what actually causes phantom drift, and only
[[*Stage 4 — the ~-g~ model change][Stage 4]] fixes it. On Ubuntu the fix appears total only because 84 adopted packages
happen to exceed the limit.

*So the honest claim for Stage 1 is:* a mis-scoped command can no longer purge a system,
and can never remove a protected or OS-essential package. It can still remove a handful of
your own packages on a small machine. Stage 4 is not optional.

The harness now records exactly this, rather than asserting a refusal that only holds on
big systems.

** I1 =BUG= — the harness is one Windows checkout away from never running

The repo has *no =.gitattributes=* and git on Windows defaults to =core.autocrlf=true=, so
every =.sh= is rewritten to CRLF on checkout. Those scripts run under =dash= inside the
Linux containers, where a trailing carriage return turns line 41's ~set -u~ into
=set: Illegal option -= and the whole harness dies before a single test runs. Hit live
during this work.

Fixed by adding =.gitattributes= pinning =*.sh=, =*.bash= and =Dockerfile*= to =eol=lf=.
The =.rs= files are unaffected — git normalizes them on commit, and the compiler does not
care either way.

** I2 — `conda` was the same bug, and it is now fixed with verified evidence

=conda list= returns the env's whole solved closure. Measured on the tools image's stock
=base= env: *88 packages installed, 4 actually requested*. `conda env export --from-history
--json` reports the 4, in clean JSON. Wired up and unit-tested against the real payload.

** I3 — one e2e test is flaky on Windows, and it is not ours

=test_e2e_sync_flow_hermetic= intermittently fails with =Access is denied (os error 5)=
writing the WAL journal, when cargo runs several test binaries in parallel. Confirmed by
stashing: it passes on a clean baseline *and* on this branch when run alone; two full suite
runs afterwards were green (361 passed, 0 failed). Worth a look, unrelated to this change.

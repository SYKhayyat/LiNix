### F1 — `main` does not compile on any Unix — *blocker*

`RawExecutor::TERMINATION_GRACE` is a private associated const in `src/core/executor.rs:351`.
`src/core/supervise.rs:58` names it from another module. Both are `#[cfg(unix)]`, so a Windows
build never sees either line and `cargo build` on this host is clean.

```
error[E0624]: associated constant `TERMINATION_GRACE` is private
```

Found in a container before I looked at CI; CI run `31655121309` agrees — MSRV, both Apple
targets, both Linux targets and all seven distro integration jobs failed. **Reproduced again
from the committed tree** on `rust:1-slim`, `cargo check --lib --locked`: one error, that one.

`git log -S` puts its introduction in **`d1b3618`**, and CI's last green main was `3affcc5` —
**26 commits earlier**. (An earlier draft of this section said six; the number was wrong and the
correction matters, because 26 is the size of the window in which nothing on any Unix was
compiled even once.) Only one commit separates `d1b3618` from the first run that went red, so CI
caught it on the first opportunity it was given; it was not given one for 26 commits.

**The blind spot, not the typo.** 45 `cfg`-gated blocks across 17 source files are invisible to
the verify chain in `CLAUDE.md`, because that chain runs on Windows only. The obvious cheap
cross-check is **not available**: `cargo check --target x86_64-unknown-linux-gnu` from this host
dies in `mlua`'s vendored C build for want of `x86_64-linux-gnu-gcc`. So a container or CI is the
only instrument, and the chain that gates a change does not use either.

### F2 — `check` reports a clean machine it could not survey — *blocker*

Ubuntu container, `priority` naming eleven managers, run with an empty `PATH` so none is
reachable:

```
$ shall check health
Backends: 4 OK, 0 degraded, 8 critical, 44 not installed (of 56 total).
  [FAIL] apt — `apt` is not on PATH, so the `apt` backend cannot run
         — and `priority` lists it, so Shall was told to use it
Some checks are CRITICAL. Install the missing tools, or run `shall heal`.

$ shall check ; echo $?
ok  health      4 backend(s) ready
Nothing needs you.
0
```

**Mechanism.** A manager not on `PATH` probes as `Absent`. `check health` promotes it
(`check.rs:840`): absent **and named by `priority`** is a failure, because the user wrote down
that this machine uses it. The `check` rollup consumes the same probe and never promotes —
`HealthStatus::Absent => {}` (`check.rs:382`) — so its `critical` is 0 where the detail view's
is 8.

**Ruled, not a judgement call.** `target-state.md` §Q2: *"The rollup and the detail view read the
same tally, because two counts of one machine will disagree."* The same table defines the
promotion the rollup skips: **critical** is *"it is installed, **or `priority` names it**, and it
cannot work"*.

**It was fixed here once and grew back by another road.** `check.rs:365`: *"This rollup used to
skip `critical` entirely … the rollup said `25 backend(s) ready` while `check health` called the
same machine `23 critical`."* That cure taught the rollup to count `Critical`. It left the
`Absent`→`Critical` promotion inside the one caller that performs it, so the rollup still cannot
see the failures that only exist after it.

**And the comment asserting this cannot happen is on the shared function.** `probe_all_health`
(`check.rs:149`): *"They share this one now, which is also what keeps the two views from
disagreeing about the same machine."* Sharing the probe was mistaken for sharing the verdict.

**Reachable with no `PATH` manipulation at all — `sudo` does it.** The empty-`PATH` construction
above proved the mechanism and invited the objection that nobody runs that way. Measured since, on
a stock Ubuntu container with real `sudo` installed and its shipped default
`secure_path="/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/snap/bin"`:

```
cargo  -> /root/.cargo/bin/cargo    INVISIBLE under sudo
bun    -> /root/.bun/bin/bun        INVISIBLE under sudo
uv     -> /root/.local/bin/uv       INVISIBLE under sudo
```

Three managers Shall supports, installed where their own installers put them, and off
`secure_path` by default. The identical repository, the only difference being `sudo`:

```
$ shall check                  ->  drift   4 to install ...     ok  health  13 backend(s) ready
$ sudo -n env SHALL_CONFIG_DIR=... shall check                  ok  health  10 backend(s) ready
```

`ok`, with three managers named in `priority` unable to run. That is the rollup's `Absent => {}`
reached without a contrived environment. (`sudo` also resets the environment, so the config dir
has to be carried across explicitly or the two runs read different repositories — the first
version of this measurement did exactly that and was thrown away.)

Also: `init` writes `priority` from what it finds, and a manager can leave afterwards.
`shall schedule` exists, so an unattended sync is a supported use, and it is exactly where `PATH`
is not the user's.

Red test: `tests/the_rollup_counts_the_same_machine_as_the_detail_view_tests.rs` (3 tests, 1 green
control).

### F3 — an option written after a value is silently absorbed — *blocker*

`config/grammar/options.rs:240` refuses `@version=1.0.0 @hold` and its message names the failure
exactly: *"`@hold` is absorbed into the option before it rather than being an option at all."*
The detector requires `bytes[i - 1].is_ascii_whitespace()`. Without the space it does not fire.

`cargo:ripgrep@version=1.0.0@hold` is therefore one package at version `1.0.0@hold`, with no hold,
and nothing says so. Ten of ten bare flags are lost this way — `hold`, `optional`, `system`,
`download_only`, `allow_http`, `unverified`, `classic`, `allow_shrink`, `sandbox`, `shim`.
`shall hold` then reports nothing held. Confirmed end to end against real apt.

Three of the losses are more than cosmetic: `hold` is what stops an upgrade moving a pin,
`sandbox` is what confines `shall run`, `system` decides whether a package is written into the
environment the OS owns.

Red test: `tests/an_option_after_a_value_is_not_swallowed_tests.rs` (4 tests, 1 green control).

### F4 — `Skipped` carries two opposite questions through one list — *major*

`SyncChanges::skipped` is fed by two producers that mean the reverse of each other:

| producer | what a row is |
|---|---|
| `planner.rs:369`, `planner.rs:705` (via `Declined::reported`) | a **removal** declined — installed, undeclared, and it stays |
| `planner.rs:793` | an **install** skipped — declared, *not* installed, and it does not arrive |

Three surfaces print that list, and all three describe every row with the first producer's
sentence: `sync.rs:902`, `plan.rs:273`, `check.rs:235`. For an install skip all three clauses are
false, and the follow-up advice — *"Declare them to keep them"* — asks for the thing the user
already did.

One `shall check` prints both of these, in this order:

```
 WARN `tree` is declared for `apt`, which is not on this machine — skipping it.
->  drift  1 package(s) installed and declared nowhere that `sync` will not remove: apt:tree
```

**This is the bug the type was built to stop.** `Skipped`'s own doc (`planner.rs:240`) says a
fixed sentence *"is wrong for every input it does not describe — `adopt` printed 'Left alone: 185
(listed in the manifest)' about items none of which were listed in the manifest."* The per-row
`reason` field exists because the reasons differ; the headers assert three facts about every row
regardless. `Declined::reported` makes the distinction carefully and correctly — and the install
path never passes through it.

The `drift` row is not only a sentence: it is what decides whether `check` reports the machine as
needing attention.

Red test: `tests/a_skipped_install_is_not_an_undeclared_leftover_tests.rs` (5 tests, 2 green
controls).

### F9 — a test in the suite asserts a property of the host — *major (raised from minor)*

`exit_code_contract_tests::a_refusal_exits_three_and_not_one` runs `purge-undeclared --yes` on a
scratch config and asserts exit 3. That refusal fires only when the machine has undeclared
packages; the test never establishes that. It passes on a developer machine and **fails on the
CI Windows runner** — the sole failure in that job, 534 passed, 1 failed:

```
assertion `left == right` failed: the unadopted-machine ratio refusal is a decision, not a failure
  left: 0
 right: 3
```

The command returns 0 when the crawl comes back empty (`cleanup.rs:277`), which on a host where
nothing can be listed is indistinguishable from a clean bill. Same family as F2.

**Raised to major on the evidence, which arrived after the first draft.** Two things were not
known when this was filed as minor:

**It is the only thing between Windows and green.** With F1 red on every Unix, Windows was
described in this document as the one platform that compiles and passes. It compiles. It does not
pass — and this single test is the entire reason. `Build for x86_64-pc-windows-msvc` is red at
`cfad22d`, so of five build targets in CI, **five are red**, and 19 of 24 jobs failed. The four
green ones are `Advisories and licences`, `Harness mutation`, `Shell scripts`, and
`Integration (Windows native, nightly)` — one of which builds and runs the program, and none of
which is a build target.

**It went red exactly when the inventory crawl was rewritten.** The `windows-msvc` job was green
for the eight runs before `cfad22d` and red for both runs at it. `cfad22d` is the commit that
created `src/app/inventory.rs` (+438 lines) — the file holding `installed_but_undeclared`, which
is precisely what decides whether the crawl comes back empty. *Stated as the correlation it is:*
I have not run a pre-refactor and a post-refactor binary against one clean host, so I cannot rule
out the runner image having crossed the threshold on its own. The coincidence of the dates with
that file is strong and it is not proof. What is certain either way is the property the test
asserts and never establishes.

**Why a host-dependent test is worse than a missing one.** The lifecycle-floor file already found
this exact class in the shell harness and wrote it down — *"the gate's coverage is therefore
inversely proportional to how much the machine is used, and it never noticed"* — and built a
ratchet to fix it. Nobody asked whether the Rust suite had the same defect. It does, in the
mirror image: this test passes **because** the developer's machine is used and fails on a clean
one, so the suite is greenest exactly where it is least trustworthy.

### F14 — the exit table that "cannot drift" has drifted, and its only test is a tautology — *minor, and the best argument in the review for a mutation gate*

`Exit::table()` carries this doc: *"One line for `--help` and the readme, generated from the enum
so the documentation cannot drift from what the binary returns."* Three findings, in the order
they were reached — and the first was reached by `cargo mutants`, not by reading.

**1 — one mutation of the meanings changes nothing.** `cargo mutants --file src/core/exit.rs`,
run twice, and the two runs are a lesson in their own right.

The first run scoped the tests to the eleven whose names contain `exit_code` and reported **4
missed of 7**. That number is wrong and is recorded here because throwing it away quietly would
be the more comfortable choice: `--test suite <filter>` runs the *integration* target only, and
`every_code_is_distinct_and_documented` — the test this finding is about — is a **lib** test, so
the first run excluded the very thing it was measuring. Re-run against `--lib`, three of those
four are caught: `table()` returning `""` or `"xyzzy"` both fail `table.contains(e.meaning())`,
and `meaning()` returning `""` fails `assert!(!e.meaning().is_empty())`.

**One survives, and it is the one that matters:**

```
MISSED  replace Exit::meaning -> &'static str with "xyzzy"
```

Every meaning becomes `"xyzzy"`, the published table becomes `"0 xyzzy\n1 xyzzy\n2 xyzzy\n3
xyzzy"`, and the suite is green. The `Exit::code` mutants are **caught**, which is the control
that makes this a finding rather than a complaint: the codes are genuinely guarded, and only the
prose is not.

**2 — the reason is that its one test compares the function to itself.**
`every_code_is_distinct_and_documented` asserts `table.contains(e.meaning())`. `table()` is
*built by calling* `meaning()`. Replace every meaning with `"xyzzy"` and the table becomes
`"0 xyzzy\n1 xyzzy…"`, which still contains `"xyzzy"`. The assertion cannot fail.

**3 — and nothing consumes the generator, so the hand-written copy drifted.** `Exit::table()` is
called from exactly one place in the tree: `exit.rs`'s own `#[cfg(test)]` module. `shall --help`
prints no exit-code information at all; no readme or `docs/` file carries the generated text. So
the module doc-comment at the top of the same file keeps a hand-typed markdown table, and one of
its four rows no longer says what the binary returns:

```text
doc comment: | 2 | differences found — a read-only command that looked and found work to do |
meaning():        "differences found — something needs you"
```

Eight lines apart, in the file whose premise is that this cannot happen.

**Why the existing gate does not cover it — and this is not the gate's fault.**
`a_pub_fn_nobody_calls_is_dead_tests` catches a `pub fn` nobody calls, and `Exit::table()` passes
it because its own unit test calls it. My first draft of this entry called that a blind spot. It
is not: the gate's header states the bar and argues it, *"zero references, not zero production
callers — a `pub fn` reached only from tests is usually a test double … and policing those would
make this a gate people delete."* That reasoning is correct, and a version of the gate that
flagged every test-only caller would drown in the mock executor's API.

So the accurate claim is narrower and more interesting: nothing covers the *intersection* — a
function whose only caller is a test, **and** whose test cannot fail. Either property alone is
benign. `Exit::table()` has both, which is why a function, its test, and its documentation could
all three be wrong at once with every gate green. It is the same shape as F11 (a setting nothing
reads) and F7 (a test reading a copy): three ways of saying the tree cannot presently tell a
binding from a resemblance — but here it is a gap between two sound rules rather than a hole in
either.

Red test: `tests/the_exit_table_is_generated_not_retyped_tests.rs` (1 red, 1 green control that
the scan finds both copies and that they are the same table rather than two unrelated ones). It
asserts only that the two copies agree — deleting the hand-written table, generating it, or
correcting row 2 each satisfy it. It deliberately does **not** demand that `--help` print the
table, which would be answering a question nobody asked.

### F10 — `@sandbox` does not sandbox, by default, and says so only at `debug` — *blocker*

Ubuntu container, no `bwrap`, stock configuration:

```
$ shall run -p apt:bash@sandbox -- sh -c 'id -u; touch /srv/escaped'
IN-SANDBOX-UID=0
$ ls /srv/escaped
/srv/escaped          # on the host filesystem. rc=0. Nothing on stdout or stderr said so.
```

**Three mechanisms in a row, each of which alone would be enough.**

1. `SandboxSettings::fallback_allowed` defaults to **`true`** (`config/config.rs:34`).
2. `Sandbox::is_available` is `bwrap_available() || settings.fallback_allowed`
   (`sandbox.rs:30`). It does not answer *"is a sandbox available"* — it answers *"is a sandbox
   available, or are we permitted to skip it"*. With the default, it is a constant `true`.
3. `wrap_linux` (`sandbox.rs:185`) then finds no `bwrap`, logs *"Falling back to PATH
   isolation"* at **`debug!`**, and returns `Command::new(cmd).args(args)` — a bare command with
   an unmodified environment. **There is no PATH isolation.** The sentence names a boundary the
   code does not build, which is word for word the bug `hooks.rs:278` records having already
   found once: *"It was called `setup_lua_sandbox`, which claimed a boundary this does not
   build."*

**The one user-visible warning is unreachable.** `run.rs:135` reads `else if
settings.fallback_allowed { warn!("Sandbox requested but unavailable...") }`. Reaching it needs
`can_sandbox == false && fallback_allowed == true`, and step 2 makes that combination impossible.
The `warn!` is dead for every input; the live path logs at `debug!`.

**The mechanism works when it is asked to.** With `fallback_allowed = false` the same run refuses
cleanly:

```
rc=1  Platform or architecture not supported: Sandboxing is required by policy but not
      functional on this host.
```

So this is a default and a predicate, not a missing feature — which is why it is cheap to fix and
why it has survived: every test that sets the policy explicitly passes.

**Compounded by F3.** `@sandbox` written as `@version=1.2.3@sandbox` never reaches this code at
all — it is absorbed into the version string. So there are two independent ways to believe a
command is confined when it is not, and `shall run`'s entire purpose is running something in a
box.

### F11 — the setting that exists to prevent F10 does nothing — *blocker, and F10's sibling*

`SandboxSettings::require_bwrap` is declared, documented — *"On Linux, if true, Shall will fail
if 'bwrap' is missing"* — defaulted and serialised. **Nothing reads it.** `grep -rn require_bwrap
src/` returns two lines, both in `config/config.rs`: the declaration and the default.

Its Windows twin is wired. `windows_require_sandbox` is checked at `sandbox.rs:303` and raises
exactly the refusal its doc promises. The Linux one — governing the platform where `bwrap` is the
only real mechanism — was never connected. That is the asymmetric-sibling shape `CLAUDE.md` names
explicitly: *"the parallel field / the twin adapter"*.

**Why this is not merely a dead field.** `require_bwrap` is the documented remedy for F10. An
administrator who reads the configuration reference, decides silent unconfined execution is
unacceptable on their fleet, and writes `require_bwrap = true` has taken the step the
documentation offers — and gets byte-for-byte the same unconfined run. The knob whose entire
purpose is to close the hole is the one that is not there.

**The whole family, checked:** 76 `pub` fields across the configuration schema, scanned for any
use outside `src/config/`. **Exactly one is dead**, and it is this one. No false positives, so
the instrument is naming a singular case rather than a pattern of noise.

The repository already gates dead `pub fn`s (`a_pub_fn_nobody_calls_is_dead_tests.rs`, 1,110
functions, all reachable). It had no equivalent gate for settings — the same question asked of the
surface a **user** touches rather than the one a caller touches. There is one now.

Red test: `tests/a_setting_the_config_declares_is_a_setting_that_acts_tests.rs` (2 tests, 1 green
control that verifies the scanner can see a wired setting, including F11's own twin).

### F12 — one skipped declaration erases every other kind of drift from `check` — *major*

`check.rs:231` matches `!c.skipped.is_empty()` **before** the arm at `check.rs:288` that prints
the counts. They are alternatives, not a sum, so a machine with one skip and any amount of real
pending work reports the skip and nothing else.

Measured on Windows, from one repository, adding a single line between the two runs:

```
$ shall check                                   # one link: declared, target not on disk
->  drift       0 to install, 0 to remove, 1 to place, 0 to undo

# append `apt` to priority and `apt:tree` to the module — nothing else changes
$ shall check
->  drift       1 package(s) installed and declared nowhere that `sync` will not remove: apt:tree
```

The file is still missing from disk. `sync` would still place it. `check` no longer says so.

**The JSON loses it too, and that is the half that cannot be argued as a wording preference.**
Package work survives the skip arm because `install` and `remove` are attached to `counting` on
both arms. Resources have no key there at all — `r.summary()` inside the summary *string* is the
only place a pending `link:` is ever reported, and the skip arm writes a different string:

```json
{"counts":{"install":0,"remove":0,"skipped":1},"ok":false,"section":"drift",
 "summary":"1 package(s) installed and declared nowhere that `sync` will not remove: apt:tree ..."}
```

There is no reading of that document under which a file is missing from disk.

**Reached by the same `sudo` road as F2**, and measured there: under `secure_path` the drift row
went from `4 to install, 0 to remove, 0 to place, 0 to undo` to three skips and no counts. In that
run one genuinely pending `apt` install was hidden — `counts.install` was `1` in the JSON while
the line a person reads named only the three phantoms.

**Severity, honestly bounded.** The exit code is still 2, so a script gating on `check` is not
misled. `--json` consumers keep package counts. What is lost is the default human surface, and —
for resources — every surface `check` has.

**The family, checked, including what is clean.** Three surfaces print `skipped`:

| surface | behaviour |
|---|---|
| `check` rollup | **collapses** — the skip replaces the counts |
| `plan` | additive — prints `Left in place (1)` *and* `1 resource(s) to place` |
| `sync` | additive — prints the skip list *and* the transaction summary |

So `check` is the only one, and `plan` printing both in the same run is what proves the fact is
computed rather than lost upstream. Also checked and not a counter-example: the detail view
`shall check drift` lists no resources in **either** state, so its silence here is a separate and
smaller gap, not this one.

The JSON half has its own family, and it is also a family of one. Every other rollup row in
`check_summary` attaches `.counting` **outside** its `if`/`match`, so all arms carry the same
keys: `health` keeps `ready`/`degraded`/`critical` even on the arm whose prose names only one of
them, and `security` counts advisories on both arms. `drift` is the only row where the two arms
attach different key sets, and resources are the only quantity in the whole command that lives
solely inside an English sentence.

Red test: `tests/a_skip_does_not_erase_the_rest_of_the_drift_tests.rs` (4 tests, 2 green controls
— one that `check` reports the resource with nothing skipped, one that `plan` still reports it
*with* the skip present, which is what places the loss in the reporting rather than the planner).

### F15 — a group-kill leaves packages installed and owned by nobody — *blocker, and F1 was hiding it*

**This one is not mine.** It is the repository's own `S87` check, in its own container harness,
and it fails on current source. My only contribution was making the harness able to run at all —
which is the finding underneath the finding.

```
FAIL  crash/groupkill: the crash left pv ncdu installed and under nobody's management,
      so the command for removing them will report success and take nothing away
```

**The mechanism, in the harness's own words** (`run-in-container.sh:2063`): the ownership registry
is written *once*, at the end of a run; the write-ahead log is written *per operation*. A kill in
between leaves a package installed and owned by nobody — and nothing downstream notices. `sync`
converges, because the package genuinely is installed. The preview plans nothing, because there is
nothing to plan. The damage surfaces only when somebody tries to remove it, as a cleanup that
reports success and takes nothing away.

**The A/B, because a crash test is exactly where a timing artifact would hide.** Same image, same
harness, same host, and — the part that matters — **both binaries built `debug`**, so the build
profile is controlled for rather than argued about:

| binary | result |
|---|---|
| `3affcc5` — CI's last green main | **425 pass, 0 fail** |
| `HEAD` | 424 pass, **1 fail** |
| `HEAD`, run again | 424 pass, **1 fail** |

Deterministic across both HEAD runs. *Which* canaries land unowned varies with the race — `pv
ncdu` the first time, `ncdu` the second — but the check fails every time, and never on `3affcc5`.
The sibling scenarios `crash/midway` and `crash/completed` pass on both binaries, so it is the
group-kill shape specifically: the one where the signal reaches the manager and Shall together.

**It is a regression, not an unverified check, and it bisects to one commit.** `20aafbe`
(2026-08-04) added the group-kill scenario and `e7eeaaf` (2026-08-11) added this assertion with
the `S87` fix it belongs to — both ancestors of `3affcc5`, whose tools leg then ran **green** on
2026-08-12. Four more binaries built and swept on the same image and harness:

| commit | | result |
|---|---|---|
| `3affcc5` | CI's last green main | 425 pass, **0 fail** |
| `2516c22` | the commit before the suspect | 425 pass, **0 fail** |
| `d1b3618` | *"fix: twelve findings from the release review"* | 424 pass, **1 fail** |
| `cfad22d` | | 424 pass, **1 fail** |
| `HEAD` | ×2 | 424 pass, **1 fail** |

**`d1b3618` is the commit, and it is also the commit that introduced F1.** One change brought in
a blocker and, in the same breath, the compile error that took offline the only instrument that
could see it. The 25 commits before it in the untested window are exonerated by `2516c22`.

That is the sharpest thing in this review, and it is not a coincidence to be enjoyed — it is the
mechanism. A verify chain that runs on one platform cannot report on a defect that only the other
platform's harness detects, and the *same* commit that blinds the chain is free to carry anything
past it.

**And this is what F1 actually costs.** Not "CI is red" — that is the symptom. The container
harness builds the binary in-image, so a tree that does not compile on Linux takes every
fault-injection check offline with it. Fixing F1 is one word (`pub(crate)`; measured: 1 error to
0, no second error behind it, binary builds and runs), and the first thing the restored harness
did was hand back a blocker that its own author had shipped in the same commit.

**It did not reproduce on `fedora`/`dnf`, and the log says why — so this is a boundary, not a
manager-specific bug.** `linix-it-fedora` with the same HEAD binary: **351 pass, 0 fail.** The
difference is one line of the same scenario:

```
tools  (apt): SIGKILL left 3 newly-opened operation(s) … with 1 of 3 canaries on disk   -> FAIL
fedora (dnf): SIGKILL left 3 newly-opened operation(s) … with 3 of 3 canaries on disk   -> PASS
```

The defect needs the kill to land **mid-batch**, leaving some canaries installed and the run dead
before the registry write. On `apt` it lands there every time; on `dnf`, in the one run I have, it
landed after all three were on disk, so the partial state the defect needs never existed. *So the
correct claim is not "apt only" — it is that a single green `dnf` run is not evidence of absence,
because that run did not reach the state under test.* Whether `dnf` can reach it is unmeasured.

Also worth recording, because it is the honest other half: across the two images, **424 of 425 and
351 of 351 checks pass**, 26 backends complete a real install → list → binary → remove, and the
lifecycle ratchet holds at 26 ≥ 26. The harness is good. It was simply switched off.

No test added here: this *is* a test, it already exists, it is well-written, and it is red.

### F16 — `sync --dry-run` does not consult the removal guard; `plan` does — *major*

The rehearsal of a command must answer the same question the command answers. Measured on the
tools image: adopt everything, un-declare N packages the guard protects, then ask each surface.
The **only** variable in the 2×2 is the `--dry-run` flag.

| run | rc | protected packages named | refusal |
|---|---|---|---|
| `sync --dry-run --yes`, 1 package | 0 | 0 | none |
| `sync --yes`, 1 package | **3** | 1 | yes |
| `sync --dry-run --yes`, 13 packages | 0 | 0 | none |
| `sync --yes`, 13 packages | **3** | 10 | yes |

The preview reports `install 0  remove 13`, exit 0, nothing protected. The act refuses, exit 3,
and names ten protected packages. A user reads the first and gets the second.

**`plan` gets it right, which is what makes this a defect rather than a missing feature.** Same
tree, same state, same moment:

| surface | rc | protected named | refusal text |
|---|---|---|---|
| `sync --dry-run` | 0 | **0** | **no** |
| `plan` | 0 | 10 | yes |
| `sync` (real) | 3 | 10 | yes |

The information is computed and available. One of the two previews of the same operation does not
ask for it.

**It contradicts a ruled decision, not merely a principle.** My first draft cited `S25` at
`cli/args.rs:996` — *"**`--dry-run` never exempts anything**"* — which is about lock scope and
was an argument by analogy. The closer authority is **`Q7`, ruled by the owner on 2026-07-28**,
and it names this exact symptom in the defect it was called to fix:

> Deleting a `link:` … made the next `sync` tear that resource down without counting it,
> **without naming it in the plan or the `--dry-run` preview**, and without consulting
> `protected_packages`.

Q7 closed that for **resources**. The same silence is still live for **packages**: the
`--dry-run` preview neither names them nor consults protection. In fairness to the ruling, its
two binding clauses are about `protected_packages` covering resources and the ceiling counting
the whole command — the dry-run preview appears in the description of the bug rather than in the
clauses. So this is the same defect one type over, in a surface the ruling had already noticed.

**Not a regression — it is longstanding.** `3affcc5`, CI's last green main, behaves identically
across all four rows. So this predates the untested window and is not `d1b3618`'s doing.

Severity is bounded honestly: the surprise runs in the safe direction (the preview promises *more*
work than the act performs, never less), so nothing is destroyed. What breaks is the purpose of a
rehearsal — and a pipeline that gates on `shall sync --dry-run` gets exit 0 for an operation that
will exit 3.

### F17 — the guard's OS-essential protection has no test anywhere in the Rust suite — *major, and it is what the mutation gate was for*

`cargo mutants` over `src/app/sync/guard.rs`: **125 mutants, 101 caught by the lib tests, 11
unviable, 13 surviving.** Re-running the survivors against the **full** suite — lib *and*
integration, 2,349 tests, with only this review's own red tests masked out so the baseline is
green — caught all but four. Three of the four are the same function:

```
MISSED  replace essential_names -> HashSet<String> with HashSet::new()
MISSED  replace essential_names -> HashSet<String> with HashSet::from_iter([String::new()])
MISSED  replace essential_names -> HashSet<String> with HashSet::from_iter(["xyzzy".into()])
```

**What that mutant costs, measured rather than asserted.** I built a Linux binary carrying
exactly the surviving mutation and ran it against the clean one, same image, same scenario —
un-declare the five packages the *static* config list does not cover:

| binary | rc | protections by the OS-essential rule | outcome |
|---|---|---|---|
| clean | **3** | 5 — `tar`, `sed`, `grep`, `gzip`, `findutils` | guard refuses |
| `essential_names → {}` | **1** | **0** | guard silent; removal attempted |

Deleting the protection outright is invisible to every Rust test in the tree. The machine survived
only because **apt refuses to remove its own `Essential: yes` packages** — a second line of defence
Shall does not own, does not check for, and cannot assume of every backend.

**Why the suite cannot see it, and this is the structural point.** The Rust suite is hermetic: it
drives mock providers, and no mock reports an essential set, so `essential_names` never returns
anything in any test.

**Nor does the container harness — measured, not assumed.** I ran the mutant binary through the
full `tools` sweep. Result: **424 pass, 1 fail, and the one failure is F15** — the same
group-kill check that fails on the clean binary. Every essential-related check passes on a binary
whose essential protection has been deleted, including `protected includes a system essential`
(`run-in-container.sh:510`), which greps `shall protected` — a command that reports the *static*
config rules and is byte-identical between the two binaries (39 names each).

So the honest conclusion is stronger than "the unit tests miss it": **nothing in this repository
catches it.** Not the 1,814 lib tests, not the 535 integration tests, not the 425-check container
harness. The only thing standing between this mutation and a broken machine is apt's own refusal
to remove `Essential: yes` packages.

**A second, smaller pattern in the same data.** Three of the six survivors are numeric-boundary
mutations — `MAX_LISTED` (`>`→`>=`, cosmetic), `allow_the_count` (`!=`→`==`, gates a `warn!`
only), and `too_many_changes` (`>`→`>=` at `guard.rs:656`, which moves the removal ceiling to
trigger *at* `max_removals` instead of above it). The last is behavioural, and errs safe. Taken
together they say the guard's thresholds are tested for "well over" and "well under" and not at
the limit itself — which is where a ceiling is worth testing.

**The other survivors are mostly not behavioural, and saying so is what makes the first one mean
something.** `guard.rs:365` is `if protected.len() > MAX_LISTED` — flipping it to `>=` appends
*"…and 0 more protected package(s)"* when exactly ten are protected. `guard.rs:508` is
`if before != report.objections.len()`, which gates a `warn!` and nothing else. So the true
reading of 125 mutants is **one serious behavioural hole and one safe-direction off-by-one, not
six** — and the serious one is exactly what the hermetic suite structurally cannot reach.

*Two things I had to throw away getting here, both recorded because the wrong version is the
instructive one.* I first concluded that `essential_names` was inert for apt, on the strength of
`apt_like_core` setting `essential_args: None` — that line is at `generic.rs:2238`, and
`#[cfg(test)]` begins at `2210`, so it is a **test fixture**, not production. The container then
showed the real thing working: *"apt reports it as essential to the system"*, five times. I also
briefly had a list of thirteen "unprotected" essentials, which was the `MAX_LISTED = 10` display
cap truncating the protected list — the very constant named above. Both wrong readings ran in
Shall's disfavour, and both died on a container run rather than on reflection.

**The positive half, and it is the larger half.** 101 of 125 mutants killed by unit tests alone,
and every remaining one except this function's caught by the integration suite. `Reaped::scope`,
`Reaped::for_reason` and `protection_of` are *unviable* — the compiler rejects the mutation
because `Reaped` has no `Default`, which is the token doing precisely the job its doc claims. This
is a well-tested file with one hole in it, and the hole is exactly where the hermetic suite ends.

## 2. Three questions, not answered in code

Per `CLAUDE.md`, these change behaviour a user would notice and touch a ruled decision, so they
are the owner's. None is fixed and none has a test pinning an answer.

**Q-A — should a read-only command that finds work exit 2?** `target-state.md:1443` says exit 2
*"means a read-only command found work to do"*. Only `check` builds `Error::Differences`.
Measured: `shall plan` prints *"1 install(s), 0 removal(s)"* and exits **0**; `shall list
--outdated` lists dozens of outdated packages and exits **0**.

*Recommendation: yes for `plan`, no for `list --outdated`.* `plan` answers the same question
`check` does and writes the machine-readable artifact a script consumes, so a script that branches
on drift will reach for it and always be told "converged". `list` is a listing — its subject is
inventory, not verdict, and a listing that exits non-zero for having contents would be surprising.
U21 settled the table before the commands existed; this is the first command it did not cover.

**Q-B — `outdated`: remove the name, or add the subcommand?** F7 makes the arm dead either way.
Removing the string is a one-word change; promoting `list --outdated` to a subcommand is a
user-visible addition. *Recommendation: remove the string, and fix the guard to read the table
rather than a copy of it — the copy is the actual defect and it will produce this again.*

**Q-C — is a declaration Shall could not act on a failure, or a declaration that does not apply
here?** This is F13, and it is a genuine chiluk rather than a bug with an obvious fix. If `cargo`
being absent means *this line is not for this machine* — the way a `when os == linux` block is
not — then exit 0 is right and only the wording is wrong. If it means *Shall was told to use
`cargo` and could not*, then the run did not converge and 0 is a false report.

*Recommendation: the second, and the spec has already ruled the underlying distinction.*
`target-state.md` §Q2 defines **critical** as *"it is installed, **or `priority` names it**, and
it cannot work"* — so a `priority`-named manager that cannot be reached is already, by rule, a
failure of the machine rather than an inapplicable declaration. `sync` is the one command that
has not been told. Note this is the same ruling that decides F2, which is why the two findings
keep arriving through the same door.

*What the ruling has to cover, whichever way it goes:* a partial skip as well as a total one —
the container run skipped three of three, but three of four is the ordinary case and is worse,
because something did get installed and the summary looks like a successful transaction.

## 3b. What I attacked and could not break

Reported because a review that lists only what failed reads as though everything was tried and
everything broke. These were each driven end to end, most in containers, and they held.

- **The removal guard.** `sync -y` over `max_removals` refuses with exit 3 and every package
  intact; `--allow-mass-removal` carries it out; `--dry-run` performs nothing. All nine refusals
  are live, including the three whose `policy.toml` rules are otherwise unreferenced.
- **`--keep-going` no longer flips a total failure to 0.** The previous round's B1 is closed.
  Re-measured across the flag matrix, not just the default path.
- **The `@sha256` verification path** fails, and fails for the stated reason rather than by
  accident.
- **`adopt` → `check` → `sync` converges to zero changes** on a real machine: 133 declarations
  across 22 managers, 490 rows over 17 managers with no junk rows, and a second `check` that
  finds nothing to do.
- **The exit-code matrix** is correct for install failure, usage error, refusal and difference —
  once the fixture stops leaking `max_removals` between cases (see §5, lesson 4).
- **`U31`'s `@health=` hook ledger** is built and enforced by a sync preflight. `GRADER.md` says
  otherwise and `GRADER.md` is stale.
- **The `luarocks` parser and the `choco` count-row defect** — both previously reported, both
  correct now.
- **`shall sync` does not silently skip a declaration whose manager is missing.** It warns by
  name, once per declaration. F4 is about the *sentence* it then prints and F13 about the *exit
  code* it then returns — neither is about a silent skip. A person watching the terminal is told.
- **`export` does not clobber.** It steps to `package.shall.json`, then `.2`, `.3`. The one thing
  it is most likely to be run next to is a real `package.json`, and it leaves it alone.
- **A `SIGKILL` mid-sync, twice, and it recovered both times.** This is the one I most expected to
  break, and it is the best thing in the review. Ubuntu container, four `apt:` declarations:

  | kill point | dpkg state after | Shall's read | next `sync` |
  |---|---|---|---|
  | during planning | clean, nothing installed | `-> drift 3 to install` — accurate | `WARN the transaction journal records an interrupted run; healing first`, installs all three, rc=0 |
  | with `apt-get`/`dpkg` live | `dpkg --audit` clean | `-> drift 4 to install` — accurate | same warning, installs all four, rc=0 |

  Both runs left `shall.lock` and `exec-locks/apt.lock` behind and **neither wedged the next run**
  on them. `check` afterwards: *"the machine matches your files."* No phantom state, no
  double-install, no silent skip. The window I could not reliably hit is between `dpkg`'s unpack
  and configure phases, which is where `dpkg` itself gets wedged and would need
  `dpkg --configure -a` — that slice remains untested by anyone (see §3).
- **Two `shall sync` runs launched at the same moment against one data directory.** The second
  printed `shall: waiting for the data directory — held by shall sync (pid 32)`, waited, re-planned
  once the first finished, and reported `already up to date`. Both exited 0, all five packages
  installed once, `dpkg --audit` clean, and a third `sync` afterwards still worked. The lock is an
  OS `flock` on an open handle with a bounded wait and a message that names the holder — and
  `datalock.rs:73` records that the old advice, *"remove `shall.lock` if nothing is running"*, was
  deleted precisely because a still-contended lock **proves** a live holder rather than a corpse.
  That is the correct reasoning, written down.
- **Which commands take that lock.** Read as a whole rather than spot-checked, because
  `CLAUDE.md` says a guard on one command is a guard on nothing. `Commands::lock_scope` is an
  exhaustive match over every subcommand returning `Writer`, `Reader` or `Deferred`, so a new
  subcommand does not compile until it answers — strictly better than a default, and better than
  the hand-written list of twenty-one names it replaced, twelve of whose entries had rotted into
  naming commands the program does not have. I went looking for a `Reader` that writes and did not
  find one: the sharpest candidate, `repl`, delegates every line to the resolver and prints, and
  the three `Deferred` entries (`watch`, `shell`, `run`, plus `history`) are unbounded-in-time
  commands that take the lock at the write instead of around the wait, which is the right call and
  is argued for each of them in place.
- **A package left unpacked-but-not-configured is not called installed.** `dpkg --unpack` without
  `--configure` leaves `rolldice` in `iU`; `shall list --installed` does not carry it, `plan` says
  `1 install(s)`, `check` says drift and exits 2. The lazy read — "dpkg knows the name, call it
  present" — would have said converged.
- **A batched removal of five packages removed all five.** One `apt` command, five `✓` rows,
  `Status: SUCCESS`. I spent a while convinced one had survived; see lesson 14.
- **The backend sweep, run for the first time since `3affcc5`, is 424 of 425.** On the `tools`
  image with a binary built from current source: **26 backends through a real install → list →
  binary-on-PATH → remove**, the lifecycle ratchet held at 26 ≥ 26, every registered backend got
  a lifecycle or a plan-smoke, and 57 of 61 subcommands were *executed* rather than `--help`'d.
  `fedora`/`dnf` on the same binary: 351 of 351. The single failure is F15. This harness is the
  best thing in the repository and it is the thing that was switched off.
- **The removal guard survives mutation.** 125 mutants over `guard.rs`: 101 killed by unit tests
  alone, 11 rejected by the compiler, and of the 13 survivors the integration suite killed all
  but four — of which two are a display cap and a log line. `Reaped::scope`, `Reaped::for_reason`
  and `protection_of` are *unviable*: the mutation does not compile, because `Reaped` has no
  `Default` and cannot be conjured. That is the token enforcing at compile time exactly what its
  doc claims, demonstrated rather than asserted, and it is the strongest single result in this
  review in the program's favour.
- **`shall protected` is unchanged by deleting the essential query.** Both the clean and the
  mutated binary list the same 39 names, because that command reports the *static* config rules.
  Recorded as a negative because it is the check the container harness uses
  (`run-in-container.sh:510`), which is why the harness does not catch F17 either.

- **`shall run` refuses correctly when told to.** With `fallback_allowed = false` the same
  invocation that silently runs unconfined under the default (F10) fails with *"Sandboxing is
  required by policy but not functional on this host"* and exit 1. The mechanism is sound; the
  default and the predicate in front of it are the defect.
- **Windows suite: 0 pre-existing failures, across every run of this review.** 542 tests passing
  before this round's tests were added, 544 with the first two of them in; clippy and `fmt` clean
  throughout. Nothing here broke anything that was working.

## 5. The grades, and what moves each one

Each axis carries **both** deltas, because they are different questions and the second is the one
that gets skipped: what moves it *one letter*, and the full list of what is standing between it
and an **A+**. Nothing here is graded against a curve — the bar is the program this spec
describes, working.

---

**1 · Bugs — D−, marked down.** Nine independent "Shall reports fine when it could not tell"
bugs — F2, F3, F4, F10, F11, F12, F13, F15, F16 — plus no Unix build (F1). I had this at D+
before auditing the sandbox path and held it at D through F12 and F13, on the reasoning that
they were further instances of one kind rather than new kinds. **F15 is what moves it, and it
moves it for a reason that is not about counting.**

Every finding up to F13 was Shall *saying* something untrue about a machine it had not surveyed.
F15 is Shall *leaving* a machine in a state it cannot describe: a group-kill puts packages on
disk owned by nobody, and the removal command for them reports success and takes nothing away.
That is the same sentence one layer down — not a report that is wrong, but a **state** that
makes every future report wrong — and it is the failure mode a declarative machine-state manager
exists to make impossible. It is also, unlike the others, a regression: `2516c22` does not have
it and `d1b3618` does.

F16 is filed here rather than under Verification because it is a user-facing disagreement, not a
gap in a gate: the rehearsal of a command reports different work from the command.

*Up one letter:* F1 and F2 fixed, and F2's fix placed in `probe_all_health` where the two views
already meet rather than in the rollup — a second copy of the promotion is how this came back the
first time.

*What stands between this and A+:* all nine, and specifically **the whole family rather than the
nine instances.** Every one is the same shape — an operation that could not do its job returning
the same answer as one that did it and found nothing. The A+ version of this axis is not "these
bugs are gone"; it is that a *reader that could not read*, a *survey that surveyed nothing*, a
*confinement that did not confine* and a *convergence that converged nothing* are each unable to
produce a success value at the type level. `Reaped` is the existing proof that this repo can
express that — and this round *measured* it: three mutations of `Reaped` are rejected by the
compiler rather than by a test. Until the rest of the family is closed the same way, the next
refactor produces instance ten and the grade returns here.

F15 adds the condition the others do not: **a write and its ownership record are one fact and
must be one write.** The registry is written once at the end of a run and the log per operation,
so the window between them is a state no report can describe. Making that impossible is a
transaction boundary, not a test.

F12 also adds a second, narrower A+ condition on this axis, because it is not quite the same
shape as the rest: **one report, one fact.** The drift row is a single string that four different
questions take turns owning, so answering one of them silently unanswers the others. A summary
built by *appending* what is true, rather than by a `match` that elects a winner, cannot lose a
fact by adding one — and `counts` needs a key for every quantity the prose mentions, since a
number that exists only inside an English sentence is not machine-readable no matter what the
document is encoded as.

- **F15.** Patching F1's one word and running the container harness produced a **blocker on the

"verified on Windows" and nothing in the chain says so. **(b) The interrupted-run tests assert recovery from a

logic is measured and the **premise** is not: nothing in the suite checks that a process killed

held, twice** (§3b) — which is the good news, and also the point, because that evidence exists
only in this document — though the container harness *does* have the kill in the loop
(`crash/midway`, `crash/completed`, `crash/groupkill`), which is how F15 was found, so the gap is
that the Rust suite cannot see what the harness sees and the harness was off. **(c) Nothing
measured the tests themselves, and now something has.** `GRADER.md` demands "a test you did not
watch fail is not a test", and the only mutation gate in the tree is the `Harness mutation` CI
job, which covers the *shell* harness rather than the Rust suite. This round ran `cargo mutants`
over the guard for the first time: **125 mutants, 101 killed by unit tests, 11 unviable, and of
the 13 survivors the integration suite killed all but four.** That is a good score and it found a
real hole (F17). It also cost ~90 minutes for one file of 125 mutants, so the honest
recommendation is not "mutate everything" but **a gate over the handful of files where a silent
mutation is a safety failure** — `guard.rs`, `exit.rs`, `datalock.rs`, `transaction.rs` — run on
a schedule rather than per change.

**(d) The hermetic suite has a hard ceiling, and nothing states where it is.** `F17`'s hole is
not an oversight in a test; it is a class the suite *cannot* cover, because mock providers never
report an essential set. Every guard behaviour that depends on a real manager's answer is in that
class. An A+ here needs the boundary written down — which behaviours only the container harness
can verify — so that harness being red is understood as those behaviours being unverified,
rather than as one more job to re-run later.

An A+ on this axis is a chain where a change cannot be called verified on the strength of a
platform, a copy, a claim, or a mock.

## 5b. Lessons — mostly about the instrument, and most of them mine

A finding is only as good as the thing that measured it. Every one of these cost me a wrong
answer first, and each is written as a rule because the next reviewer will otherwise pay for it
again.

**1 · A wall clock in a busy room measures the room.** First pass: `list` 47.8 s, `check health`
78.4 s — alarming, and taken while four containers compiled Rust. Fastest-of-three on a quiet box:
3.2 s and 3.4 s, matching the file's own recorded figures. I nearly reported a regression that did
not exist. The suite already learned this once — `latency_budget_tests` takes the fastest of three
for exactly this reason — and I did not apply it to my own measurement until it burned me. *Rule:
a timing that would become a finding gets re-taken on an idle machine before it is written down.*

**2 · `rc=$?` after a pipe reads the pipe.** Cost me a false "install failure exits 0" — twice, in
the same session. Re-measured without the pipe, the program was correct both times. *Rule: capture
the exit code before anything touches the output; `PIPESTATUS` or nothing.*

*Postscript, and it is the reason this list exists.* I did it a **third** time, after writing the
rule down: `cargo test --no-fail-fast 2>&1 | tail -60`, whose reported exit code was `tail`'s `0`
over a run with eighteen failures in it. Harmless here, because the failures were the deliverable
and I read the output file anyway. Not harmless in general, and the specific lesson is sharper
than the rule: **knowing a trap is not the same as having a habit that avoids it.** A rule in a
document is a comment; the fix is `${PIPESTATUS[0]}` typed by reflex, which is the same argument
this whole review makes about `Reaped` versus a doc comment, turned on the reviewer.

**3 · Do not reason about a CLI's behaviour when you can run it.** I tried to reproduce the
fan-out latency synthetically — 120 fake `cargo:` lines — and got ~160 ms, which "proved" there
was nothing there. The tool's own `--timings` then handed me the mechanism in one run: 1.0×
overlap, 21 waves over 21 children. *Rule: use the program's own instrument before building one.*

**4 · Build the fixture fresh per case, or you are measuring the last case.** The exit-code matrix
came out wrong because `max_removals=2` was still set from an earlier case, so cases 3–5 measured
a guard refusal (3) rather than an install failure (1). A `fresh()` per case fixed it. *Rule:
state that survives a case is a confound, whether or not you put it there.*

**5 · A screening instrument that over-reports gets deleted, and then the real findings come
back.** The first draft of the citation checker required *every* symbol a comment names to be near
the cited line: 53 failures where hand-checking found 15. Tightened to "at least one named symbol
within ±4 lines": 19, all real. *Rule: pick the weakest rule that still catches every instance you
found by hand.*

**6 · Read the whole output before calling it a bug.** I had `check` exiting 2 on a converged
machine written up as a finding. The full output showed the `security` row at `->` with 183
advisories — the 2 was honest and the finding was withdrawn. *Rule: a surprising exit code is a
question about the output, not a conclusion.*

**7 · Do not edit code that a suite is currently running.** Two costs in one session: a
`LNK1104: cannot open file` when a second `cargo test` fought the first for the test binary, and
twenty minutes spent hunting a `package.json` in the repository root that a *still-running* suite
had written with the pre-fix binary — a bug I had already fixed. *Rule: one build at a time, and
when a fix lands mid-run, the run's artifacts are evidence about the old code.*

**8 · A test that spawns the binary must set `current_dir`.** `shall export` writes into the
working directory, and a child inherits the runner's. Mine left five files in the repository root.
The suite's own `dry_run_every_verb_tests` has a comment on exactly this line, which I did not
read until after I had reproduced the bug it describes. *Rule: read the neighbouring test's
comments before writing the new one.*

**9 · Check state at the right moment, or manufacture a finding.** `GRADER.md` §7 says this and it
is the most frequently violated line in the file — by the suite (F9 asserts a refusal that depends
on the host's package inventory) and by me (lessons 1 and 4 are both this).

**10 · When a finding names a mechanism, go straight to the mechanism's siblings — the bug is
usually already there.** F10 is a behaviour I measured. F11 came from a different move: not
"what else is broken" but *"what is the knob that should have prevented this, and is it wired?"*
It was not, and its Windows twin was — an asymmetry nothing in the tree could see, because the
suite gates dead `pub fn`s and had no gate for dead settings. `CLAUDE.md` states this rule (*"the
parallel field / the twin adapter"*) and it is worth restating as a search strategy rather than a
fix policy: **the twin of a confirmed bug is the cheapest place to look for the next one.**
*Corollary, and this one is lesson 5 applied correctly for once:* I prototyped the config-key scan
in one throwaway command before writing it as a test. 76 fields, one hit, no noise — so the test
was worth writing. Had it come back with thirty, the right move was to narrow it or drop it, not
to file thirty findings.

**11 · The structural lesson, and it is the review's finding as much as any bug: an instrument
that reads a *transcription* of its subject reports on the transcription.** Four in this tree —
a test reading a hand-typed copy of the class table (F7), a verify chain compiling one platform
of two (F1), a probe wired to one image of six (F8), a test asserting an unstated property of the
host (F9). And a fifth kind, which is the one worth carrying away: **a rule written as a comment
beside the code it governs is a transcription too.** `Skipped`'s doc describes F4's failure mode
and cites the last time it happened. `check.rs:365` describes F2 and cites the last time it
happened. `probe_all_health`'s doc asserts the property F2 breaks. `Class::of`'s doc asserts the
property F7 breaks. The swallow refusal in F3 names the exact bug it fails to catch. And
`hooks.rs:278` records having already caught F10's exact shape once — *"It was called
`setup_lua_sandbox`, which claimed a boundary this does not build"* — while `sandbox.rs:187`
logs *"Falling back to PATH isolation"* over a bare, unmodified command. **Six findings, six
comments that already knew.** The analysis was done and written down and it decayed
at the first refactor that moved lines, because prose does not fail a build. `Reaped` is the
counter-example this repo already owns: it makes consulting the guard a compile-time requirement,
and it is the one mechanism here I could not find a way around.

**12 · A grep tells you a line exists, not that it runs.** Chasing F17 I made three wrong readings
in a row, each of which would have been a published finding, and each died on a container run
rather than on more reading:

1. *"`sync --dry-run` plans to remove thirteen `Essential: yes` packages and the guard never
   fires."* — I had grepped the output for `"refusing this removal"`. The guard does not refuse
   protected packages, it **skips** them: `Left in place (1) … (protected by config rule bash)`.
   Wrong oracle.
2. *"`essential_names` is inert for apt, because `apt_like_core` sets `essential_args: None`."* —
   that line is `generic.rs:2238` and `#[cfg(test)]` opens at `2210`. I had read a **test
   fixture** as production configuration. The container said otherwise in one run: *"apt reports
   it as essential to the system"*, five times.
3. *"Thirteen essentials are unprotected."* — the protected list is truncated at
   `MAX_LISTED = 10`. My "unprotected" set was the display cap.

*Rule: when a claim is "this code does not run", the evidence is a run — a binary built with the
line changed, executed against the real thing — never a grep, a line number, or a `None` in a
literal.* The variant I would tell a reviewer: **a `cfg(test)` block is production code to
`grep` and to nobody else**, so check where the line falls before you build a finding on it.

**13 · A mutation score is a statement about the test command you gave it, and nothing else.**
The sharpest instrument failure of the review, because it produced a *finding-shaped* result
rather than an obvious error. `cargo mutants --file src/app/sync/guard.rs -- --test suite guard`
reported, in its first eleven mutants, **eight missed and zero caught** — including
`GuardScope::reconciles` replaced with `true` and, separately, with `false`. That function decides
whether a failed transaction gives a removed package back, and its own doc says inheriting `true`
means *"a failed run may leave your software deleted"*. A load-bearing safety predicate, mutable
in both directions, undetected. I had the paragraph forming.

`--test suite <filter>` runs the **integration** target only. `reconciles` is asserted for all
twelve scopes, in both directions, by a **lib** test in `src/core/transaction.rs:1880`. My run
excluded the target that held the coverage, so the score was a measurement of my own command
line. The same error had already run once on `exit.rs` and inflated that finding from one missed
mutant to four (F14 records both numbers rather than the flattering one).

*Rule: before reporting a surviving mutant, `grep` for the symbol in the tests and confirm the
test command you used would have run what you find.* And the general form, which is this review's
own thesis pointed back at the reviewer: **a mutation score is exactly as trustworthy as the
claim that its test command represents the suite** — one more instrument reading a transcription
of its subject, and I built it myself, four days of findings into arguing that this is the
tree's central defect.

**14 · `dpkg -s` succeeds for a package that is not installed, and it cost me a near-miss
blocker.** After a batched removal I read five packages back with `dpkg -s` and one — `figlet` —
still answered `0`, against a `sync` that had printed `✓ [apt] figlet` and `Status: SUCCESS`. That
is a removal reported as done and not done: a blocker, and a clean reproduction, and I had the
write-up half drafted. Self-testing the instrument first killed it. `apt remove` (as against
`purge`) leaves a package with conffiles in state `rc` — *removed, config files remain* — and
`dpkg -s` prints a record and exits 0 for `rc` exactly as it does for `ii`. `dpkg -l` says `rc`,
and `/usr/bin/figlet` was gone. Shall was right; my reader was wrong. **This is the same bug
`CLAIMS`-checking `command -v` was, in a different dialect** — `CLAUDE.md` opens its family rule
with that very story, and I walked into the sibling it warns about. *Rule: to assert a package is
gone, test the file, or read the state column — never the exit code of a query that has more than
two answers.*

**15 · A missing binary is a PATH question before it is a bug.** In the same run I recorded
"`rolldice` does not run" after `sync` claimed success. `/usr/games` is not on root's `PATH` in
that image; the file was there the whole time, in both the unpacked and configured states. Two
instrument failures in one script, both in the direction of a false accusation. *Rule: `[ -f path ]`,
not a bare invocation, and certainly not `command -v`.*

**16 · `sudo` resets the environment, which will confound an A/B you meant to be about `PATH`.**
My first F2-under-`sudo` run compared a repository at `SHALL_CONFIG_DIR` against one at
`/root/.config/shall`, because `env_reset` dropped the variable — so run B reported a *missing
config*, not a missing manager, and for a few minutes that looked like the finding. Re-run as
`sudo -n env SHALL_CONFIG_DIR=… shall check`, so `PATH` was the only difference, and the real
result came out. *Rule: when the experiment is one variable, prove the other variables survived
the boundary before reading the result.* (Worth saying plainly: three of this round's four new
measurements were wrong on the first attempt, and all three were wrong in Shall's disfavour. A
grader who does not self-test files fiction.)

## 6. One page, no colour words

This program is careful in a way most are not. Nearly every finding above was **predicted by a
comment already in the tree** — `Skipped`'s doc describes F4's failure mode and cites the last
time it happened; `check.rs:365` describes F2 and cites the last time it happened;
`probe_all_health`'s doc asserts the property F2 breaks; `Class::of`'s doc asserts the property
F7 breaks; the swallow refusal in F3 names the exact bug it fails to catch. The analysis was done.
It was written down. It was not turned into a mechanism, and so it decayed at the first refactor
that moved lines.

That is the through-line and it is worth more than the individual bugs. The failures here are not
failures of understanding. They are failures of **binding** — a rule stated in prose next to the
code it governs, where a rule stated as a type or a test would have held. `Reaped` is the proof
that this repo knows how to do the other thing: it makes consulting the guard a compile-time
requirement, and it is the one mechanism in this review I could not find a way around.

The four instruments in axis 6 have the same defect as the four comments: each watches a
transcription of its subject rather than its subject. A test that reads a copy of a table, a gate
that compiles one platform out of two, a probe wired to one image, an assertion about a host
nobody stated. None is expensive to fix, and until they are, the tree's own evidence about itself
is weaker than it appears.

**Not releasable.** Not because the bugs are numerous — six commits ago this tree was in far worse
shape — but because several of them are the specific failure this program's entire premise is a
promise against: a machine that does not match its manifest, and a Shall that says it does.

**The last thing found is the one to sit with, and it is not a bug.** `d1b3618` shipped a private
constant and a group-kill regression together. The constant took every Unix build offline; the
container harness builds its binary in-image, so it went with them; and that harness is the only
instrument in the repository that can see the regression — the Rust suite is hermetic and
structurally cannot. One commit therefore introduced a blocker *and* disabled the only thing that
would have reported it, and both went unnoticed for 26 commits because the verify chain in
`CLAUDE.md` runs on the one platform where neither is visible.

That is not carelessness; every individual decision behind it is defensible. A hermetic suite is
right. A container harness for the rest is right. Running the fast chain locally is right. The
failure is that nothing anywhere states **which behaviours only the harness can verify**, so a red
harness reads as a job to re-run rather than as a list of properties currently unverified. F17 is
the same gap measured from the other side: the guard's OS-essential protection can be deleted and
2,349 Rust tests, plus 425 harness checks, all stay green.

Fixing F1 is one word. What it buys back is the ability to find out.

## F15 — fixed, and the bisect pointed at the right commit for the wrong reason

**Verified in the container, on both sides.** Same image, same harness, same host:

| binary | result |
|---|---|
| before the fix | **354 pass, 2 fail** — `crash/groupkill: the crash left ncdu installed and under nobody's management` |
| after the fix | **356 pass, 0 fail** — `crash/groupkill: every canary the crash left on the machine is under Shall management` |

**What the bisect got right.** `d1b3618` is the commit. What it changed was also *correct*:
`dpkg-query -W` has no status filter, so the lister was taught to ask for `${db:Status-Status}`
and to read `unpacked`, `half-installed` and `half-configured` as **not installed** — which they
are. It did not introduce the hole; it exposed one that had always been there.

**The mechanism, and my first two readings of it were wrong.** I said `heal` never runs: it does.
I then said `reconcile_ownership` would claim these once it could see them, and wrote
`Journal::completed_installs` for the window between the per-operation log and the once-per-run
registry write. That window is real and the method stays — but it is not this. The harness says
`SIGKILL left 3 newly-opened operation(s)`: the entries were **open**, not completed, so
`completed_installs` could not see them either.

What actually happens is three things in a row, and only the last is a defect:

1. The group-kill lands mid-`apt`, which wedges dpkg — every later `apt` invocation refuses until
   `dpkg --configure -a` runs. Shall detects this and names the repair, which the harness checks
   and which passed all along.
2. So `heal`'s replay of the interrupted installs **fails**, correctly, and says so in its exit
   code — also already checked, also passing.
3. And the failure branch ended with *"the entry stays recorded as interrupted, so nothing claims
   this package is installed."* **That sentence is the bug.** The kill can leave a package
   unpacked — on disk, on `PATH`, runnable — so the package *is* on the machine and the registry
   claims nothing. `sync` converges, because it genuinely is installed. The preview plans
   nothing, because there is nothing to plan. `uninstall` reports success and takes nothing away,
   for ever.

**The fix is that an install Shall started is Shall's to own, whether or not recovery finishes
it.** The durable log saying *"I began installing this"* is the evidence; ownership is not a
claim that the package is installed but a claim that **Shall is answerable for whatever the
operation left behind**. Taking it costs nothing when the install truly did nothing — the line is
still declared, so the next sync installs it rather than removing it. Not taking it costs
software nobody can remove.

**And its sibling, which would have made the fix inert.** The registry write at the end of `heal`
was gated on `!recovered.is_empty() || !kept.is_empty()`. The group-kill run is exactly the run
where *every* replay fails, so it changes the registry and nothing else — and would have written
nothing. `failed` is in that condition now.

**Covered in the hermetic suite as far as it can be**, which is the boundary `CLAUDE.md` now
states: `Journal::completed_installs` has a unit test with a control asserting that
`interrupted_actions` cannot see the entry it returns — the whole reason the method had to exist.
The end-to-end behaviour is the harness's, because reaching this state needs a real manager and a
real kill.

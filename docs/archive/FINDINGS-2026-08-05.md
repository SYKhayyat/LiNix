# Findings — 2026-08-05: the Windows stall, and everything found chasing it

**What this is.** Every finding from one session. Nothing is left as "unknown" and nothing is
deferred out of the document — where something looked unexplained it was chased until it was
explained, and the chase is written down with the measurement that ended it.

**Result.** The stall was never one bug. Three different things produce the same picture — an
idle `linix`, a frozen log, and a run that resumes the moment it is killed — and all three are
now named and measured. The sweep they were blocking **ran to completion unattended for the
first time**: `pass=234 fail=13 soft=23`.

---

## 0. Method, which is the finding that matters most

Four earlier chances to see a wedged sweep were spent killing the process. Three explanations
were written and later refused by measurement. This session proposed a fourth and it was **also
wrong** — and the only reason that is known is that the capture was armed *before* the run
instead of written up afterwards.

`scripts/stall-snapshot.ps1` photographs and never kills: the process table, the descendant tree
of every `linix`, CPU measured across a window so "idle" is a number rather than an impression,
and each thread's wait reason. `scripts/integration-windows.sh` arms it, and a stall now lands
in the run summary instead of vanishing with the process.

It was self-tested against a wedge whose cause was already known before it was trusted with one
whose cause was not. **It then immediately refuted the person who built it.**

The two-sample CPU window is what earns its keep: a single frame cannot tell a slow command from
a stuck one, and two of the three captures below would have been misread without it.

## 1a. THE PRODUCT GAP — scoop, winget and choco run with no exit policy at all

**This is the most important finding in this document, and it is a bug rather than a question:
the correct behaviour is already ruled.**

`with_manager_policy(core)` attaches a manager's `ExitPolicy` to the executor that runs its
commands. `register_generic` applies it — *"so no registrar can forget it"*, says its own comment
— but that only covers backends routed through it. **Sixteen registrars call `reg.register`
directly and never attach it at all:**

```
apk  apt  aur_helper  bun  choco  dotnet  gem  macports  mas  pip
pkg_add_openbsd  pkg_freebsd  pkgin  scoop  winget  zypper
```

That is not a Windows problem. `apt` is on that list.

The three Windows ones are simply where the measurements are:

```rust
fn register_scoop(...)  { let core = Arc::new(GenericBackendCore { executor: executor.duplicate(), ... });
                          reg.register(Arc::new(BackendCapabilities::builder(core.clone()) ... )) }
// register_winget and register_choco are the same shape.
```

So on Windows the three principal package managers run with `ExitPolicy::default()`: **no
`failure_markers`, no `permanent_markers`, no `absent_markers`.**

**Measured in isolation, deterministically:**

```
linix -y install scoop:linix-no-such-pkg-zzz
  rc=1
  linix-failure-class: unknown
  Error: `scoop` failed (exit 1): Couldn't find manifest for 'linix-no-such-pkg-zzz'.
  -> still declared in modules/imperative.txt
```

`"find manifest for"` is in scoop's `absent_markers` **and** its `failure_markers`. The policy is
correct; it is simply not attached.

### What that one missing line causes

1. The failure is `unknown`, so **Q1's ruling never fires** — Q1 (2026-07-27) withdraws the line
   when the backend's ExitPolicy calls the failure permanent. The dead declaration stays.
2. The leftover then fails **every later install of anything** (§5) — ten of the run's thirteen
   failures, plus `rollback`, `activate`, and the real-lifecycle ratchet collapsing to 1 of 5.
   The harness comment at `integration-windows.sh:674` predicted exactly this.
3. `heal` retries it 23 times per run (§4).
4. **The worst one, and not yet observed only because nothing exercised it:** scoop's policy
   exists because *"scoop exits 0 on every outcome, so its output is the only evidence there
   is"* (`exit_policy.rs:349`). Without the policy, `reads_output()` is false — so **a scoop
   command that fails while exiting 0 is read as success.** That is Q28's class on the default
   Windows backend.

### The guard test cannot fail

`a_generic_backend_carries_its_managers_exit_policy` exists for precisely this, and its doc says
*"Every manager the exit-policy table knows carries its policy into the registry"* and *"the next
conversion fails here first."* It does neither:

```rust
assert!(with_manager_policy(core).executor.classifies_absent_names(), ...)
```

It builds its own core and **applies the helper inside the assertion**. It proves
`with_manager_policy` works; it never asks whether any registrar calls it. `scoop`, `winget` and
`choco` are all in its `argv_cases()` filter, so they are nominally covered and still invisible.

This is the defect class this repo keeps rediscovering — a check that cannot fail, guarding the
exact thing that then broke — and it is why a real product gap survived on the platform's three
main backends.

### The fix

Route the three hand-written registrars through `with_manager_policy`, and rewrite the test to
assert against the **built registry** rather than against a core it constructed itself. No ruling
needed: Q1 already ruled the behaviour, and this is code that fails to implement it.

## 2. `Q32` — the bound covers the wait, not the read

`wait_watched` bounds `child.wait()`, the child's *exit*. The read of its output is outside it:

```rust
let status = match idle { ... };     // bounded; kills on silence
stdout: joined(out_task.await)?,     // no clock of any kind
```

`out_task.abort()` lives only in the timeout branch, unreachable once `child.wait()` has
returned. A manager that hands stdout to a background process and exits leaves LiNix reading
toward an EOF that never arrives — bounded by nothing, because there is no child left to kill.

**Reproduced deterministically.** Fake manager that detaches, bound set to 20s, orphan holding
stdout 60s:

```
ARM C rc=0 elapsed=64s
  [scoop] fakepkg   (60771ms)
```

64s against a 20s bound — **and it exited 0 and called the install a success.** That second half
is a separable defect and by Q28 a defect class of its own.

## 3. `Q37` — 180 seconds downloading a file it was always going to reject

The `heal` capture had no orphan and no child, so Q32 does not explain it. Timestamping every
output line found two gaps, both ending on the same message:

```
 60.9s gap  ->  could not recover github:sharkdp/fd — refusing to deploy `fd.exe`:
119.1s gap  ->      C:\Users\Administrator\.local\bin\fd.exe already exists and LiNix did not create it.
```

`deploy_executable` takes an **already-downloaded, already-extracted** `src`, and its refusal
reads only the *destination*. The check needs zero downloaded bytes and runs after the download.

**180 of that `heal`'s 201 seconds were spent fetching an artifact it would refuse.** Silent
throughout, zero CPU, no child — an in-process `reqwest` download, which is exactly why it looks
like a wedge. Downloads correctly have no whole-request timeout (`core/http.rs`), which makes an
*avoidable* download both unbounded and invisible.

## 4. `Q33` — `heal` is doomed and serial

`get_incomplete_actions()` returns `InProgress | Failed | Abandoned`, and every failed install
writes a **new** operation rather than resolving the old one. In one sweep's journal: **22
separate operations for a single `scoop:linix-no-such-pkg-zzz`**.

One `heal`, measured three times at 189s / 193s / 201s, makes **30 recovery attempts**:

```
23 x scoop:linix-no-such-pkg-zzz     (cannot exist)
 2 x winget:MSIX\Microsoft.Winget.Source_...  (Q36)
 2 x nimble:nimjson                  (a full nim build)
 2 x github:sharkdp/fd               (Q37, 180s of the total)
 1 x web:...dust.zip
```

Every one is known-doomed before it starts, and they run one at a time — in a program whose sync
is a parallel DAG.

`watch --once` costs **208s** for the same reason: **`watch` runs `heal` first.**

## 5. `Q34` — `install X` converges the whole manifest

```
linix -y install bun:sort-package-json
Planned changes:  install 2   backends: bun, scoop   <- an unrelated leftover
```

The scoop member cannot resolve, the transaction fails, and the caller is told **bun** failed.

**Ten of the run's thirteen failures are this** — bun, dotnet, github, nimble, pnpm, pub, winget,
yarn, plus `activate converges onto the named profiles` and the real-lifecycle ratchet collapsing
to `1 real lifecycle, below the recorded 5`. None of those backends had anything wrong.

Section 12 of the Windows sweep has not been measuring backends. It has been measuring one
leftover declaration — a large part of why the Windows leg has never meant what the container leg
means, and invisible before because the sweep never got that far without being killed.

**Q34 is a symptom, not the disease.** The declaration is only there because scoop's failure was
classified `unknown` (§1a), and Q1 already rules that a permanent failure withdraws the line. Fix
§1a and *that* cascade does not start. What remains genuinely open in Q34 is narrower and worth
asking anyway: when a member unrelated to the requested spec fails, the error still names the
innocent package.

### CORRECTION — the scoop leftover was only one of two sources

I first attributed ten of the run's thirteen failures to the leftover above. **The confirmation
run, with §1a fixed, disproves the larger half of that.** `the unresolvable name is out of the
manifest` is gone and `nimble` now classifies `permanent` instead of `unclassified` — so §1a was
real — but `bun`, `dotnet`, `pnpm`, `winget` and `yarn` still fail, for a different reason
entirely:

```
Error: `sc` failed (exit 1056): [SC] StartService FAILED 1056:
An instance of the service is already running.
```

`adopt` wrote **150 `service:X@status=running`** lines — every running Windows service. Converging
one runs `sc start` on a service that is already running, which returns `1056`; that is the
*desired state*, it appears nowhere in the codebase, and the service backend has no exit policy at
all. Q34 then fails the whole transaction and blames the innocent package. Written up as **Q39**,
which is probably the most user-visible defect on Windows: **after `adopt`, every `install`
fails.**

The general lesson, which cost me a wrong claim: **a cascade with one identified source is not a
cascade with one source.** I should have re-run before attributing, which is exactly what the
confirmation run was for.

## 6. `Q36` — `adopt` writes declarations that decay

`winget list` reports MSIX/ARP pseudo-ids, and those ids **contain the version**. `adopt` wrote
186 of them. One moved while this session ran:

```
adopted:       MSIX\Microsoft.Winget.Source_2026.805.1050.50_neutral__8wekyb3d8bbwe
installed now: MSIX\Microsoft.Winget.Source_2026.805.1206.6_neutral__8wekyb3d8bbwe
```

10:50 to 12:06, same day. The declaration now names a package that does not exist, can never
converge, and **feeds Q34's cascade on any real Windows machine that runs `adopt`** — this one is
not a harness artifact.

## 7. `Q35` — the terminal handed to Windows children, for a reason Windows does not have

U40 lets a mutation share stdin because *"`sudo` asks for a password on the terminal it was
started from"*. `executor.rs:834` is `if sudo && !cfg!(windows) && ...` — sudo is never inserted
on Windows, so nothing there has anything to ask, while the sharing stays:

| LiNix's stdin | same install |
|---|---|
| not a terminal | **48ms** — child gets `Stdio::null`, reads EOF, done |
| a real console | **21.9s** — the whole bound; at the shipped 900, fifteen minutes |

**This was my theory of the stall and the capture refuted it** — the wedged process had no child
at all. Recorded because the hazard is real and measured, and because the next person seeing an
idle `linix` should find all three shapes here rather than rediscover one.

## 8. `Q38` — `watch --once` failed and exited 0

```
WARN watch: reconcile failed: `scoop` failed (exit 1): Couldn't find manifest for '...'
rc=0
```

A scheduled `watch` is the least-watched surface in the program. An exit code that says "fine"
after a failed reconcile is Q28's class at the one place nobody reads the output.

## 9. The seven open journal operations, explained

The run's `journal: 7 operation(s) are still open ... and nothing crashed` was previously assumed
to be an artifact of hand-killing wedged processes. **It is not.** Nothing was killed by hand in
this run, and the seven are exactly the entries `heal` can never recover:

```
github:sharkdp/fd x2   nimble:nimjson   scoop:linix-no-such-pkg-zzz x2
winget:MSIX\Microsoft.Winget.Source_... x2
```

Q37, Q33 and Q36 respectively. The harness check is right to flag it; the number means
"permanently unrecoverable", not "interrupted".

## 9a. Speed — `heal` is the one path with no parallelism at all

The 2026-08-02 ruling is standing: *as parallel as possible, as efficient as possible, as fast as
possible; restructure if it takes that.* Measured on this host, LiNix's own `--timings`, same
machine and same minute:

| command | wall | child commands | overlap | waves |
|---|---|---|---|---|
| `sync --dry-run` (466 declarations) | 2.65s | 21 → 10.35s | **3.9x** | 2 |
| `check health` (~55 backends) | 6.6s | — | — | — |
| `list` | 3.2s | — | — | — |
| `--version` | 0.1s | — | — | — |
| **`heal`** | **205.14s** | 27 → 33.31s | **0.2x** | **27** |

The engine is fine. `heal` is not part of it: **27 waves for 27 commands is fully serial**, and
each call is `handler.install(std::slice::from_ref(spec))` — one package per command, so I-1's
batching is bypassed too. 23 of the 30 attempts were the *same* package.

And only 33s of the 205s is inside child commands. The other ~172s is the in-process GitHub
download of §3 — which, being in-process, never appears in the breakdown at all. That is why
three stalls read as wedges.

Written up as **I-48** and **I-49** in `docs/INEFFICIENCIES.md`, with the caveat that I-48's
correct fix is to route recovery through the transaction engine rather than parallelise a second
copy of it — and that the loop deciding *which* entries to run is `Q33`, which is OPEN and is the
same loop. They should land together.

## 10. Defects in the harness — mine

1. **An automated sweep handed LiNix a terminal.** Fixed: `exec < /dev/null`, with
   `LINIX_IT_KEEP_TTY=1` to put it back — a fix that deletes the only way to reproduce a bug
   leaves nobody able to show it existed.
2. **The stall capture's arming check depended on `command -v powershell.exe`**, which fails in a
   stripped shell, so the capture would have silently not armed. Fixed with a System32 fallback.
3. **The first `heal` probe's watcher guarded on `pgrep -f linix.exe`**, which never matches a
   native Windows process from msys — it exited on tick one and took **zero** snapshots while
   reporting nothing wrong. Fixed by removing the guard. This is the same disease as the rest of
   this document, committed by the person documenting it, twice.
4. **The summary's stall excerpt greps too loosely** and prints the harness's own `bash`
   processes instead of the wedged `linix` tree. Cosmetic, real, not yet fixed.
5. **The Q34 cascade makes section 12 measure the leftover.** The harness must resolve its
   deliberate unresolvable declaration once it has finished asserting on it.
6. **`choco` was skipped for want of elevation.** Elevation is one prompt away on this host, so
   this is an avoidable coverage gap rather than a property of the platform.
7. **The harness and the product disagree** about whether a failed install's name leaves the
   manifest. `GRADE-2026-07-28` E2 records that this assertion was deliberately pointed at the
   product, so it is not obviously stale — surfaced rather than picked.

## 12. Waiting on a ruling

`Q32`, `Q33`, `Q34`, `Q35`, `Q36`, `Q37`, `Q38` are in `docs/spec/decisions.md` as **OPEN**, each
with its measurement and a recommendation.

Ranked by what they cost:

0. **§1a — the missing exit policy on scoop/winget/choco. Needs no ruling; it is a bug against
   an existing one (Q1).** It is the root of ten of the run's thirteen failures, and it leaves
   the default Windows backend unable to tell a nonexistent package from a dropped network — or,
   worse, a failed scoop command from a successful one. Fix this first; several entries below
   shrink or vanish when it lands.
1. **Q37** — 180s per `heal`, and the reason three stalls were misread. One-line ordering fix.
2. **Q32** — unbounded, silent, and reports success. A bound a command can walk around is not one.
3. **Q36** — `adopt` plants declarations that decay; feeds the same cascade on a real machine.
4. **Q33** — doomed and serial; the cost multiplies the three above.
5. **Q34** — reduced by §1a to "the error names the innocent package".
6. **Q38**, **Q35** — small, and both are "says fine when it is not".

**And one that is not on the list because it is not a decision:** the guard test in §1a must be
rewritten to assert against the built registry. Every other item here was found by measurement;
that one was found by reading a test that had been green all along.

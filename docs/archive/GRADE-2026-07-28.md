## 0. Verdict

**Overall: B−.** Up from C+. The blockers are closed; the gap to B is two enumerations that were never re-derived.

The blockers are genuinely closed. `E1` — the config-wedging bug that was the headline — is
fixed at the mechanism, not the instance. The harness assertion that could not fail is gone and
was replaced with one that examines the product. The catch-all that laundered defects into
"ecosystem variance" is now an empirical classifier that retries once and calls a repeat a
defect. `cargo fmt` is hard in both local gates and the tree is clean. **27 of the 34 indexed
defects are closed, and I could reproduce the closure of every one of them independently.** (I
scored E11 closed on this machine and had to reverse it when a fresh container showed the real
argv — see the note in §2.)

Three things keep it off B, and two of them are worse than anything in the original list.

**A removal path with no guard, no count, and no plan line.** `src/app/apply/extras.rs:105`
tears down every non-package resource LiNix manages — `link:`, `service:`, `setting:`, `shim:`,
`schedule:`, `repo:` — by calling `remove()` directly, outside the transaction and outside
`guard::enforce`. Measured: with the guard configured to refuse more than one removal and to
protect a name, `linix sync -y` deleted five managed files including the protected one, exited
0, and printed `already up to date`. `--dry-run sync` printed `already up to date` too. This
contradicts `readme.md:266` ("**every path that removes anything** goes through one guard"),
`guard.rs`'s own module doc ("*Every* path that deletes is guarded... A guard on one command is
a guard on nothing"), and `CLAUDE.md`. It is the same shape as the bug that motivated the guard,
in the one family nobody enumerated.

**`--dry-run` still performs five commands.** `dry_run_tests.rs` fixed the reported case and its
three nearest neighbours; `activate`, `deactivate`, `lock`, `git init` and `config init` were not
among them. `--dry-run activate Work` switches the active profile — which decides what the next
`sync` installs and removes — and prints nothing at all.

**The security refusals exit `1`, not `3`, and never fire the refusal hook.** Eight sites whose
own message says *"refusing to…"* — plain HTTP, unverified downloads, unprotected secrets,
decryption into the git repo, unapproved hooks, deploying over a foreign file, files outside
`$HOME` — are not built as `Error::Refused`. So they return the code that means "failed", and
`on_guard_refusal` never fires for any of them, while `main.rs:185` states in so many words that
every refusal in the program passes through that arm. The refusals that behave correctly are the
ones about removing packages; the ones that do not are the entire SEC/T series.

All three are the same failure the whole assessment is about, and it is worth naming precisely:
each fix went to the instance that had a reproduction attached, and the *family* was never
enumerated from the code. `readme.md:266` quantifies over removal paths — ten sites, nine
guarded. `main.rs:185` quantifies over refusals — twenty-three sites, fifteen conforming.
`CLAUDE.md` has a section called "Fix the whole family, not one instance"; these are the siblings
it names.

**What a user can rely on today:** the package engine. Install → list → binary-on-PATH → remove →
gone is a real, verified round-trip on scoop (Windows) and on apt/cargo/gem/github/npm/pipx/uv
(Ubuntu container), plus 20 more in the `tools` image. Failures are loud and legible. The package
removal guard holds on all nine package-removal call sites enumerable from the code, and two
concurrent syncs serialise correctly on the data lock.

**What they cannot:** anything that removes a non-package resource; `--dry-run` on `activate`,
`deactivate`, `lock`, `git init`, `config init`; a script that branches on the published exit
codes to tell a security refusal from a crash; and any of the ~30 backends that have still never
been run against their real tool.

Severity is user impact.

### G-1 — `sync` removes managed resources with no guard, no count, and no plan line — **blocker**

`src/app/apply/extras.rs:105`. The word `guard` does not appear in that file.

```
$ linix protected
  Protected packages (1):  f3
  Maximum removals in one command: 1 (max_removals).

$ linix sync -y            # five link: declarations applied, five files created
$ : > modules/starter.txt  # undeclare all five
$ linix --dry-run sync
already up to date
$ linix sync -y
already up to date
$ ls <targets>
(empty)
```

Five managed files deleted, including the protected `f3`, against `max_removals = 1`, reported as
no change. Three distinct failures:

1. **Invisible** — nothing in `plan`, `--dry-run` or the summary names the removal.
2. **Uncounted** — the count is never computed, so `max_removals` cannot apply.
3. **Unprotected** — `protected_packages` does not reach it, and V.26 says protection is a
   refusal nothing overrides.

`--dry-run` itself correctly performs nothing (the `dry_run` check at `extras.rs:66` works); the
defect is that neither the preview nor the real run *reports*.

**Family checked.** I enumerated every call site that can reach a backend `remove`/`purge` from
the code, not from a list — 10 sites. Nine route through `guard::enforce`, and I read each rather
than trusting the count: `leases.rs:75` (ExpirySweep), `sync/mod.rs:726` (Heal),
`transaction.rs:500/502` (guarded at plan time by `sync/mod.rs:141`), `transaction.rs:714`
(rollback, guarded at `:688`), `cleanup.rs:88` (RemoveOrphans — `enforce` at `:57`, dry-run
guarded, confirmed), `cleanup.rs:298` (PurgeUnmanaged), `packages.rs:437` (Remove),
`plan.rs:427` (Apply). **`extras.rs:105` is the only one that is not.** It is unguarded for all
six extra kinds, not just `link:`.

`link:` is the mildest member — the source file stays in the config repo, so the bytes are
recoverable. `service:`, `setting:` and `shim:` have no such net.

Red tests: `tests/grader_extras_guard_tests.rs` (2, both red).

### G-3 — `Retryability::Transient` is a claim nothing tests, and here it is false — **medium**

The container harness proves transience the only way it can be proved — it retries once and calls
a repeat a defect. The product decides the same question by matching a string.

```
$ curl -o /dev/null -w '%{http_code}' https://luarocks.org/manifest-5.5
200
$ luarocks install luafilesystem      # three times, byte-identical each time
Warning: Failed searching manifest: Failed downloading https://luarocks.org/manifest-5.5
Error: No results matching query were found for Lua 5.5.
```

The manifest is reachable from this host; luarocks' own downloader fails, because the `wget` first
on this PATH is a scoop shim. `exit_policy::luarocks()` lists `"failed downloading"` and
`"failed searching manifest"` as transient, so LiNix keeps the declaration and tells the user
`sync` will try it again. It will fail identically forever.

The policy's doc comment names this exact cause — "a machine whose only problem is that the `wget`
on its PATH is BusyBox's applet, which rejects the GNU flags luarocks passes" — and classifies it
as the network anyway. That is READINESS §3.4's defect moved from the harness into the product.

This is E12's real content. The builder's ruling (don't pin a Lua version) is defensible and I am
not second-guessing it; the finding is that the *classification* is asserted rather than tested.

Red test: `tests/grader_transient_claim_tests.rs` (1, red).

### G-4 — the gate-parity check compares basenames, not gates — **medium**

`harness-logic-test.sh:291` exists because a local gate weaker than CI turns a local GO into a CI
NO-GO. It greps `ci.yml` for `scripts/*.sh` and asserts each **basename** appears in both release

CI runs `harness-mutation-test.sh` **twice** — once with no argument (the Windows harness) and once

appear in both files.

Compounding it: the budget the container harness needs lives only in `ci.yml`. Running the script

```
$ bash scripts/harness-mutation-test.sh docker/integration/run-in-container.sh --check apt jq
   90 check(s) passed anyway
 FAILED: 90 checks survive a do-nothing binary, over the budget of 86.
```

**I checked before claiming this was a CI failure — it is not.** CI passes `SURVIVOR_BUDGET=92`.
The finding is the split, not a red CI.

This is READINESS §5.3's family (a checker examining something adjacent to what it is named for)
living inside the check that was written to close §5.3.

Red tests: `tests/grader_gate_parity_tests.rs` (2, both red).

### G-7 — `list --backend <typo>` succeeds silently, and that disarms the rubric's own A-bar check — **medium**

`install` is asked whether a name is a backend and answers loudly:

```
$ linix install nosuchbackend:foo -y
Error: Configuration error: <argument>: `nosuchbackend` is not a backend LiNix uses
  add `nosuchbackend` to your `priority` file, or check the spelling.
rc=1
```

`list` is asked the same question and says nothing:

```
$ linix list -b nosuchbackend ; echo $?     ->  0, no output
$ linix list -b aptt          ; echo $?     ->  0, no output      (a typo)
$ linix list -b APT           ; echo $?     ->  0, no output      (wrong case)
$ linix list -b ''            ; echo $?     ->  0, no output      (empty)
```

Zero rows and exit 0 is exactly what a real backend with nothing installed prints. So a user who
mistypes `--backend` is told, in the program's own voice, that the manager is empty. Principle I
is "fail loud, never silent", and one verb obeys it while its sibling does not — E18's family
(one condition, two behaviours), on a different pair of verbs.

**It also invalidated a measurement of mine, which is why it is here rather than in a footnote.**
§8.1's A bar includes "Every `[READY]` backend can answer `list`". I ran that check over all 24
READY backends and all 24 exited 0 — and then, testing the oracle rather than trusting it, found
that a nonexistent backend exits 0 too. Only **11** of the 24 returned any rows; the other 13 are
indistinguishable from a typo. My own check could not fail for half its subjects. The ledger row
above is corrected accordingly.

Red test: `tests/grader_unknown_backend_tests.rs` (1, red).

### G-8 — the argv-drift gate checks subcommands, not flags, and the first flag added after it shipped is rejected — **high**

`capability.rs:34` — `const VERIFIES_ITSELF: &[(&str, &str)] = &[("helm", "--verify=false")];` — is
E11's fix. It is emitted unconditionally when a declaration carries `@unverified`.

| host | helm | result |
|---|---|---|
| this Windows box | **v4.2.3** — `helm plugin install --help` lists `--verify` | flag accepted |
| the `tools` container | **helm 3.x** — no such flag | `Error: unknown flag: --verify` |

So `@unverified` works on helm 4 and breaks every helm 3. The original E11 error text was helm 4's
own suggestion (`Use --verify=false to skip verification`), which is presumably where the flag came
from — a fix derived from one machine's error message and shipped unconditionally.

**The gate that exists to catch exactly this cannot see it.** `tests/argv_drift_tests.rs:103`
says in its own words: *"A token that is a subcommand rather than a flag"* — flags are out of
scope by construction. 72 subcommands are verified against live tools; **zero flags are.** The
first flag the repo added after building the drift gate is one a real manager rejects, and the
gate was green the whole time.

This is E13's class exactly — an argv LiNix constructs that upstream does not accept — reopened
one level down, in the dimension the gate does not cover.

### G-9 — four more backends fail a real install, found the first time anyone ran them — **high**

The `tools` image is the widest live coverage this repo has (18–24 ecosystem managers). I built
and ran it. Every one of these failed **twice** — the harness's classifier retried and correctly
called them defects rather than variance, so none is a network flake:

| backend | error | reading |
|---|---|---|
| `asdf` | `No such plugin: --` | LiNix passes a bare `--` where a plugin name belongs |
| `mix` | `Could not find an SCM for dependency :hex` | wrong verb — `hex` installs via `mix local.hex` |
| `spack` | `Spec ~~zlib has no name; cannot concretize an anonymous spec` | LiNix emits `~~zlib`; the version-pin syntax is doubling a `~` |
| `opam` | `No switch is currently set` (exit 50) | opam needs an initialised switch; nothing sets one up or says so |
| `nimble` | install and `list` both pass, binary never reaches `PATH` | E6c's family — and `reachable.rs` did not warn here |

Three of the five are malformed argv, which is the same family as E13 and G-8 and is what an
argv-drift gate over **flags and operands** would catch.

**This is READINESS §5.1's thesis confirmed by measurement, not argument.** Twenty-four backends
attempted a real lifecycle in that image; **six failed.** A 25% defect rate in code that had never
been run against its real tool, exactly as predicted, found in a single pass.

**Credit where it is due:** none of these was laundered. The E5 classifier retried each once and
named it `a defect, not ecosystem variance`, and the coverage audit hard-failed instead of
soft-passing. The instrument did its job on real data — which is the strongest evidence in this
report that the harness work was worth doing.

### G-10 — the security refusals exit 1, and the refusal hook never hears them — **blocker**

`readme.md:708` publishes the contract: `3` refused, `1` failed. E25 found one refusal returning
`1` and it was fixed for `purge-unmanaged`. The family was not swept.

```
$ linix install 'web:http://example.com/tool.tar.gz' -y
Error: Validation error: refusing to download … over plain HTTP
EXIT=1                                     <-- contract says 3

$ linix reset </dev/null
EXIT=3                                     <-- correct, for contrast, same binary
```

Enumerated from the code: every site whose own message says *"refusing to…"* and which is **not**
built as `Error::Refused`:

| site | what it refuses | rule |
|---|---|---|
| `core/download.rs:46` | plain HTTP | SEC2 |
| `core/download.rs:69` | unverified, no `@sha256` | SEC2 |
| `core/executor.rs:396` | a secret nothing protects | T5 |
| `backends/link.rs:68` | decrypt into the git repo | T2 |
| `app/hooks.rs:55` | unapproved hooks | II.12 |
| `app/shim_manager.rs:98` · `utils/file.rs:174` | deploy over a foreign file | SEC1 |
| `app/apply/dotfiles.rs:67` | files outside `$HOME` | SEC3 |

**The refusals that correctly return 3 are the ones about removing packages. The refusals that
return 1 are the ones about security.** That is the whole SEC/T series.

**The exit code is the lesser half.** `src/main.rs:185`, on the `Error::Refused` arm:

> *"`on_guard_refusal` (XIII.13) fires here and nowhere else: this is the one point every refusal
> in the program passes through, so no command can be added that refuses without the hook hearing
> about it."*

False for all eight. Someone who wires `on_guard_refusal` to be told when LiNix refuses something
is told about a mass removal and is **not** told when LiNix refuses an unverified download, an
unprotected secret, or an unapproved hook — silent exactly where it matters most. It is a comment
asserting something about paths it never enumerated, which `spec/history.md` calls the mistake
that cost more than the rest combined.

**It also explains a harness result.** `classify_install` keys `refused` on rc=3, so LiNix
refusing correctly (`github:sharkdp/fd` — the target file exists and LiNix did not create it)
arrives as rc=1 and is scored *"a defect, not ecosystem variance"*. READINESS §3.4 complained that
a correct refusal was laundered into a soft pass; it is now laundered into a **false hard
failure**. The harness still cannot see the truth, because the product does not tell it.

Red tests: `tests/grader_refusal_exit_code_tests.rs` (2, both red; `reset` returning 3 is the
control).

### G-11 — the coverage audit has a floor for an empty registry and none for collapsed coverage — **medium**

The clean Windows sweep reports:

```
backends: 4 real lifecycle, 12 install-attempted, 44 plan-smoked
PASS  every registered backend got a lifecycle or a plan-smoke
```

Four. Not because anything broke — because **8 of the 15 canaries were already installed on this
host**, and the harness correctly refuses to remove software the user already had:

```
soft  bun: cowsay is already installed on this host — left alone rather than removed
soft  cargo: hexyl is already installed on this host — left alone rather than removed
soft  gem: colorize …   soft  go: …hello …   soft  npm: cowsay …
soft  pipx: pycowsay …  soft  pixi: ripgrep …  soft  pnpm: cowsay …
```

The rule is right. The consequence is that **the gate's coverage is inversely proportional to how
much the host is used** — a developer's real machine tests a quarter of what a clean runner would —
and the coverage audit passes identically either way, because a plan-smoke satisfies it.

G2 gave this audit a floor for the case where the *registry* enumerates nothing. It has no floor
for the case where *real lifecycles* collapse. A run with 4 and a run with 15 are both `PASS`.

**No red test for this one**, and deliberately: the honest assertion is a threshold on a number
that legitimately varies by host, and picking that threshold is the owner's call, not mine. The
measurement is the finding. A floor of the form "fail if real lifecycles fall below the last
recorded count for this host class" is the shape the mutation gate already uses.

### Things that held up, checked adversarially rather than assumed

Recorded because a report that lists only defects misrepresents the tree.

- **Concurrency.** Two `linix sync -y` runs started at once: the second waited on the data lock,
  named the holder and its pid (`waiting for the data directory — held by linix sync (pid 61648)`),
  then correctly reported `already up to date`. The package was installed exactly once.
- **pty vs pipe.** In the ubuntu container, `linix list -b apt` through a real pty
  (`script -qec`) and through a pipe produced **579 lines each**, identical but for line endings.
  The stdio defect is genuinely fixed.
- **Hostile input.** Package names containing `'; New-Item …`, `$(touch …)`, backticks, `;`,
  embedded newlines, `--force`, `CON`, `../../../etc/passwd` and `\\?\C:\Windows\System32` all
  produced named refusals. Nothing panicked; no marker file was created; nothing executed.
- **The exemption predicate can fail.** I re-added `undo` to `EXEMPT_CMDS` and watched
  `harness-logic-test.sh` go red (`exempts subcommands the binary does not have: undo`), then
  restored the file. E29's fix is a real check, not a green one.
- **EPIPE.** `linix list -b winget | head -1` exits 0 with no panic.

### G-6 — 86 of 120 Windows-harness checks pass against a binary that does nothing — **low, contextual**

Not a new defect; the mutation gate reports it honestly and ratchets it. Recorded because it is
the number that sizes the remaining work: 72% of the Windows harness's checks are exit-code-only.
The 34 that caught the stub include the ones that matter (`list shows jq`, the refusal checks, the
G2 registry floors), so the harness is not hollow — but "283 checks passed" means far less than
it reads.

Related oracle weakness, per §2.5: `jq binary is on PATH` survives the do-nothing stub because
`jq` is already installed on this host. The install→list pair catches it; the PATH check alone
does not.

## 7. The two things to do first

Not E7, and not the coverage ratio. **G-1 and G-10** — and they are the same bug wearing two
coats.

G-1 costs a user files: `sync` deletes managed resources past a configured `protected` entry while
the preview and the summary both say nothing happened. G-10 costs them the ability to *know* LiNix
refused: the eight refusals that protect against plain HTTP, unverified downloads, unprotected
secrets and unapproved hooks exit with the code that means "failed" and never fire the hook whose
entire purpose is announcing a refusal.

Both were found the same way, and it is the way the repo's own history says to find them: **not by
reading the sentence that quantifies over the paths, but by enumerating the paths from the code.**
`readme.md:266` says every path that removes anything is guarded — ten sites, nine guarded.
`main.rs:185` says every refusal in the program passes through one arm — twenty-three sites,
fifteen do. Each sentence was true when written and neither was re-derived afterwards.

That is the whole finding, and it is the same one READINESS §5.3 made: *a list is an assertion
about what is absent, and nothing verifies that half.* The fix for both is mechanical. The habit
that prevents the third one is not.

## 0. Verdict

**Overall: B.** Up from B−. The two round-2 blockers are genuinely closed, at the mechanism, and
I could reproduce the closure of each independently. What keeps it off B+ is that **two of the
six new findings are the previous rounds' own blockers, alive one branch over** — and both were
found the same way as last time: by enumerating from the code instead of reading the sentence
that quantifies over the paths.

**The round-2 work is the strongest single round this repo has had.** G-1's guard, G-2's five
previews, G-10's refusals-and-hook, G-3's empirical retry classifier, G-4's parity check, G-7's
unknown-backend refusal and G-5's deletion are all real, all reproduced here, and several are
better than the brief asked for. The retry classifier in particular now says, in the user's own
words, *"tried 4 times; the failure did not change, so a further retry will not help — this is
not the transient failure its output looks like"*. That is the best sentence in the program.

Three things keep it off B+.

**E1 is live on three of five backends.** The blocker the whole assessment opened with — a name
nothing can install, left in `modules/imperative.txt`, wedging every later command — is fixed for
`scoop` and `cargo` and **not** for `npm`, `github` or `luarocks`. Measured: after `linix install
github:linix-zzz-nope/nope -y`, the line stays and every subsequent `sync` exits 1 forever.
`withdraw_what_can_never_succeed` matches two error shapes; a third turned up the first time a
different backend was asked. The user is told *"`sync` will try it again"* — the exact sentence
`packages.rs`'s own comment forbids for a failure that repeats identically.

**The extras family is outside the model everywhere except the apply loop.** G-1 listed three
failures: unguarded, uncounted, invisible. The guard and the count are fixed and verified. The
invisibility is not. `linix check` reports *"the machine matches your files"* while a declared
`link:` is missing from disk, and again after one LiNix placed is deleted behind its back.
`plan` freezes an empty plan in both directions and `apply` prints `Plan is empty`. `sync`
places files and prints `already up to date`. And the guard's own refusal text tells the user to
run `linix plan` to *"see exactly what would be undone"* — where they will see nothing.

**The flag half of the argv-drift gate cannot fail on the flag it was built for.** Plant a
plainly bogus flag in `VERIFIES_ITSELF` on a host where helm is `[READY]`, and the gate stays
green — because `tool_help::accepts_flag` withholds the flag before it reaches an argv, and the
gate reads argvs. Measured green in both directions. This is the repo's signature defect
occurring inside the check built to end it.

**What a user can rely on today:** the package engine and the safety model. Install → list →
binary-on-PATH → remove → gone is a real round-trip on scoop and cargo (Windows) and on
apt/cargo/gem/github/npm/pipx/uv (Ubuntu container, 283 checks, 0 failures, re-run today).
Removal is guarded on every path enumerable from the code, including the extras path that was
not, and protection is not overridable by `--allow-mass-removal` — I tried. Security refusals
exit 3 and fire `on_guard_refusal`; so does the new extras refusal. `--dry-run` performs nothing
across every mutating verb I could reach, fourteen of them, each with a control.

**What they cannot:** `linix check` as evidence that the machine matches, if anything but
packages is declared; `plan`/`apply` for anything but packages; `linix info` as an answer about
the machine; a `sync` that stays usable after a failed `npm`/`github`/`luarocks` install; and any
of the ~24 backends that have still never run against their real tool.

## 3. Findings beyond the list

Severity is user impact.

### N-1 — E1 is live on three of five backends, and wedges `sync` forever — **blocker**

`src/verbs/packages.rs:153` (`withdraw_what_can_never_succeed`). One machine, one binary, five
names that cannot exist:

| declaration | exit | line taken back out of `imperative.txt`? |
|---|---|---|
| `scoop:linix-no-such-pkg-zzz` | 1 | **yes** |
| `cargo:linix-no-such-crate-zzz` | 1 | **yes** |
| `npm:linix-no-such-pkg-zzz-9` | 1 | **no** |
| `github:linix-zzz-nope/nope` | 1 | **no** |
| `luarocks:luafilesystem` | 1 | **no** |

```
$ linix install github:linix-zzz-nope/nope -y
 WARN `github:linix-zzz-nope/nope` is still declared in …/modules/imperative.txt, so `sync`
      will try it again. If you did not mean it, run `linix unmanage github:…`.
Error: Package 'linix-zzz-nope/nope: the repo has no published release' was not found in the
       target repository
rc=1

$ linix sync -y            # and identically, forever
Error: Package 'linix-zzz-nope/nope: the repo has no published release' was not found …
rc=1
```

**Why.** The withdrawal matches exactly two shapes: `Error::Unresolvable`, and
`Error::CommandFailed { retry: Permanent }` **whose message quotes the package name**. github
raises neither — it has its own not-found error. luarocks is the sharper case: LiNix retried four
times, compared the outputs, and told the user *"a further retry will not help"* — and then kept
the line anyway, because that verdict is not the same value the withdrawal reads.

**And the wording is the one the file forbids.** `packages.rs` says of a kept line: *"it must not
be described as a transient failure. '`sync` will try it again' … promises a retry that fails
identically forever, which is the sentence…"*. Three of the five backends print exactly that.

**Family checked.** Five backends sampled by hand, chosen to span a system manager (scoop), a
language manager (cargo, npm), a download backend (github) and a manager whose failure is
environmental (luarocks). Two withdraw, three do not. Not affected, and checked: the refusal
path — a plain-HTTP or missing-`@sha256` line is *deliberately* kept, the code says why, and the
refusal names the edit to make. That is a different case and it is right.

Red tests: `tests/grade2_wedged_manifest_tests.rs` (2, both red, control green).

### N-3 — `info` answers about the resolver, not the machine — **medium-high**

Two symptoms, one root: `App::get_info` (`src/app/context.rs:541`) never asks whether the prefix
is a backend, and never falls back to the machine when the resolver's pick comes up empty.

```
$ linix list -b cargo          →  cargo  ripgrep  15.2.0
$ linix info cargo:ripgrep     →  Package: ripgrep   Backend: cargo   Version: 15.2.0
$ linix info ripgrep           →  'ripgrep' is not installed on this machine …
$ linix list -b cargo          →  cargo  ripgrep  15.2.0        (unchanged, checked after)
```

`linix eval` shows the mechanism: bare `hexyl` resolves to **`choco:hexyl`** because choco is
first in `priority` and carries the name, so `info hexyl` asks choco, choco has nothing installed,
and LiNix reports a package the user has as absent. Same for `7zip` (installed via scoop).

And the typo case, where `install` and `list` both get it right:

```
$ linix install nosuchbackend:foo -y   → `nosuchbackend` is not a backend LiNix uses    rc=1, 215 ms
$ linix list -b nosuchbackend          → the same message                              rc=1
$ linix info nosuchbackend:foo         → 'nosuchbackend:foo' is not installed …        rc=0, 83 522 ms
```

83.5 seconds, twice, reproducibly: the unresolvable string is handed to every available backend —
the exact behaviour `get_info`'s own comment says was removed.

**Family checked.** `--backend` on `rebuild`, `upgrade`, `repo list`, `list`: all refuse, all
rc=1. The `backend:name` spec form on `info`, `unmanage` and `why`: none validate the prefix —
`unmanage nosuchbackend:foo` says *"not managed and not declared — nothing to forget"* at rc=0,
`why nosuchbackend:foo` says *"not under LiNix management"* at rc=0. `install` is the one that is
right.

Red tests: `tests/grade2_info_tests.rs` (2).

### N-4 — the flag half of the argv-drift gate cannot fail on the flag it exists for — **medium**

`src/backends/artifact/capability.rs:34`, `src/backends/generic.rs:414`,
`tests/argv_drift_tests.rs`. On this host `helm` is `[READY]` at v4.2.3.

```
# table as shipped
CALL: helm plugin install --verify=false -- https://example.invalid/linix-drift-probe
test result: ok. 1 passed

# one character of drift planted in VERIFIES_ITSELF
CALL: helm plugin install -- https://example.invalid/linix-drift-probe
test result: ok. 1 passed
```

`accepts_flag` asks helm's own help and **withholds** a flag the help does not document. That is
a good thing to do and a bad thing to do silently: the withheld flag is precisely the drifted one,
so the gate that inspects argvs has nothing to inspect exactly when it matters. Green over a
correct table and green over a wrong one.

The user-visible half is not hypothetical. If helm renames the flag, LiNix withholds it, helm
refuses the unsignable source, and `explain_verification` tells the user to *"Add `@unverified`
to the line"* — the line they already wrote.

The assertion the gate is missing: **a flag the capability table names, for a backend installed
here, must survive into the argv.** `tests/grade2_flag_drift_blindspot_tests.rs` is that
assertion; it is green on the shipped table and red on the mutation above, verified in both
directions.

### N-6 — the container gate cannot run at all on a Windows working tree — **medium, developer-facing**

The documented local entry point, on a clean clone of this branch:

```
$ bash docker/integration/run.sh jq
############### BUILD ubuntu (apt) ###############   … 18 min, succeeds
############### RUN ubuntu (apt) ###############
/src/docker/integration/run-in-container.sh: 22: set: Illegal option -
  ubuntu (apt): FAIL
```

`run.sh` bind-mounts the host's copy of the harness, and four `.sh` files in this working tree
have CRLF endings — `run-in-container.sh`, `integration-windows.sh`, `harness-logic-test.sh`,
`release-check.sh`. dash reads `set -u<CR>` and aborts before a single check runs.

**The committed blobs are LF, so CI is unaffected** — I checked with `git show HEAD:… | file -`,
and the four distro legs are green. `.gitattributes` exists for exactly this
(*"`*.sh text eol=lf` … without this, the integration harness is broken on any Windows clone"*)
and does not help, because it governs what checkout writes, not what an editor writes; the files
are the ones the round-2 commits edited. Nothing in the repo checks the working tree.

Cost: on the machine this project is developed on, the entire local container gate is silently
unavailable, and the failure names a shell option rather than a line ending. I re-ran the harness
with an LF copy to get the numbers in §1.

## 7. The two things to do first

Not the coverage ratio, and not `search`'s 160 seconds.

**N-1, because it is the same bug the assessment opened with.** A user who mistypes an npm package
name has a config that fails on every subsequent command until they read the warning and run
`unmanage`. That was E1, it was the headline, it was fixed for the two backends that had a
reproduction attached, and the other three were never enumerated. The fix is not a third arm in
the match; it is making "this name cannot exist here" a thing a backend *returns* rather than a
thing a message happens to contain.

**N-2, because it is the same bug as N-1 in a different currency.** G-1 named three failures and
two were fixed. The third is the one that decides whether a user trusts `linix check` — and today
`check` reports that the machine matches while a declared file is missing from it.

Both are the shape this repo keeps producing and the shape it keeps writing down: **a fix goes to
the instance that had a reproduction attached, and the family is never enumerated from the code.**
The round-2 work did enumerate — `readme.md:266` is true now, and I checked it path by path rather
than reading it. That is real progress and it is why the grade moved. The habit has to reach one
more layer: not just *"which paths remove?"* but *"which paths withdraw?"*, *"which paths report
drift?"*, and — the one that would have caught N-4 and N-5 — *"which gates would go red if the
thing they name were happening right now?"*

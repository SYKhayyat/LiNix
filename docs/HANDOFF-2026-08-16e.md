## What this round finished

### `schedule:` reads itself back — `J2`'s sibling, closed properly (`J6`, V.192)

**The defect.** Editing when a job runs, or what it runs, was reported as *nothing to do* by the
very `sync` that rewrote it. `cron` and `run` are not part of a schedule's ledger key, so the
edited line was the same key, was found in the applied-extras ledger, and never counted.
Provisioning is idempotent, so the machine always converged — it just never said so.

**The fix that was rejected, and why it matters.** `J2` was closed by putting the discriminating
option into the key (`setting:x@scope=system`). That does not transfer. A `setting:`'s scope makes
two genuinely different subjects; a schedule's **name is its identity** at the OS scheduler, so
`schedule:nightly@cron=old` and `@cron=new` are one cron entry. `reconcile` runs after the apply
phase and deprovisions by name — it would have deleted the schedule the apply phase had just
written. Editing a schedule would have silently removed it.

**So the machine is asked.** `TaskProvisioner` grew `rendered` and `read_task`, and each scheduler
answers in its own terms:

- **systemd and launchd keep files**, so the comparison is the whole unit Shall would write
  against the whole unit on disk. Exact, and self-maintaining: the next option added is covered
  without anybody extending a comparison.
- **Task Scheduler keeps no file**, so both sides are canonicalised — the declaration from the
  `/SC` arguments, the machine from its trigger XML. **The trigger shapes were captured from real
  tasks on this Windows 11 box**, not imagined; that is the only reason the comparison can be
  trusted. Weekdays sort Sunday-first on both sides, because `<DaysOfWeek>` is a set and a cron
  reading `5,1` would otherwise report drift for ever against an identical task.

**A shape Shall did not write is `unverifiable`, never drift** — V.188's rule arriving on a third
store. An unrecognised trigger, a second trigger somebody added by hand, an unanswerable query:
each reported as a mismatch would rewrite the task every sync for ever and keep `check` red on
something nobody can see. On Windows the query failure is separated from the answer by asking
`schtasks` a question it can always answer, because `ERROR: The system cannot find the file
specified.` is translated on a non-English Windows.

### Four new `schedule:` options, each expressed or refused by name

`enabled` (provision it and leave it silent), `persistent` (run a firing the machine was switched
off for), `jitter` (spread a fleet around the scheduled moment), `elevated` (run at the highest
privilege the account holds). **No scheduler has all four.** A `--user` systemd timer cannot raise
its own privilege; launchd has no randomised delay and no switch for catch-up; `schtasks` can set
neither `RandomDelay` nor `StartWhenAvailable`, because both live in XML it has no flag for.

Each provisioner expresses what it can and **refuses the rest by name, before it writes
anything** — accepting an option and dropping it is the same failure as the cron that was once
silently widened into `DAILY`. **An option nobody wrote is never refused**, which is why each
arrives as an `Option` rather than as a default: `persistent` is refused outright on Windows and
its default everywhere is *true*, so a default-as-value would refuse every schedule on every
Windows machine.

`every_option_is_either_expressed_or_refused_by_name` asserts the whole matrix as a table. **Its
first run found a hole** — launchd took `persistent` on an `@reboot` job, which has no calendar to
miss.

### Two defects the one-renderer rewrite exposed

- **An `@reboot` systemd job wrote its output nowhere.** The boot shape was produced by
  *overwriting* the file the ordinary shape had just written, and the replacement carried no
  `StandardOutput=`/`StandardError=` at all. The one kind of job nobody watches run.
- **`is_task_active` asked only about the timer**, so `remove_task`'s end-state assertion — the
  one that exists to stop Shall reporting a schedule as removed while it keeps firing — was
  vacuous for every boot job, which is precisely the case where a surviving unit runs the command
  again on the next boot.

launchd and Windows were checked for the same pair and have neither.

### NixOS: evaluated, built, and rolled back — on a real one

The biggest row in `proving.rs` got much smaller, with receipts:

| what was asked | answer |
|---|---|
| Does the module carrying `services.cron.enable`, `networking.firewall.enable` and both port lists **evaluate and build** on real NixOS 26.05? | **Yes** — `nixos-rebuild build` produced `nixos-system-nixos-26.05pre-git` |
| Is that check vacuous? | **No** — one option nixpkgs does not have failed with `The option ... does not exist` |
| Is the activation failure Shall's? | **No** — control: `nixos-rebuild switch` with the machine's own configuration and no Shall fails identically, exit 4, same dbus error |
| Did anything about Shall get proven by the failed switch? | **Yes, the rollback**: both `/etc/nixos` files were put back and the error named them, on a real failure nothing hermetic can stage |

**And it is automated now.** `scripts/nix-validate.sh --evaluate` imports each generated module
into a real NixOS module system (`<nixpkgs/nixos>`, same `nixos/nix` image) and forces the
attributes Shall writes. Measured end to end at **25s** — six modules parsed, four evaluated,
two container starts — so it is a per-push gate rather than a nightly; `--self-test` implies it and CI already passes `--self-test`. The evaluation self-test is
the failure it exists for — a module that is *perfectly valid Nix* naming a service nixpkgs has
never heard of, asserted to parse on the way in so it cannot pass by proving the parse gate again.

**A trap worth carrying forward, because it cost an hour.** The container harness first came back
`pass=384 fail=10`. None of it was a defect: the `shall-it-ubuntu` **image had a stale binary
baked in**, predating the nine-kind lock vocabulary, so `shall lock exec` and `shall lock adapters`
hit an older CLI that only knew `versions|backends|scripts|all`. The harness script is
bind-mounted and current; the binary is built into the image and is not. **When the harness fails
on a command's argument grammar, rebuild the image before reading it as a defect** — and the
tell is that the failures cluster on argument parsing rather than on behaviour.

Second trap, same afternoon: `latency_budget_tests` failed at 9.5s against a 5s budget for `shall
vars`, a command that reads no manager. The box was running a docker image build *and* the
container harness at the time. **The latency tests want a quiet box and say so in their own
message** — "on an unloaded box" is an assertion about the machine, not a claim about it.

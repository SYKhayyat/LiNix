## 0. Verdict

**Overall: B−.** Down from B, and not because the round was weak. **N-1 and N-2 are genuinely
closed, both at the mechanism, and the fixes are better than the findings asked for.** The grade
moves down because hunting past them turned up a defect of the class this repo's history is named
after: **`linix adopt --dry-run` writes the managed-state registry and no manifest, which leaves
the machine one recommended `sync` away from uninstalling everything it just previewed.** I drove
it end to end in a disposable data directory. One package installed, unmanaged, previewed, and then
removed by the `sync` that `linix check` told me to run.

**What the round got right, verified rather than accepted.** N-1's fix is not a third arm in a
message match — it is `Error::CommandFailed { absent_name: bool }` and a new `NoSuchPackage`
variant, with a doc comment that says why `absent_name` must not be derived from `Permanent`
(helm's `plugin already exists` is permanent about a name that plainly exists). Measured on five
backends: scoop, cargo, npm and github now withdraw the line; luarocks keeps it and says
*"the failure above repeated on every retry, so `sync` will keep failing the same way until its
cause is fixed"* — which is correct, because a manifest LiNix could not download is not a name that
does not exist. Two of five became four of five plus one right answer.

N-2 is closed in all three parts. `check drift` now reads *"0 to install, 0 to remove, 3 to place,
0 to undo"*; `plan` freezes resources and names each one with `+`/`- (no longer declared)`; `apply`
reconciles them. The extras family is in the model.

And the two inert gates from round 3 are in force, which I established by breaking them rather than
by reading them: planting a CRLF shell script turns `harness-logic-test.sh` red, and deleting one
floor mount from `ci.yml` turns it red with the count difference named. I also built and ran the
ubuntu image here and watched the ratchet actually compare — `real-lifecycle ratchet: 7 >= 7
recorded for container-linux-ubuntu-local`, where every leg of every round-3 run said *"the
real-lifecycle ratchet is not in force"*. `run.sh`'s new pre-flight self-tests its own CRLF detector
before trusting it, because MSYS `grep` normalises away the byte it was written to find. That is the
standard this document keeps asking for, met without being asked twice.

**Three things hold it at B−.**

**The dry-run blocker (B-1), and the gate that could not see it.** `tests/dry_run_every_verb_tests.rs`
opens by saying the honest reading of a probe of 13 of 61 subcommands is *"at least five, never
exactly five"* — and then snapshots the **config** directory only, and exempts `hold`, `unhold` and
`heal` with the words *"holds live in the data dir, not the config dir"*. The data directory holds
`registry.json`, the file that decides whether the next `sync` removes a package. Three verbs are
excused for writing precisely where the instrument cannot look.

**`plan` predicts a refusal `apply` does not make (P-1).** Undeclare three `link:` lines and `plan`
prints *"WARNING: `linix apply` will refuse this plan"* and explains it as *"its manager reports a
name no package line can hold"*. `apply` then performs it at rc=0, and so does `sync`. The guard
documents this exact trap and carries a unit test asserting it cannot happen — the test exercises
`inspect_removals(…, RemovalKind::Extra, …)`; `plan.rs` calls `inspect(…)`, which is `Package`.

**`linix protected <bare name>` is wrong for every name (P-3).** Including `jq`, the example in its
own `--help`, and including `sudo`, which *is* protected and gets the wrong reason. The guard's own
comment says why this matters: *"an inspector that contradicts the guard is worse than none, because
it is believed."*

**What a user can rely on today:** the package engine, the withdrawal of names that cannot exist,
the removal count guard, protection that `--allow-mass-removal` cannot override, refusals that exit
3 and fire `on_guard_refusal`, and — new this round — `check`/`plan`/`apply` telling the truth about
declared resources. The one lifecycle I drove here today — `github:sharkdp/hexyl`, installed, listed,
unmanaged, removed by `sync`, gone from `list` — worked at every step, and it worked while
demonstrating B-1; the round-trip evidence at any breadth is still the containers', not this
machine's.

**What they cannot:** `--dry-run` as a promise that nothing changed — on `adopt` it arms a removal;
`linix protected` for any name typed without a backend; `plan`'s guard warning as a prediction; and
`linix list -b pixi`, which reports a package named `exposes`.

### B-1 — `--dry-run` writes the managed-state registry, and on `adopt` that arms a removal — **blocker**

`src/app/adopt.rs:236-255`, `src/verbs/packages.rs:605`, `src/verbs/packages.rs:624`.

Fresh `LINIX_CONFIG_DIR`/`LINIX_DATA_DIR`, one binary, nothing else on the machine touched:

```
$ linix --dry-run adopt -y
Adopted 112 package(s).                                  <- past tense, no [DRY-RUN] marker
Manifest:  …/cfg/modules/adopted.txt                     <- and this file was NOT written
Deleting a line UNINSTALLS that package on the next sync.

$ find cfg data -type f | diff before -
> registry.json 29645                                    <- 112 packages recorded as managed

$ linix check
ok  config      0 package(s) declared
->  drift       0 to install, 112 to remove, 0 to place, 0 to undo
                   run `linix sync`

$ linix --dry-run sync
Planned changes:
  install 0   remove 112   (total 112 change(s))
  backends: bun, cargo, choco, go, helm, npm, pipx, pixi, pnpm, scoop, winget
```

A *preview* leaves the machine in the one state the model reads as **the user deleted every line**:
managed, undeclared. Driven to its conclusion in a disposable data directory, with only `github` in
`priority` so nothing on the real machine was in scope:

```
$ linix install github:sharkdp/hexyl -y     ✓ [github  ] sharkdp/hexyl  (60637ms)
$ linix unmanage github:sharkdp/hexyl       no longer managed by LiNix. It is still installed.
$ linix --dry-run adopt -y                  Adopted 113 package(s).
$ linix check                               ->  drift  0 to install, 1 to remove …  run `linix sync`
$ linix sync -y
  install 0   remove 1
Status:       SUCCESS
  ✓ [github  ] sharkdp/hexyl        (70ms)
$ linix list -b github                       (nothing)
```

**Why.** `adopt` routes its manifest write through `Writes::for_run(self.config.dry_run)` — correct
— and then calls `state_mut.add()` for every discovered package followed by `save()`, with no
dry-run test at all. The honest line about the manifest goes out at `info!`, below the default
filter; the misleading line is a `println!`. Run it with `-v` and both are visible at once:

```
 INFO adopt: Would write 347 line(s) in …/cfg/modules/adopted.txt
  Added `use adopted` to profile Main — that module is now part of this machine.
Adopted 112 package(s).
```

Two past-tense sentences about writes it did not make, and one write nobody asked for that is not
mentioned at all.

**The count guard is the only thing between this and a mass uninstall**, and only above the
ceiling: 112 > `max_removals` 20 would refuse (I did not run that on this machine — READINESS §0
rule 5), while the 1-removal case above was under it and nothing objected. Any machine with fewer
than 20 adopted packages gets the removal with no refusal at all. And the refusal a bigger machine
gets ends with `<command> --allow-mass-removal carry out this removal anyway`.

**Family, enumerated from the code.** All 17 `.save()` sites listed, 14 read in context. Three write
under `--dry-run`:
`adopt` (above), `hold` and `unhold` — measured, `registry.json` changes and the output reads
`Held 1 package(s).` / `Released 1 hold(s).`. **The sibling that was fixed proves the class was
known**, `src/verbs/cleanup.rs:467`:

```rust
// The registry is what LiNix believes it manages. A preview that persisted `forget` would
// leave the package unmanaged for real while promising it had changed nothing.
if !app.config.dry_run {
```

Cleared, with the reason: `app/sync/mod.rs:198` and `verbs/plan.rs:509` run after a transaction
that `--dry-run` never enters; `app/leases.rs`, `verbs/upgrade.rs` and `app/diagnostics.rs` sit

**Why no gate caught it.** `tests/dry_run_every_verb_tests.rs` asserts that every subcommand

```
("hold",   "holds live in the data dir, not the config dir"),
("unhold", "holds live in the data dir, not the config dir"),
```

### P-1 — `plan` predicts a refusal `apply` does not make, in the wrong vocabulary — **high**

`src/verbs/plan.rs:254-272`. Three `link:` lines placed, then undeclared, default config:

```
$ linix plan
Wrote plan to linix-plan.json — 0 install(s), 0 removal(s), 0 resource(s) to place, 3 to undo.
  - link:…/dest/s1 (no longer declared)

WARNING: `linix apply` will refuse this plan.
apply: refusing this removal.
  - link:…/dest/s1 would be removed (its manager reports a name no package line can hold, so
    LiNix cannot manage it — and removing what you cannot declare is not something you asked for)

$ linix apply linix-plan.json -y
Applied plan: 0 installed, 0 removed, 3 resource(s) reconciled.        rc=0     (all three gone)
$ linix sync -y                                                        rc=0     (all three gone)
```

**Why.** `plan.rs` merges `extra_removal_pairs(&plan.resources.undo)` into the package removal list
and calls `guard::inspect(…)`, which is `inspect_removals(…, RemovalKind::Package, 0)`. The merge is
right — the ceiling is a property of the command, and a sync dropping three packages and three links
removes six things. Passing `Package` is not. `protection_of` opens with
`is_declarable(backend, name)`, and no extras key can ever parse as a package line, so all six kinds
come back `Undeclarable`.

**The guard documents this trap and carries a test against it.** `src/app/sync/guard.rs:973`,
`no_extra_is_refused_merely_for_not_being_a_package_line`, asserts a teardown of one of each of the
six kinds is allowed — through `inspect_removals(…, RemovalKind::Extra, …)`. It passes. The product
calls the other function. And `app/apply/extras.rs:146` states the property this violates, in the
opposite direction: *"a preview that skipped the guard would report a teardown the real run then
refuses, and the two must never disagree about the same machine."*

**Second symptom, same root.** With `max_removals = 1` the count objection fires, and `plan` renders
it with the wrong noun: *"it removes 3 **packages**, over the limit of 1"* for three `link:` lines.
`sync` and `--dry-run sync` both say *"3 **managed resources**"* — and both refuse at rc=3, with the
same text, so **the sync-side preview is sound**; this is `plan`'s alone.

Cost: the one warning a user is told to read before a removal cries wolf on the ordinary case —
deleting a dotfile line — and explains itself with a sentence about package names. A preview that is
wrong in the harmless direction is the same code that will be wrong in the other.

Red tests: `tests/grade3_plan_guard_kind_tests.rs` (3).

### P-2 — `sync` re-places every declared resource on every run — **medium**

`src/app/apply/extras.rs`. Same fixture, three consecutive runs:

```
$ linix sync -y          # nothing placed yet
 WARN Link: Cross-drive fallback to COPY for …/src/s1   (×3)
$ ls dest/               s1 s2 s3

$ linix sync -y          # everything already in place
 WARN Link: Cross-drive fallback to COPY for …/src/s1   (×3)
already up to date
$ ls dest/               s1 s1.linix-backup s2 s2.linix-backup s3 s3.linix-backup
```

`check` says *the machine matches your files* for this state and `plan` says *0 resource(s) to
place*. Both are right, and both now use `ExtrasManager::in_effect` — the probe round 3's fix added.
The placement loop asks neither, re-copies all three, and the second run creates
`.linix-backup` files in the user's directory that are backups of LiNix's own copies, under a
summary reading `already up to date`.

**Checked, and it is the one thing that goes right:** a user's genuine pre-existing file is backed
up on the first sync and the backup is **not** overwritten by later ones — I put
`PRECIOUS-USER-FILE` at the target, synced twice, and it was still in `s1.linix-backup`. The
teardown half is also correct and idempotent (`reconcile` returns early when the ledger matches).

Family: measured for `link`. `shim` has an `is_in_effect` probe and is presumably in the same loop;
`service`, `setting`, `schedule` and `repo` need Linux and are **not measured** — for a `service:`
this is the difference between reporting `already up to date` and re-running an enable on every
sync.

Red tests: `tests/grade3_resource_idempotency_tests.rs` (2).

### P-3 — `linix protected <bare name>` calls every unqualified name protected — **medium-high**

`src/verbs/cleanup.rs:525-546`. The command's `--help` documents the form: *"Check specific packages
instead of listing the rules (`apt:python3` or `jq`)"*.

```
$ linix protected jq
PACKAGE      PROTECTED  REASON
jq           yes        its manager reports a name no package line can hold, …
$ linix protected sudo                 # `sudo` IS in protected_packages (7 rules in force)
sudo         yes        its manager reports a name no package line can hold, …
$ linix protected ripgrep / hexyl / python3 / bash / zzz-not-a-thing
             yes        …the same sentence, every time
$ linix protected cargo:ripgrep
cargo:ripgrep  no       no rule matches
$ linix protected jq --json
  "protected": true
```

**Why.** An unqualified name gets `backend = ""`, and `protection_of` opens with
`is_declarable("", "jq")`, which builds the line `":jq"` and rejects it — so `Undeclarable` returns
before any rule is consulted. The comment three lines above states the intent exactly: *"a bare name
is checked against the config rules only."* It is checked against none of them.

Two harms, and the second is worse. A name no rule mentions is reported guarded; and for `sudo`,
which really is guarded, the answer to *which rule decides this* — the only question the command
exists to answer — is a sentence about package lines. `src/app/sync/guard.rs:96`: *"Everything that
asks 'is this protected?' must route through here — the `protected` command included. When the
inspector and the enforcer answer separately they drift apart, and an inspector that contradicts the
guard is worse than none, because it is believed."* The enforcer, given the backend the package
really has, says `no rule matches`.

**Family, from the code.** Every `protection_of` caller read. `app/leases.rs:35`, `verbs/sync.rs:342`
(rebuild) and `core/transaction.rs:691` take the backend from the state registry or a resolved plan,
so none can be empty; the extras path uses `RemovalKind::Extra`, which skips the declarability test
deliberately. **The empty-backend call is unique to this inspector** — one instance, and I checked
rather than assumed.

**Why no gate caught it.** `tests/unknown_backend_family_tests.rs` derives the verbs that take a
package spec from `--help`, which is the right instrument, and then exempts this one by hand:

## 7. The two things to do first

**B-1, because a preview that arms a removal is the bug this repo is named after.** E1 was a failed
install that wedged a config; this is a *dry run* that leaves the machine one recommended command
from uninstalling everything it just listed, and the command that recommends it is `linix check`.
The fix is not a third `if !dry_run` — that is how there came to be seventeen `save()` sites and
three that forgot. It is one writer that cannot be called under the flag.

**And the exemption lists, because they are how B-1 stayed invisible.** Two files in this repo now
carry hand-written lists of verbs excused from a rule, and **four** of those excuses do not hold: two
name the instrument's blind spot (`hold`, `unhold`), one calls a group whose `install` writes to
system hook dirs a read-only listing (`hooks`), and one calls a command that takes `[PACKAGES]...`
and answers about them a listing of the rules (`protected`). Every one was written by someone closing
a real finding, which is exactly why they were believed.

The pattern, four rounds in, is no longer *"a fix goes to the instance that had a reproduction
attached."* That habit is genuinely improving: `absent_name` swept ten backends, the resource model
closed all three parts of N-2, the floor gate compares counts rather than asserting a file exists,
and the CRLF check tests its own detector before trusting it. The pattern now is one layer up.
**Every finding in §3 is a gate that examines the wrong thing while the product does the wrong thing
behind it** — a snapshot of the wrong directory, a unit test of the wrong enum arm, an exemption for
the wrong reason, a fixture from no tool at all. That is READINESS §5.3's diagnosis three rounds
after it was written, having moved out of the shell harness and into the Rust test suite. The
question at the end of `GRADER.md` still finds something every time it is asked:

> **If the thing this is supposed to catch were happening right now, would this go red?**

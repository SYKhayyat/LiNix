## 2. What I verified rather than assumed

### 2.1 The removal guard is a real type-level proof

The strongest claim in the repo, and the one most worth checking independently. `Installable::remove`
cannot be called without a `Reaped` token; the token can only be minted by `Reaped::for_reason`.

`grep` finds **33** `for_reason` sites under `src/`, which looks alarming. Classifying each by
whether it falls inside a `#[cfg(test)]` block gives the real answer:

| | count |
|---|---|
| production mint sites | **2** |
| inside `#[cfg(test)]` | 28 |
| doc comment / definition | 3 |

The two are `app/sync/mod.rs:1196` (heal) and `core/transaction.rs:1210` (rollback), each carrying a
`file:line` justification for why the guard already ran. `src/backends/link_teardown_test.rs` looks
like production code from its path and is gated by `#[cfg(test)] mod link_teardown_test;` at
`backends/mod.rs:17`.

**This holds up.** It is the best piece of design in the repo and it is not decorative.

### 2.2 The declarative loop works, end to end — for packages with no conffiles

**Read B0 before believing this section.** The six steps below are real and they passed. They
passed because I ran them with `cowsay`, which is one of the packages that cannot expose B0. The
same six steps with `figlet` fail at step 5. I verified the product's central promise with a
sample that could not disprove it, which is precisely the defect this report spends nine sections
accusing the repo of.

Driven in a clean `ubuntu:24.04` container against real `apt`. Six steps, all correct **for this
package**:

```
0. before anything:            ABSENT
1. after first sync:           INSTALLED   <- installs what is declared
2. after idempotent re-sync:   INSTALLED   <- does not thrash
3. after out-of-band removal:  ABSENT      <- (apt-get remove, behind Shall's back)
4. does check see it?          drift: 1 to install, 0 to remove
5. after repair sync:          INSTALLED   <- repairs drift it did not cause
6. after deleting the line:    ABSENT      <- declarative removal
```

Step 4 is the one that mattered and it is genuinely right for this package: Shall queried the
machine rather than trusting its own registry. But the query it used is the one B0 shows is wrong,
so what step 4 actually proves is narrower than it reads — that the machinery *asks*, not that the
answer is true.

*(A correction against myself: a no-op `sync` benchmarks at 18 ms, and I flagged that as
"impossibly fast — it cannot have asked apt anything". It had. `dpkg-query -W` genuinely returns in
about 20 ms in a container. The suspicion was unfounded and the test above is what disproved it.)*

### 2.3 The panic surface is clean

102 production panic sites by raw count (`unwrap` 40, `expect` 57, `panic!` 2, `unreachable!` 3);
zero `todo!`/`unimplemented!`. After removing test-only files, ~15 are real, and I read all of them:

- `module_registry.rs:38` — `segs.last().unwrap()` guarded by `segs.len() > 2`.
- `profile_expr.rs:221` — `it.next().unwrap()` guarded by an `is_empty()` check.
- `snapshot_restore.rs:341` — `get(key).unwrap()` inside the `else` of `!contains_key(key)`.
- `transaction.rs:469` — `.err().unwrap()` inside the branch that proved the result is `Err`.
- The rest are `Regex::new` and `ProgressStyle::template` on compile-time literals.

None are data-driven. This matters more than usual because `panic = "abort"` in the release profile
means any panic is a hard abort with no unwinding — no `Drop`, no rollback.

### 2.4 The grammar refuses bad input well

A 30-case battery of malformed manifest lines (empty backends, path traversal in `use`, shell
metacharacters, command substitution, unbalanced quotes, bare control characters): **zero panics,
zero unexpected exit codes**, and the errors are genuinely good — file, line, the offending text,
and a fix:

```

  `use` takes a name. Fetch the file into `modules/` first, then `use` it by name.
```

### 2.5 Other things that check out

- **Exit codes are correct on the paths I first checked** — bare sync (1), inited sync (0), failed
  install (1), unknown backend (1), unknown verb (1). This is exactly the check that made me
  believe the exit contract was sound, and it is why B1 is in this report and not in the last one:
  every case above omits `--keep-going`, which is the flag that breaks it. A sample that only
  contains the default path proves the default path.
- **Downloads require a checksum by default**, with a per-line `@unverified` opt-out and a 2 GiB

- **`LockScope` is an exhaustive match with no `_ =>` arm**, so a new subcommand does not compile

- **Hook re-entrancy** is likewise now a property (`is_manager_hook` → `starts_with("hook-")`)
  asserted against `pm_hooks.rs`, not a widened `matches!`.

## 3. Bugs — **C**

Nine findings. Seven are wrong sentences and cost nobody a package. One is a wrong **exit code**.
One is a machine that silently stops converging, and it is why this axis is a C.

Six of the nine are the same family the repo already knows it has and is proudest of defending:
**a question that could not be answered, or an action that did not happen, is reported as though it
had.**

### B0 — an apt package Shall removed can never be reinstalled, and `list` says it is installed (CRITICAL)

`apt`'s lister, `backends/registry.rs:211-212`:

```rust
list_binary: Some("dpkg-query".into()),
list_args: vec!["-W".into(), "-f=${Package} ${Version}\\n".into()],
```

**`dpkg-query -W` has no Status filter.** It lists every package dpkg knows about, and dpkg keeps
knowing about a package after `apt remove` — the package enters `deinstall ok config-files`, which
means *the software is gone and its configuration was kept*. Shall removes with
`remove_args: ["remove", "-y"]` (`registry.rs:207`), not purge, which is the correct and safe
choice. The lister is what is wrong.

The whole chain, measured in a clean `ubuntu:24.04` container:

| step | dpkg's actual Status | what Shall says |
|---|---|---|
| declare `apt:figlet`, sync | `install ok installed` | installed — correct |
| undeclare, sync (Shall removes it) | **`deinstall ok config-files`** — not installed | — |
| `dpkg-query -W` (Shall's exact lister) | still lists `figlet 2.2.5-3` | — |
| `shall list -b apt` | package is **absent from the machine** | **`apt figlet 2.2.5-3`** |
| re-declare it, `shall check drift` | absent | nothing to do |
| re-declare it, `shall sync` | absent | **"already up to date"**, exit 0 |
| after that sync | **still absent** | — |

Three separate failures, one root:

1. **`list` states an untruth about the machine.** The flagship verb, and the exact category error
   this codebase is proudest of refusing — except this is not "could not be asked", it is a
   confident wrong answer.
2. **`check` cannot see the drift.** A package removed by hand with `apt remove` is invisible to
   the drift report, because the dpkg state is identical whether Shall or a human removed it.
3. **`sync` will not converge.** The machine does not match the manifest, Shall says it does, and
   re-running does not help — it is not eventually consistent. This is the product's one promise.

**Scope, and why this is CRITICAL rather than HIGH.** It applies to every apt package that ships a
conffile — anything with files under `/etc`, which is most of what a real machine runs: `openssh-server`,
`nginx`, `vim`, `git`, `postgresql`. `cowsay`, `sl` and `toilet` are unaffected because they have
no conffiles, so dpkg forgets them entirely on remove and they reinstall correctly. That is exactly
why §2.2's end-to-end verification passed: I picked `cowsay`.

*The fix* is the lister, not the remover: filter on status, e.g.
`-f=${db:Status-Abbrev} ${Package} ${Version}\n` keeping only `ii`, or read `${Status}` and keep
`install ok installed`.

*Family check — not done, and it should be:* every backend whose lister can report a
not-currently-installed package. `dpkg` is the sharp one, but `snap` keeps disabled revisions and
`flatpak` keeps unused runtimes. The rule to enumerate is *"does this manager have a state that is
listed but not installed, and does our lister exclude it?"* — for all 52.

### B1 — `sync --keep-going` reports SUCCESS and exits 0 when every package failed (HIGH)

Measured in a clean `ubuntu:24.04` container against real `apt`. Four cases, one variable:

| case | exit | `Status:` | reality |
|---|---|---|---|
| impossible package, **with** `--keep-going` | **0** | **SUCCESS** | nothing installed |
| impossible package, without `--keep-going` | 1 | (no summary) | correct |
| good + bad together, **with** `--keep-going` | **0** | **SUCCESS**, `Installs: 2` | `cowsay` **ABSENT** |
| all failed, `--keep-going --quiet` | **0** | — | **0 bytes printed** |

The transaction summary from case 3, verbatim, with both task lines showing a failure mark
immediately underneath the word SUCCESS:

```
=== Transaction Summary ===
Status:       SUCCESS
Time:         1.70s
Installs:     2
Removals:     0

Parallel Task Breakdown:
  ✗ [apt     ] shall-no-such-package-zzz (1683ms) (1 of 2 in one `apt` command)
  ✗ [apt     ] cowsay               (1683ms) (1 of 2 in one `apt` command)
```

There are four separate defects here and they share one root.

**The root: `Metrics::record_error` has zero callers.** It is the only writer of `Metrics.errors`
(`app/metrics.rs:116`). Nothing in the tree calls it — verified by tokenising all of `src/` and
`tests/` and counting references, not by grep. So `inner.errors` is structurally, permanently
empty, and every reader of it is dead code that cannot know it:

- `metrics.rs:183` — `Status:` is `SUCCESS` if `errors.is_empty()`, else `DEGRADED`. **`DEGRADED` is
  unreachable.** The headline line of the transaction summary is a constant.
- `metrics.rs:159-168` — the whole body of `print_summary_quiet`. Its comment reads *"Quiet mode:
  say nothing on success, but never swallow errors"*, and its doc comment promises it *"suppresses
  everything except errors"*. Since the only thing it can print is the unreachable error block,
  **`--quiet` prints nothing, ever, including when everything failed.** Measured: 0 bytes.

**Second defect: the counts are the plan, not the outcome.** `app/sync/mod.rs:749-750` calls
`record_install(changes.total_install())` unconditionally after the execution loop, with no
reference to what succeeded. `Installs: 2` means "two were planned".

**Third defect: `--keep-going` does not keep going.** Its own help says *"Finish the packages that
still can when one of them fails… the per-run opt-in for a fleet rollout that would rather take
what it can get."* In case 3 `cowsay` is installable and was not installed, because batching put
both names into one `apt install` and the bad name failed the whole command. The flag's promise and
the batching design (up to 100 packages per manager command line) contradict each other, and
batching wins silently.

**Fourth defect, and the one that cannot ship: the exit code.** Without `--keep-going`, a failed
sync exits 1. With it, the same failure exits 0. The flag's stated purpose is unattended fleet
rollout — precisely the context where the exit code is the only thing anybody reads. A GitOps
pipeline running `shall sync --keep-going` is green while installing nothing.

*Why no test caught it:* every test that drives a failing sync asserts the exit code of a run
**without** `--keep-going`, where the behaviour is correct. The flag changes the contract and no
test crosses that boundary. This is the repo's own "enumerate, do not inspect" rule owed a member:
the enumeration is *(failing sync) × (each flag that changes how failure is reported)*.

So I ran that enumeration. One package that cannot exist, every flag combination, exit code and
status line recorded:

| flags | exit | reported |
|---|---|---|
| *(none)* | 1 | — |
| `--quiet` | 1 | — |
| `--dry-run` | 0 | — (nothing was attempted; correct) |
| `--keep-going --dry-run` | 0 | — (correct) |
| **`--keep-going`** | **0** | **`Status: SUCCESS`** |
| **`--keep-going --quiet`** | **0** | **nothing — 0 bytes** |

`--keep-going` is the only variable that flips the exit code, and it flips it in both rows it
appears in outside `--dry-run`. That is the whole bug, and the matrix is the test that should
exist.

**The sibling check, because `--keep-going` is a global flag.** This report accuses the repo of
fixing one member of a family and leaving the siblings live, and the first draft of B1 tested one
verb. Every verb that can fail, with and without the flag:

| command | plain | `--keep-going` | status line |
|---|---|---|---|
| `sync` (bad package declared) | 1 | **0** | **SUCCESS** |
| `install <bad>` | 1 | 1 | — |
| `uninstall <never installed>` | 1 | 1 | — |
| `upgrade` (bad package declared) | 0 | 0 | SUCCESS |
| `rebuild` (bad package declared) | 0 | 0 | — |
| `adopt`, `update` | 0 | 0 | — |

**This narrows B1 rather than widening it:** `sync` is the only verb where the flag changes the
exit code. `install` and `uninstall` are correctly guarded in both modes.

**Two rows are inconclusive and are not a clean bill.** `upgrade` and `rebuild` exit 0 in both
columns because a declared-but-never-installed package gives them nothing to do — so the probe
never made them fail, and it says nothing about what they report when they do. `upgrade` printing
`Status: SUCCESS` over a no-op is consistent with the dead-`record_error` root reaching every
caller of the summary, not just `sync`. Constructing a genuine mid-flight failure for those two
(install a package, break it, then upgrade) is work this review did not do.

### B2 — the grammar validates only the first option on a line (MEDIUM)

The cleanest demonstration in this report, because the same text is both refused and accepted
depending only on position:

```
cargo:ripgrep@nosuchkey              → REFUSED: "`@nosuchkey` is not an option"
cargo:ripgrep@sha256=abc @nosuchkey  → ACCEPTED silently
```

`split_options` (`config/grammar/statement.rs:1138`) splits on the **first** `@` and hands the rest
to `parse_short`, which separates options on commas. An option value is never checked for
containing an `@`, so everything after a space is absorbed into the previous option's value:

```
pkg@version=1.2.3 @sha256=deadbeef   → version = "1.2.3 @sha256=deadbeef", sha256 dropped
pkg@requires=jq @hold                → hold silently inert
```

The documented form is `pkg@version=1.6,hold` — one `@`, commas between options — so the
space-separated form is user error. That is exactly the case a validator exists to catch, and
V.113's own rule ("a name is admitted by a grammar **and** a validator, and the two must agree") is
the rule being broken. The direction is mostly fail-safe: a swallowed `@sha256` makes the download
refuse for want of a checksum. A swallowed `@hold` is fail-open, but see B2 — the consumer that
matters refuses the run anyway.

*Family check:* this affects **every** key in `PACKAGE_OPTION_KEYS` in every position after the
first. The W10 table-driven option test declares one key at a time, which is precisely why it
cannot see this.

### B3 — `shall hold` reports a clean bill it cannot support (MEDIUM)

With a manifest that has one valid `@hold` line and one syntax error elsewhere:

```
$ shall hold                       # stdout
No packages are held.
$ echo $?
0
$ shall hold 2>&1 >/dev/null       # stderr
WARN the manifest could not be resolved (...), so `@hold=true` lines are not being
     honoured on this run; `shall hold` entries still are.
```

The warning is correct and well-written. The **answer** is a confident falsehood, on stdout, with
exit 0 — so anything scripting this gets "nothing is held" and no way to know better. This is
`context.rs:745`'s own rule ("Absence and unavailability are different answers and only one of them
is knowable") violated in a shipped verb.

**Contained, and I checked:** `upgrade` on the same broken manifest exits 1 and does nothing, so no
held package is actually bumped. This is a wrong sentence and a wrong exit code, not a lost pin.

### B4 — `shall check drift` can print a clean bill from questions that failed (MEDIUM)

`handle_status` (`verbs/plan.rs`), reached from `shall check` via `Section::Drift`
(`verbs/check.rs:65`). Lines `:41` and `:54`:

```rust
let resources = app.extras().changes(&state).await.unwrap_or_default();
let undeclared = app.installed_but_undeclared().await.unwrap_or_default();
```

If both yield empty the command prints *"System matches your manifests; nothing to install, no
drift, nothing undeclared."* `installed_but_undeclared` already carries the right comment twenty
lines up — *"'nothing here is unmanaged' and 'one manager never answered' both come out as an empty
list, and only one of them is a clean bill"* — and then the caller prints the clean bill.

The sharper half is in the JSON schema, and it is an asymmetry rather than an omission. Run
`shall check drift --json` and the keys are:

```
to_install  to_remove  undeclared  unverified  left_in_place
resources_to_place  resources_to_undo  resources_unverifiable
```

**`resources_unverifiable` exists. There is no packages equivalent.** The concept is modelled for
one half of the model and missing from the other — so the distinction this codebase is proudest of
survives into the machine-readable contract for resources and is lost for packages. A script
consuming that JSON cannot tell "no drift" from "three managers never answered".

### B5 — the `composer` terminator row is wrong in the unsafe direction (LOW-MEDIUM)

Not mine — CI found it, and it has been red for two nights:

```
`composer` is listed as terminating and behaves as NOT terminating.
  swallows: composer global require -- shall-no-such-thing
```

Shall believes `--` protects it, and composer ignores `--`. `PACKAGE_NAME_REGEX` is
`^[a-zA-Z0-9._@:+/-]+$`, which permits a **leading** hyphen, so `composer:--version` passes
validation and reaches composer's argv unprotected. Narrow — you need a package named like a flag —
but it is the unsafe direction, and it is the same family as the `stack` row fixed last round.

### B6 — `bisect` ships an untested copy of a well-tested function (LOW)

`app/bisect.rs:20` defines `first_bad`, a pure binary search with **five** unit tests including a
logarithmic-call-count assertion. It has **zero** production callers. The shipped search is
`search_for_culprit` at `:173`, which re-implements the same loop with an async oracle — the
comment even says *"We mirror `first_bad`"*.

So the tested code is not the shipped code, and the shipped code is untested. This is the "two of
everything" CLAUDE.md forbids, in the one file where the loop restores snapshots on a live machine.

### B7 — `sync --json` silently ignores an unmet requirement (LOW)

`sync --help` says `--json` *"Output the transition plan as JSON (requires --dry-run)"*. The
requirement is documented and not enforced:

```
$ shall -y sync --dry-run --json     → {"install": [], "remove": [], "change_count": 0}   exit 0
$ shall -y sync --json               → (no JSON, no warning, no error)                     exit 0
```

clap can express this (`requires = "dry_run"`); it is not set, so a script that forgets `--dry-run`
gets human-readable text or nothing at all, and a success code either way.

*Correction against myself:* I first recorded this as "`sync --json` does not emit JSON", having
tested it without `--dry-run` and read the human summary as the JSON output. The documented
combination works correctly and the JSON is clean. The finding is the unenforced `requires`, which
is a much smaller thing — and I would not have caught my own error if the flag had errored the way
it should.

### B8 — an empty `priority` file is silently accepted (LOW)

A **missing** `priority` gives one of the best errors in the program (names the file, the fix, and
an example). An **empty** one is accepted without comment and Shall proceeds against a default set.
Same file, adjacent state, opposite treatment.

## 4. Performance — **A**

### 4.1 The headline: Shall is not slower than metapac. It is much faster.

metapac 0.10.1, installed from crates.io. Both tools configured over the **same** backends, both
release builds, clean `ubuntu:24.04` container, hyperfine, 8 runs each:

| workload | shall | metapac | result |
|---|---|---|---|
| **real sync — installs 3 packages** | **2.987 s** ± 0.422 | 4.071 s ± 0.076 | **shall 1.36× faster** |
| converge, nothing to do (`sync`) | **18.3 ms** ± 2.8 | 1.128 s ± 0.074 | **shall 62× faster** |
| enumerate installed packages | **578.8 ms** ± 46.8 | 2.617 s ± 0.050 | **shall 4.5× faster** |
| enumerate backends | **10.0 ms** ± 0.5 | 566.5 ms ± 33.0 | **shall 56× faster** |
| process startup (`--version`) | 7.3 ms ± 0.7 | **1.6 ms** ± 0.2 | metapac 4.7× faster |

**The row that matters most is the first, and it needed three attempts to measure honestly.** A
sync that installs nothing is the easy case; a sync that does the work is the one users wait on.
Both tools were sanity-checked to actually install all three packages and exit 0 before timing —
the first two attempts produced a "metapac is 2× faster" result that was metapac failing on a TTY
confirmation prompt in 1.5 s rather than installing anything. `metapac sync` needs `--no-confirm`
under a pipe. (The 78× figure previously in this row came from the same invalid run; corrected to
62× above.)

**The reference point that makes the first row meaningful:** raw `apt-get install -y` doing the
identical work, in the same container, measured in the same batch, is **2.889 s ± 0.336**. So
Shall's total overhead over apt itself is about **98 ms on a 2.9 s operation — 3%** — while metapac
adds 1.18 s. On the verb where the package manager dominates, Shall is very close to the floor.

And Shall is doing **more** work in the enumerate row: 769 rows of output against metapac's 95,
because `shall list` enumerates everything installed while `metapac unmanaged` reports only the
explicitly installed set.

The startup row is the one metapac wins and it does not matter: 7.3 ms against 1.6 ms is 5.7 ms of
a human's life, and it buys a registry of 52 backends against 21.

The idempotent-`sync` row is the one users hit most often — most syncs have nothing to do — and
18 ms for a converge that still asks the machine is genuinely excellent.

### 4.2 The measurement I got wrong first, and why it is in here

My first head-to-head ran in WSL and said the opposite: metapac 2.6× **faster**. That result was
entirely an artifact of the environment, and finding out why produced the most useful performance
finding in this report (§4.3). The WSL numbers are:

| | WSL (inherited Windows PATH) | clean container |
|---|---|---|
| `shall list` | 10.3 s | 0.58 s |
| `metapac unmanaged` | 4.0 s | 2.62 s |

Shall degrades ~18× in that environment; metapac degrades ~1.5×. That difference is the finding.

### 4.3 P1 — backend detection is fixed-cost and `priority` does not gate it (the real finding)

`strace` syscall counts, `priority` file containing exactly one line (`apt`):

```
shall path           -> statx:   151 calls,  139 failed
shall list -b apt    -> statx: 3,188 calls, 3,156 failed
shall list           -> statx: 3,338 calls, 3,193 failed
```

**Asking about one backend costs 3,156 failed filesystem probes — 99% of what asking about all of
them costs.** `-b apt` saves nothing. `priority` saves nothing. Detection walks every PATH entry
looking for every backend's binary, before it knows or cares what you asked for.

On a normal filesystem this is invisible: the whole container run is 578 ms. It becomes the
dominant cost the moment PATH is long or slow, and there are three ordinary ways for that to
happen — WSL inheriting 56 `/mnt/c` entries over 9p (measured: `shall list -b apt` = 12.4 s wall, of
which the `dpkg-query` it actually wanted took **0.02 s**), an NFS or roaming home directory, or a
corporate machine with a large PATH.

**This is also the knob users will ask for.** The `priority` file already promises it, in its own
generated header: *"Listed = Shall uses it. Not listed = Shall does not use it at all."* That
sentence is true of querying and false of detection. Making it true of both is the fix, and it is
the difference between "52 backends" being a feature and being a tax.

*Narrower sibling found on the way:* `zfs` is probed unconditionally even with `priority = apt`, in
a container where nothing else is. Worth finding out why that one leaks.

### 4.4 P2 — the new latency gate can be satisfied by making things worse

W12 added a budget on **overlap ratio** and wave count, which was the right instinct — wall clock on
a fan-out is a fact about the host. But the ratio is `sum(child time) / wall`, and contention
inflates the numerator. Measured on the Windows host, same command, same 23 children, varying
`max_parallel`:

| max_parallel | wall | children sum | overlap |
|---|---|---|---|
| 20 | 81.2 s | 676.6 s | 8.3× |
| 8 | 92.3 s | 384.9 s | 4.2× |
| 4 | 116.2 s | 182.5 s | 1.6× |

Wall clock genuinely improves with parallelism — that part of the design is sound. But the same 23
commands take **3.7× more total CPU-seconds** at width 20 than at width 4, and the overlap ratio
*rewards* that. A regression that made every child twice as slow while holding concurrency constant
would **raise** the ratio and pass the gate.

The gate is still better than no gate; it caught a real 0.6× serialisation during this review and
said so in plain language. It should be paired with something that notices the numerator growing.

### 4.5 What I was wrong about

I predicted the fan-out was self-defeating — that firing 23 subprocesses at once inflated the
critical path enough to cost more than the overlap won. **Measured: false.** Wall clock improves
monotonically with width (116 s → 92 s → 81 s). The parallelism earns its keep. Recording it
because it was my headline suspicion going in and the numbers killed it.

## 5. Code quality — **B**

Measured on this tree rather than carried over. All counts are mine, with `#[cfg(test)]` blocks
identified by brace-matching so "production" means production.

### What is genuinely good

- **Interface segregation is real.** Eight narrow capability traits reached through
  `as_installable()` / `as_queryable()`, no fat trait full of `unimplemented!()` arms.
- **Illegal states are unrepresentable where it counts** — the `Reaped` token (§2.1).
- **Exhaustive matches with no `_ =>` escape hatch** on the two enums where a missed member costs
  something (`LockScope`, the hook property). A new subcommand does not compile until it answers.
- **The comments are unusually good**: 17,567 comment lines, 25.5% of non-test `src/`, and they
  overwhelmingly record constraints and measurements rather than narrating the code.
- **1.28:1 test-to-code ratio** (65,729 test lines against 51,229 code lines).

### What holds it at B

**`App` is a god object, and it is not close.** `app/context.rs`: **12 `pub` fields, 49 methods,
and 137 call sites taking `&App`.** No handler declares what it needs, so none can be tested
against a narrow fake and every handler test constructs the whole world. This is the one place the
design is actively anti-SOLID — the backend layer's trait work is excellent and the application
layer has no interfaces at all.

**Fifty pub functions have no production caller.** Of 1,076 `pub fn` defined in production `src/`,
**50** are referenced nowhere else in production code. Most are legitimate test doubles
(`set_response`, `with_layer`, `get_calls` — the fake executor's API, 100+ references from tests).
But **seven are referenced by nothing at all, not even a test**:

| function | file |
|---|---|
| `record_error` | `app/metrics.rs:116` |
| `new_with_executor` | `app/context.rs:138` |
| `is_supported` | `app/sandbox.rs:32` |
| `get_bin_dir` | `app/shim_manager.rs:211` |
| `rejected_by` | `backends/artifact/format.rs:327` |
| `module_blocks` | `config/grammar/mod.rs:317` |
| `is_work` | `config/grammar/statement.rs:467` |

That list is not cosmetic. **The first entry is B1** — a dead writer whose absence makes three
readers unreachable and turns the transaction summary's `Status:` line into a constant. Dead code
in a `pub` API is invisible to `cargo` (a `pub fn` in a lib is never "unused"), so nothing in the
verify chain can see this class. A scan like the one above belongs in the suite.

**Two of everything, still.** `first_bad` versus `search_for_culprit` (B6) is the clean instance:
the tested implementation and the shipped implementation are different functions. CLAUDE.md names
this as the sin that got the repo into trouble, and it is one grep away from being enforceable.

**Four files over 3,000 lines** (`registry.rs` 4,217, `grammar/statement.rs` 3,812, `generic.rs`
3,622, `executor.rs` 3,415), and modules are still organised by size rather than cohesion —
`verbs/history.rs` holds `shell`, `run`, `adopt`, `sbom`, `export`, `bundle` and `why`, none of
which is history.

**Down from B+ rather than flat** because B1 is a code-quality failure before it is a bug: a
`pub fn` that nothing calls, in a metrics type, silently disabling a status line and an entire
`--quiet` code path. The tree has no mechanism that could notice.

| backends | **52** | 21 |

This is a strict superset with room to spare, and the grade goes up from last round because the
comparison is now measured rather than sourced from a scan.

### What holds features at A− rather than A

1. **No published binary.** Still the largest missing *feature*, not just a chore: "install without
   a Rust toolchain" is on the README and does not work (§9, W1).
2. **`upgrade` covers managed packages only.** No firmware (`fwupd`), no OS release upgrade, no
   editor/shell plugin managers, no tracked git repos, no `rustup`/`gcloud` components. This is the
   one axis where topgrade does something Shall cannot, and `upgrade` is the verb where users
   expect parity.
3. **No lockfile with resolved versions and hashes.** Shall has generations, a WAL, snapshots,
   `@version` and `@sha256` — every primitive for "this machine and that machine are the same
   machine" — and nothing composes them into a machine identity. That is the rung Nix owns, and it
   is the feature that would make somebody leave metapac permanently rather than temporarily.
4. **No self-uninstall.** A tool that writes native package-manager hooks into `/etc` should be
   able to take all of them back out in one command. `reset` makes Shall forget; it does not undo.

### What holds size at B

The line counts, recounted on this tree:

| | lines |
|---|---|
| executable code in `src/` | **51,229** |
| comments in `src/` | 17,567 |
| inline `#[cfg(test)]` in `src/` | 35,522 |
| `tests/` | 30,207 |
| blank | 5,433 |
| **total `.rs`** | **139,958** |

**Two thirds of the repo is tests and comments**, which is a defence rather than an excuse for a
tool that uninstalls software. 51k of executable code for 52 managers and a real declarative model
is not padding.

The grade is B because the *surface* has not been paid for in coverage, and the numbers say so:

- **21 of 52 backends have parser fixtures.** The other 31 are argv-tested — proof that a command

- **The best real-lifecycle coverage recorded for any host class is 26 of 52** (`tools` container,

- **The job that reaches that 26 is the one job that is currently red** (§6), and has been for two

66 verbs is a very large promise for a first release. A smaller v1 — the core loop, the backends,
and fifteen verbs — would be a stronger release than this one, and the rest would lose nothing by

## 8. What this review did not cover — and why it is not finished

Stated because a report without this section is incomplete rather than clean. **This list is the
honest answer to "is the review done": it is not.**

The reason to distrust the finding count is not any single gap below. It is the rate. The worst
defect in this report (B1, HIGH) was found on the **second** pass, hours in, by a technique — scan
for `pub fn` with no production caller — that the first pass never tried. The first pass had
concluded "six findings, the worst is a wrong sentence, B+". One new technique moved a grade. When
that is still happening, the well is not dry, and the correct inference is that a third technique
would move something again.

**Safety-critical behaviour I checked structurally and never exercised:**

- **The removal guard's actual refusals.** I proved the `Reaped` token cannot be minted outside two
  call sites (§2.1) — that is the plumbing. I never tested what the guard *refuses*: `max_removals`,
  the protected set, the nine documented refusals. The most important feature in the program, and I
  verified its type signature rather than its behaviour.
- **Rollback, `heal`, and the WAL under a real `SIGKILL`.** The WAL's entire reason to exist. Read,
  never killed.
- **Two Shalls at once.** `DataLock` is central to every finding about lock scope in the last two
  rounds, and I never ran concurrent processes.
- **`--dry-run` fidelity.** I ran dry-runs; I never diffed a dry-run's plan against what the real
  run then did. "The preview matches the act" is an unverified claim.

**Surface never touched at all:** `watch`, `fleet`, `bundle`/`restore`, `try`, `snapshot`,
`bisect`, `schedule`, `service`, `firewall`, `link`/dotfiles, `setting`, both TUIs, `sandbox`,
`teleport`, `policy` enforcement. That is roughly two thirds of the 66 verbs.

**Families I named and did not enumerate:**

- **B2 (the `@` option lexer)** — I proved it for package lines. The same `split_options` shape
  plausibly affects `absent:` lines, `when` blocks and the profile set-expression grammar. Not
  checked. I flagged a family and tested one member, which is the sin this report is about.
- **B1's inconclusive rows** — `upgrade` and `rebuild` were never made to fail mid-flight (§3, B1).

**Environment limits:** 49 of 52 backends untouched by me; macOS and the full container matrix are
CI's evidence, not mine; `sudo` and the pty paths are unreachable from this host; the grammar saw
30 hand-written malformed cases and no fuzzing.

**What I would do next, in order:** drive the guard's refusals for real; `SIGKILL` a transaction
mid-flight and run `heal`; run two Shalls concurrently; diff `--dry-run` against the real run;
enumerate B2 across the other three grammars.

## 9. The work order

Ordered by what I would do first.

**W-1. Filter the apt lister on install status (B0).** The one item that blocks the release
outright, and a one-line change: `dpkg-query -W -f=${Package} ${Version}
`
(`backends/registry.rs:212`) lists `deinstall ok config-files` packages as installed, so `list`
lies, `check` sees no drift, and `sync` never converges. Use `${db:Status-Abbrev}` and keep `ii`,
or read `${Status}` and keep `install ok installed`. Do **not** "fix" this by purging on removal —
keeping conffiles is correct; the lister is what is wrong.
*Test shape:* the six-step loop from §2.2, run over a package that HAS a conffile, because the
existing coverage uses packages that do not. Table-drive it over both kinds so neither can regress.
*Family check, and it is the real work:* for each of the 52 backends, does the manager have a state
that its lister reports but which is not "installed"? `snap` keeps disabled revisions, `flatpak`
keeps unused runtimes. That enumeration is the item, not the apt line.

**W0. Make a failed sync fail, under every flag (B1).** The second item that blocks a release on
its own merits. Four changes, and the fourth is the one that makes it a family fix rather than a
patch:

1. Call `record_error` where a task fails, or delete `Metrics.errors` and the three readers that
   depend on it. Today the field exists, is never written, and silently disables both the
   `DEGRADED` status and the whole of `--quiet`.
2. Record **achieved** counts, not planned ones. `app/sync/mod.rs:749-750` passes
   `changes.total_install()` regardless of outcome.
3. Make `--keep-going` exit non-zero when anything failed. "Take what it can get" is about
   *continuing*, never about *reporting success*.
4. Decide what `--keep-going` means under batching, because today it means nothing: one bad name
   fails the whole `apt install` and takes the good packages with it. Either fall back to
   per-package commands on a batch failure, or stop promising it in the help text.

*Test shape, and this is the point:* the missing enumeration is *(a sync that fails) × (every flag
that changes how failure is reported)* — `--keep-going`, `--quiet`, `--dry-run`, `--json`. Every
existing test samples the default path only, which is why 517 tests and 426 container assertions
all passed over it.

**W1. Cut the release.** `git tag -a v0.8.0 && git push origin v0.8.0`. Still zero tags, locally and
on the remote, for the third named release in `CHANGELOG.md`. The trigger and the release job are
in place since last round; nothing else blocks this. *Verify on a machine with no Rust toolchain
that `scripts/install.sh` downloads a binary instead of falling back to a 15-minute
`cargo install`.* This is the only thing standing between this tree and a release.

**W2. Fix the `composer` terminator row (B5), and check the whole table again.** It is the unsafe
direction and the nightly has been red on it for two nights. While there: decide whether
`PACKAGE_NAME_REGEX` should admit a **leading** hyphen at all, since that is what makes the row
exploitable rather than merely wrong.

**W3. Refuse an `@` inside an option value (B2).** One check in `parse_short`, and the test that
proves it is the pair that exists today: `pkg@nosuchkey` refused, `pkg@sha256=abc @nosuchkey`
accepted. Make the option-edit test table-driven over `PACKAGE_OPTION_KEYS` **in second position**,
not just first — that is the enumeration that would have caught it.

**W4. Gate backend detection on `priority` (§4.3).** The highest-value performance item, and the
one users will ask for in their own words ("I don't have half of these — stop looking"). The
`priority` file already promises it. Today `shall list -b apt` does 3,156 failed `statx` to answer a
question about one backend. Find out why `zfs` probes unconditionally as part of the same change.

**W5. Make "could not be asked" reachable from stdout and from JSON (B3, B4).** Both verbs warn
correctly on stderr and then print a clean bill on stdout with exit 0. The JSON contract needs a
field for it; without one, the distinction this codebase is proudest of does not survive contact
with a script.

**W6. Delete `first_bad` or call it (B6).** Prefer calling it — the async oracle can be threaded
through a callback — so the five tests apply to the code that actually restores snapshots.

**W7. Enforce `--json`'s documented `requires --dry-run` (B7),** and while there, sweep every flag
whose help text names a precondition for one clap actually enforces.

**W8. Pair the overlap gate with a total-work check (§4.4).** The ratio alone rewards contention.

## 10. The one-paragraph version

This is a well-engineered codebase with a broken promise in it. The two HIGH findings from 2026-08-11 are properly fixed, and fixed
as *properties* a fourth subcommand inherits automatically. The removal guard survives independent
enumeration: two production mint sites out of thirty-three matches. The declarative loop does what
it says on a real machine for packages without conffiles. It is 1.36× to 62× faster than the tool
it competes with, on that tool's own ground, and within 3% of raw `apt` on a sync that installs.

And it will tell you a package is installed after removing it, never put it back, and report a
sync that installed nothing as a success.

That is the shape of this review. The defects are not in the hard parts — the transaction graph,
the WAL, the removal guard and the parallelism are sound, and I tried to break all four. They are
in the two places nobody instruments: the sentence printed at the end, and the exact flags passed
to a lister. A `pub fn` nobody calls made `DEGRADED` unreachable; a missing `${Status}` filter made
`list` confident and wrong. Both are one-line fixes. Neither is visible to any gate this repo owns,
which is the actual finding — the verify chain is excellent at proving the code compiles, runs and
is formatted, and has no way to notice that it is asking the wrong question.

The codebase's stated virtue is that it refuses to claim what it does not know. It holds that line
everywhere except the two places I looked hardest. Fix W-1 and W0 and this is releasable; both are
a day between them, and the family checks attached to each are the week.

# LiNix — graded by running it, 2026-08-04

> Graded at `4c647b4` on `grade/2026-07-29`, **clean tree**, against four questions: does it do
> what it says (accuracy), does it do what you think (intuitiveness), does it do what you want
> (features), does it act like Rust (speed).
>
> Hosts: Windows 11 Pro 26200 with 24 ready backends and 457 unmanaged packages — a real, used
> machine — and disposable `ubuntu:24.04` containers under Docker-in-WSL for everything
> destructive. Binaries: a clean `cargo build --release` on Windows, and the same source built
> `--release` inside `rust:latest` for Linux.
>
> Method: drive the binary as a person, not as a harness. Every number below came from a command
> run in this session. Every install was verified by asking **the package manager**, and every
> removal by asking **the filesystem** — never by asking LiNix. `docs/BUILDER.md` and the
> `GRADE-*` series were not read before testing; `docs/GRADER.md` was.
>
> Nothing was fixed. Two suspected blockers evaporated on a second look and are recorded below as
> *cleared*, because a grader who only reports the surviving half is grading their own first
> guess.

**What they cannot:** the `unmanaged` number (§3.2), the provenance line `adopt` prints to be
audited (§3.3), and `--dry-run sync` as a statement of what will happen (§3.1).

## 2. What I verified green, and is

Each of these is a command run in this session, with its real output.

**The core claim, twice, on two platforms.** `npm:figlet` on Windows and `apt:jq` in a container:
declare → `--dry-run` (machine unchanged) → `sync` → **`npm ls -g` / `dpkg -s` confirms** → binary
resolves on `PATH` → `sync` again says `already up to date` → delete the line → `sync` → **gone
from the manager and gone from the filesystem** (`ls: cannot access '/usr/bin/jq'`). The file is
the truth, and the truth propagates both ways.

**The option-drift sweep no lifecycle performs** (`GRADER` §3.5), all four steps, on `@version`:

```
npm:figlet@version=1.7.0  → sync → npm says figlet@1.7.0
                            sync → "already up to date"
npm:figlet@version=1.8.0  → sync → npm says figlet@1.8.0
                            sync → "already up to date"
npm:figlet                → sync → "already up to date", 1.8.0 left alone
```

Not "nothing happens", and not "it changed but reports a change again next time". Both halves.

**The guard, under the worst input I could build.** In a disposable container with nothing
adopted, `linix purge-unmanaged -y --allow-mass-purge` — literally the flag its own refusal tells
you to use:

```
purge-unmanaged: refusing this removal.
  - apt:apt would be removed (protected by config rule `apt`)
  - apt:bash would be removed (protected by config rule `bash`)
  - apt:bsdutils would be removed (apt reports it as essential to the system)
  - apt:dpkg would be removed (protected by config rule `dpkg`)
  - …and 25 more protected package(s)
```

Exit 3. **Zero packages removed**, 92 still installed, `bash` `ls` `dpkg` `apt` `sed` `grep` `tar`
`login` `mount` all still resolving. Note it distinguishes *protected by config rule* from *apt
reports it as essential* — two mechanisms, two sentences.

And on the real Windows machine, `sync -y` over a 307-package removal:

```
sync: refusing this removal.
  - it removes 307 packages, over the limit of 20 ([guard] max_removals)
```

`-y` does not mean "purge the system". Confirmed on live hardware.

**No essential package ever entered a plan.** Not read from a list — computed. I diffed the plan's
full 56-name removal set against `dpkg-query -W -f='${Package} ${Essential}'`:

```
==== ESSENTIAL PACKAGES IN THE REMOVAL PLAN (must be empty) ====
count: 0
==== names linix protected says YES to, that are in the plan (must be empty) ====
count: 0
```

**`--dry-run` performs nothing.** `sync`, `uninstall jq`, all mutating paths: `jq` survived every
one. And on Windows the 307-removal `--dry-run` left `npm ls -g` byte-identical.

**A pty and a pipe print the same thing.** `linix list` under `script -qec` versus under a pipe:
`diff` → **IDENTICAL**. The defect class that emptied every command's output for weeks does not
reproduce here.

**Hostile names are named refusals, not panics.** Each with `file:line`:

```
[--force]          `--force` starts with `-`, so it is an option and not a package name
[a;b]              Invalid characters in package name: a;b
[a`b]              Invalid characters in package name: a`b
[a$(id)b]          Invalid characters in package name: a$(id)b
[../../etc/passwd] Path traversal detected in name: ../../etc/passwd
[a b]              `a b` is not a package name
[BOM]              1 name parsed          ← Q22's ruling, still ruled
```

**The first hour, fixed.** All four of `GRADER` §9's *(Today: no)* items are now yes: a fresh
`sync` names `linix init` and tells you how to write the file by hand; `init` writes a starter
module; `check health` reports `24 OK, 0 degraded, 0 critical, 24 not installed` — absent is not
critical, and the rollup agrees with the detail; a typo'd `install` is rolled back out of the
config and `eval` still parses. `psresource` now probes PSResourceGet rather than PowerShell, and
hands you the install command.

**Toolchain.** `cargo clippy --all-targets --all-features -- -D warnings` — **clean**, zero
warnings, checked against raw output. `cargo test --no-fail-fast` — **exit 0**.

## 3. Findings

### 3.1 `--dry-run sync` counts what will happen and does not run the guard — **medium-high**

The preview names what is **not** happening and counts what is. Same machine, same state, same
minute:

```
$ linix --dry-run sync
Planned changes:
  install 0   remove 307   (total 307 change(s))
  backends: bun, cargo, choco, go, helm, npm, pipx, pixi, scoop, winget

$ linix plan
WARNING: `linix apply` will refuse this plan.
  - it removes 307 packages, over the limit of 20 ([guard] max_removals)
  What to do:
    linix protected <pkg>   …

$ linix sync -y
sync: refusing this removal.
  - it removes 307 packages, over the limit of 20 ([guard] max_removals)
```

Two things are wrong and they are the same thing. The preview does not say **which** 307 — a user
approving a removal cannot see what is going. And the preview does not say the run will be
**refused**, because `verbs/sync.rs:167` returns on `dry_run` before the engine's preflight at
`app/sync/mod.rs:176` ever calls `guard::enforce`.

From the code, not from the output — `verbs/sync.rs:735-772` never emits a name for an install or
a removal. It emits names for exactly one thing: `print_skipped`, the list of removals it
*declined*, capped at 10 with a comment explaining why a long list would bury the plan. The
thinking about listing happened; it landed on the wrong list.

**Family — the correct behaviour exists four times over, at the other four sites.** `--json`
names them (`"name": "figlet"`, with `source` and line number). The interactive TUI names them
(`preview.rs:134`, `Install {}:{}` / `Remove {}:{}`, one checkbox each). `rebuild` names them
(`verbs/sync.rs:405`, `batch.names().join(" ")`). `plan` warns about the guard. The one surface
that does neither is the one the readme, `init`'s closing line, and every non-interactive refusal
message point you at: *"or --dry-run to preview."*

Cleared while checking: `cleanup` is not a subcommand, so my first `--dry-run cleanup` exit-1 was
clap rejecting my typo, not a defect.

### 3.2 "unmanaged" means two different things, and the two views contradict — **medium**

Ubuntu container, immediately after `linix adopt -y`, run back to back:

```
check says:       ok  unmanaged   everything you chose is managed
check drift says: ? unmanaged — installed but not in your manifests (34):
                      apt:apt
                      apt:base-files
                      apt:bash
                      apt:coreutils
                      apt:dpkg
                      …
```

`check unmanaged` even prints the reason the other view is missing — *"33 package(s) the OS
reports as essential are left alone."* Two of the three views know about the essential exclusion.
The third does not, and it is the one that produces the alarming number. The readme (line 670)
defines `unmanaged` as *"Installed on the OS but not managed by LiNix"* — `check drift`'s
definition — which makes the rollup's cheerful `ok` the one that disagrees with the docs.

On the Windows machine the same split reads **150 versus 306**, and there it has a second cause
with a worse consequence. `adopt` skips any backend whose `tracks_manual()` is false — gem,
luarocks, nimble, pip — and that skip is deliberate and correct: `app/adopt.rs:125-131` explains
that adopting a dependency graph and then purging it costs the user their system. But the skip is
logged at `info!`, so at default verbosity it is **invisible**:

```
$ linix adopt --dry-run          # says nothing about gem, pip, luarocks, nimble
$ linix adopt --dry-run -v
 INFO adopt: backend 'gem' cannot distinguish user-chosen packages from dependencies — skipping
```

So `check` reports 156 packages as unmanaged, prints the remedy **`run linix adopt`**, and running
it will never move the number. Forever. That is the §9.3 class — rollup versus detail — fixed for
`health` and still live for `unmanaged`.

### 3.3 The provenance line `adopt` asks you to audit is wrong for 19 backends — **medium**

`manual_source()` exists for one reason, stated at `core/manager.rs:174-177`: *"An estimate whose
provenance is hidden cannot be checked… naming the command lets a reader reproduce it and
disagree."* It is printed under `check unmanaged`'s **"This is an estimate — each backend's answer
came from:"**.

The generic backends get it right, and I confirmed apt's by watching the process, not by reading
the string:

```
  apt        apt-mark showmanual
Timings:  0.02s   apt-mark showmanual        ← it really ran that
```

But **19 hand-written backends define `list_manual` and none of them override `manual_source`**,
so every one of them prints the default: *"everything this manager installed (it installs no
dependencies of its own)."* Three I could check against their code:

| backend | what it prints | what it runs |
|---|---|---|
| `emacs` | everything this manager installed (installs no dependencies of its own) | `package-selected-packages` (`emacs.rs:179`) |
| `pacman` | same | `pacman -Qe` (`pacman.rs`) |
| `dnf` | same | `dnf repoquery --userinstalled` (`dnf.rs`) |

Wrong, and wrong in the dangerous direction: it tells an Arch or Fedora user their distro's
package manager *has no dependencies* and that the list is *everything*, when the manager has a
full dependency graph and the list is a filtered subset. On this Windows box `emacs` reported 0
manual packages while 62 were installed — the string said "everything installed", the answer was
"none".

Nothing checks this, which is why it drifted: it is a hand-maintained sentence about code, in a
field whose whole job is to be checkable. The sixteen I did not read are the rest of the family:
`appimage brew btrfs conda flatpak github go mise nix psresource setting snap storage vscode web
xbps`.

### 3.4 `cargo fmt -- --check` fails at HEAD — **low-medium**

Clean tree, `4c647b4`, same stable toolchain CI resolves to (rustfmt 1.9.0 / rustc 1.96.0, no
`rustfmt.toml`, no toolchain pin, CI matrix is `rust: [stable]`):

```
$ cargo fmt -- --check
fmt exit=1
files needing format: 60
```

Real rustfmt diffs, not line endings — import ordering, e.g. `use crate::core::LockFile;` sorted
before `use crate::config::Config;` in `app/events.rs`, `app/hooks.rs`, `app/insight.rs`,
`app/sync/mod.rs`. Trivial to fix; the point is that both gates rate it fatal and it is red.

Credit where it is due: `GRADER` §2.4's asymmetry **is fixed** — `scripts/release-check.sh:39`
now rates `cargo fmt --check` HARD, matching `.github/workflows/ci.yml:77`. The gate is correct.
It is just not being run before commit.

### 3.5 An error names the wrong file — **low**

```
$ linix check
Error: Configuration error: …/cfg\active: no module named `adopted`.
  `modules/adopted.txt` does not exist. Modules on this machine: imperative, starter.
```

`cfg/active` contains one word — `Main`. The offending line is `profiles/Main:8: use adopted`. A
user opens the file the error names and finds nothing to fix. No line number either, though the
grammar tracks them everywhere else (`starter.txt:11`, `imperative.txt:6`). The repo's own rule is
that a failure names *exactly one place to look*; this names one place, and it is the wrong one.

### 3.6 The remedy block offers a flag that cannot work — **low**

Every guard refusal closes with the same four suggestions, including
`<command> --allow-mass-removal carry out this removal anyway`. After a **protection** refusal —
`apt:bash would be removed (protected by config rule bash)` — that flag does nothing, and
`linix protected` says so itself: *"the count only — it never lets a protected or essential
package through."* The block is generic and does not filter to the objections actually raised, so
it sends a user to try a flag that will produce the identical refusal.

### 3.7 Cosmetics — **low**

`search` uses fixed `{:<32}` columns and long names push the version out of alignment
(`@franco-grobler/cowsay-wasm-bundler 0.3.24` against a column of aligned rows). Every
npm-registry package appears three times — `npm`, `pnpm`, `yarn` all read one registry, so
`search cowsay` is one-third signal. And `info --help` promises *"detailed metadata and
properties"*; it works only on installed packages and returns three fields. Its refusal for the
rest is good (*"…so there is nothing to describe. `linix search bat` looks for it"*) — the help
text is what oversells.

## 4. Speed

Windows, release build, three runs each, on a machine with 24 ready backends:

| command | wall | what it is doing |
|---|---|---|
| `--version` | **48 ms** | process start and exit |
| `path` | 65 ms | + resolve config |
| `eval` | 66 ms | + parse and resolve the whole manifest |
| `protected` | 86 ms | + guard config |
| `info cargo:ripgrep` | **141 ms** | one manager, qualified |
| `info ripgrep` | 5.1 s | every manager, unqualified |
| `search cowsay` | 3.5 s | every manager, network |
| `check` | 3.3 s | 27 child commands |
| `adopt` (456 decls) | 12.2 s | full discovery crawl |
| `init` | 609 ms Win / **15 ms** Linux | 22 manager probes vs 4 |

The 200 ms fixed startup tax the previous audit measured is **gone** — 48 ms now. And `check`'s
3.3 s is not Rust:

```
Timings: 3.69s wall · 27 child command(s) summing to 21.84s · 5.9x overlap · 3 wave(s)
    0.76s    2.50s   winget list
    0.53s    2.23s   choco list
    0.70s    2.14s   scoop list
```

21.8 seconds of other people's processes compressed into 3.7 seconds of wall clock. That is the
right answer to a problem that is not yours. `--timings` is a genuinely good instrument — it
reports the overlap ratio and the number of quiet waves, which is the number you actually need to
know whether more parallelism would help.

Against `GRADER` §9's budgets: qualified `info` beats the 5 s bar by 35×. Read-only `check`
misses the 2 s bar at 3.3 s, and I would not hold that against it at 5.9× overlap — but nothing
enforces either budget, so nothing would notice if it regressed.

## 5. What I could not test, and what it would take

- **macOS.** Never run, only compiled. Needs a Mac or a runner.
- **30 of 56 backends.** Windows offered 24, Ubuntu 6. Never driven at all in this session:
  brew, pacman, dnf, apk, xbps, emerge, guix, nix, snap, flatpak, conda, uv, cabal, stack, opam,
  mix, composer, spack, mise, asdf, krew, vscode, btrfs, zfs, lvm, pkg, pkg_add, pkgin, eopkg,
  psresource. Needs the per-ecosystem container fleet `GRADER` §3.1 describes.
- **Every destructive effector.** btrfs/zfs/lvm snapshot restore, `dpkg -i`/`rpm -U` handoff, U30
  storage removal. Needs disposable VMs with real filesystems, not containers.
- **Mid-transaction `SIGKILL` → `heal`.** The WAL's entire reason to exist, untested under a real
  crash.
- **`sudo` with a real password.** On every privileged path; needs a container with a
  password-protected user and a pty.
- **Concurrency.** Two `sync` runs at once, and killing the data-lock holder.
- **A real narrow tty on Windows.** No pty available here; `COLUMNS=40` through a pipe proves
  nothing. The Linux pty run at `stty cols 40` degraded fine, so this is a gap in coverage, not a
  known defect.
- **Per-binary test counts.** The first `cargo test --no-fail-fast` completed **exit 0**. A second
  invocation, run to tally per-binary numbers, exceeded a 10-minute wall and I killed it. I do not
  claim a hang — I was building and running containers concurrently — but I did not get the
  counts, and "exit 0" is what I can stand behind.

## 6. What moves each axis up one letter

- **Accuracy B → A.** Make `check drift` use the same definition of *unmanaged* the other two
  views use, or give the two meanings two words. Make `manual_source` derivable from the command
  the backend runs, so it cannot drift — a test that quantifies over every registered backend and
  asserts the string names a binary the backend actually invokes. Then `cargo fmt`.
- **Intuitiveness B+ → A.** Name the packages in `--dry-run sync`, using the cap `print_skipped`
  already has. Run the guard in the preview. Raise the `adopt` skip from `info!` to a printed line
  and stop telling the user to run a command that cannot help them.
- **Features A− → A.** Give the five `tracks_manual = false` backends a way in — an
  `adopt --include-dependencies gem` behind an explicit flag, or a stated refusal in the docs.
  Right now those packages have no path into a manifest except by hand, and nothing says so.
- **Speed A− → A.** Nothing to fix; something to hold. Put the budgets in a gate. A 98-second
  `info` shipped once because no number was being watched, and the numbers today are good enough
  that a regression would be the only way to find out.

## 7. The one thing worth saying twice

Three of the five real findings are the same shape, and it is the shape the previous audit named:
**the correct behaviour already exists in this codebase, at a different site.** The preview that
names packages exists — in the TUI, in `--json`, in `rebuild`. The guard warning in a preview
exists — in `plan`. The essential-exclusion in an unmanaged count exists — in `check unmanaged`.
Each defect is one surface that did not get the version its siblings got.

That is not a code-quality problem. It is a *fan-out* problem, and the repo's own CLAUDE.md
already names the fix — "a bug you find is a representative of a family". The families here were
found by running the same question through four verbs and noticing that one answered differently.
That is a cheap test to automate and nothing does it: **for every fact LiNix reports, assert every
surface that reports it agrees.**

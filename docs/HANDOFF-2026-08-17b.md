# Handoff — 2026-08-17b: fifteen mutants, and the two capabilities that had one answer each

**Read `docs/SPEC.md` first.** This file is the state of play, not the map.

The previous handoff (`-17.md`) left fifteen surviving mutants and a gentoo fix that had never
run in CI. Both are answered here. Every mutant in that list is dead — twelve killed by new
tests, three deleted with the condition that generated them — and each kill was verified the way
that file says to verify one: apply the mutation to the source, run the named test, watch it
fail.

   but read the next item before believing the sweep is over.

   Dispatch **32037853435** on `e892b9b` was the first nightly to see this work, and it reported

   answered here:

   - `guard.rs:713 protected_names` — `base != name && !base.is_empty()` read as `||`. Behaviourally
     equivalent through its only caller, which runs `find_map` over the result: a duplicated
     candidate answers the same question twice and an empty one matches nothing. So it is
     asserted on the list itself. Both guards, and the `kind == Extra` test beside them, are
     unfalsifiable one level up.
   - `transaction.rs:1121 attempt > 1` read as `<`. Reversing it costs nothing in the answer — the
     run still ends `Ok`, still runs two commands, still reports one retry — because the counter
     and the loop are not what it controls. It controls whether the backoff and the manager-lock
     verdict happen at all, and the only reading of that is the clock.
   - **Two mutants that hung rather than survived**, which a shard reports as neither:
     `batches` returning one empty batch dispatches nothing for ever, and `attempt += 1` read as
     `*=` leaves the counter at nought. **A mutant that hangs hides in a shard's exit code** —
     two hours red, naming no defect.

     **Both needed the shape changed, and a `total_timeout` on the tests was the wrong fix for
     both.** It was tried first and measured failing: the 20s bound landed in `566bdfb`, and the
     shard on `d9c25a6` timed out on *both* mutants anyway. The reason is the same each time —
     `cargo mutants` runs the whole suite under `--no-fail-fast`, so the hang is in whichever
     **other** test happens to drive a transaction, and bounding the tests written for the loop
     is a race against every test written next.

     `batches` answering one empty batch spawns a task that returns immediately, which the join
     reads as progress; the loop then dispatches another, for ever. The call site now filters
     empty batches, so a pass that dispatched nothing falls through to the stall report. Verified
     against the **whole suite** rather than one test: 18s and a failure, where it used to be a
     two-hour timeout.

     **`attempt += 1` needed the loop changed, and the first attempt at it was wrong.** Bounding
     the tests that were *written for the retry loop* does nothing, because the hang is in
     whichever *other* test happens to fail an install — `cargo mutants` runs the whole suite
     under `--no-fail-fast`, so one unbounded transaction anywhere keeps the shard waiting.
     Bounding tests one at a time is a race against every test written next. So the loop is a
     `for` over `1..=max_retries + 1` now: **there is no counter for a mutation to corrupt**, and
     the two mutations the site still permits die in about a tenth of a second. The lesson is the
     stall guard's, one level up — where a mutation turns a decision into a hang, change the
     shape rather than chase the hang.

   That last one also explains `-17.md` item 2's four timeouts, and retires it.

## What this round finished

### The fourteen engine mutants, and the one fact that made most of them unreachable

Six of the fourteen read a **capability** and change the command line by its answer:
`pins_version()` at three sites, `supports_purge()` at one, and the version-strip guard's two
directions. Every one of them survived every sweep, and the reason was not fourteen oversights.
It was one property of the fixture: **`TestKernel` registers real backends, and each of them
answers each of those questions exactly one way.** A branch whose condition has one value
available in the whole suite is a branch no test can put under load.

So the plumbing that was owed is a *backend*, not another executor double —
`tests/mock_providers/recording_backend.rs`. It is registered under whatever name a test wants,
told what it can and cannot do, and it appends one line per call to a log. Several of them share
one log, which is what makes cross-manager ordering assertable at all: two mock managers with
two private logs cannot say which command ran first.

`tests/the_engine_sends_what_the_manager_can_take_tests.rs` — what the executor decides before a
manager is invoked:

- **the version strip, in all three states its guard distinguishes.** A manager that pins is sent
  `pkg-pinned@1.6`; a manager that cannot pin is sent `pkg-floating` and not `pkg-floating@1.6`
  — which is the shape of the `pkg-a@1.0` formula name that does not exist and that failed a
  rollback on a real Mac; and `@version=latest` survives on the manager that cannot pin, because
  the guard is `concrete_version` and not "is there a version key". Three assertions, four
  mutants.
- **purge, as the whole two-by-two.** The run asks or it does not; the manager offers or it does
  not; only one of the four cells purges. Either half alone reads as the same pass, which is why
  `&&` → `||` had survived: three of the four cells agree.
- **rollback's two decisions in one graph.** A removal that succeeds, an install that fails
  behind it on a second manager, and the reinstate asserted at `mock-keeper install
  pkg-keep@2.1.0`. Reversing the first decision skips the reinstate entirely; deleting the second
  reinstates at whatever is newest, so a rolled-back removal quietly loses its pin.

`tests/the_scheduler_hands_out_a_generation_at_a_time_tests.rs` — the loop's own arithmetic.
**Two mock managers, deliberately**: batching groups a ready set by manager, so two independent
nodes on one manager are one command and one task, which collapses the exact interleaving these
need. Two managers means two tasks in flight and `join_next` takes one at a time, so "something
else is still running" is a fact of the arrangement rather than a race the test hopes for.

- **a wave is not a pass.** Two independent two-node chains, one per manager. The second chain's
  root is still running when the first chain's child is handed out, and counting that as a wave
  counts the scheduler's own overlap against it. Under `||` this graph goes to at least three
  waves against a depth of two, on every interleaving.
- **a node waits for its *last* dependency.** The two roots are on different managers, so the
  child's count comes down in two separate joins. Reading either step as ready dispatches the
  child with a dependency outstanding — and then dispatches it *again* when the other lands, so
  the manager is asked to install the same package twice. Both halves are asserted.
- **a resume is measured on the work it has left.** The first run installs the root and fails on
  the child; the second run over the same transaction reports one package and one level. Nothing
  else in the suite ever calls `execute_with_telemetry` twice, which is why `total_nodes -
  completed` and `total_nodes + completed` had never differed.

### Three mutants deleted rather than killed

`else if in_progress.is_empty() && self.completed_indices.len() < total_nodes` generated three
of the fourteen, and **neither half of it can be false where it stands.** `join_next` answers
`None` for an empty `JoinSet` and for nothing else, so reaching that arm says every task ever
dispatched has been joined — and every joined result either removes its node from `in_progress`
or returns from the function. `completed < total` is the loop's own condition, and no insertion
happened on a pass that joined nothing.

So the guard could not change the outcome. What it *could* do is make the report conditional on
a fact nothing establishes: under `<` → `==` and `<` → `>` the stall goes unreported and the
loop turns for ever against a condition that will not change. It is now a plain `else`, and
`a_graph_nothing_can_start_is_refused_by_name` drives a two-node cycle into it — the first test
in this repository that has ever reached that branch.

### The lock-wait budget, extracted for the reason `backoff_for` was

`lock_waited` was a `Duration` accumulated at one call site and subtracted at another, and
reaching either needs a second package manager to hold a real lock and let go of it twice. No
hermetic test can arrange that. `LockBudget::{remaining, spend}` is the same move the last round
made on the backoff: two named operations with a test each, asserting every intermediate value —
because a budget that counts *down* from zero and a budget that never moves leave the same final
answer once it saturates.

### The guard's fifteenth, answered the way its own comment asked for

`allow_the_count`'s `before != report.objections.len()` had a paragraph above it explaining why
no test killed it: the only observable was a `warn!`, and asserting on `tracing` output from the
lib test binary is a measured race — the capture came back empty in 2 of 3 identical Linux runs.
That paragraph also said what the kill wanted: *"the announcement to be a value something reads
rather than a line something overhears"*. That is what this is.

- `GuardReport` now carries `allowed_by_flag` — the objections a mass flag answered, moved rather
  than dropped. **A report that only subtracts cannot say what it let through**: an objection
  never raised and an objection cleared leave the same empty list.
- The sentence is `announcement(&allowed, scope, noun) -> Option<String>`, so "was anything
  allowed" is a value a test reads without a subscriber.

Three assertions cover the three states that used to look alike: never raised, raised and
cleared, raised and standing. The cleared one is asserted by its **numbers** — `count: 3,
limit: 2, setting: "max_removals"` — not by a length, because a count is invariant under a
permutation and that is precisely what a comparison flip produces.

### How each of the sixteen was verified

Not "wrote a test and the suite is green". For every one: the mutation was written into the
source, one filtered `cargo test` was run, and the failure was watched. Sixteen substitutions,
sixteen `KILLED`. The script is disposable and the method is not — it costs one substitution and
one filtered run, against a nightly shard that costs two hours.

### The gentoo fix ran in CI, and the answer is not the one `-17.md` expected

`-17.md` closed by saying the gentoo fix *"has not run in CI yet"* and that the first scheduled
run after it landed was the confirmation. It did not have to wait for 03:00: `workflow_dispatch`
runs every nightly-only job, so dispatch **32027405844** on `d189f0a` asked the question the same
morning. The leg came back **red, twice over, for two unrelated reasons**, and both are worth the
paragraph.

**One: the terminator probe was right, and the floor file was stale.** `cargo` left the gentoo
image in the same change that made this leg work at all — the image now copies a prebuilt `suite`
binary out of the Ubuntu builder precisely so that it does not depend on a rolling base shipping
a toolchain. `scripts/terminator-floor.txt` still recorded `container-gentoo cargo emerge`, so
the gate reported a measurement that had gone away. Its own instruction — *restore the
measurement, or demote the row* — does not fit this case: `cargo`'s row in `src/core/argv.rs` is
measured by nine other host classes, six of them on every push, so demoting it would be false and
restoring it would put the coin-flip toolchain back. The name is deleted **with the reason and
the digests written beside it**, which is the one thing that paragraph exists to make visible in
a diff. `rc-service` and `rc-update` are ratcheted in at the same time — item 4 of `-17.md`,
taken from a full matrix run rather than from the single local measurement that item warned
against.

**Two: `emerge` cannot resolve a bare package name, and never could.** Five checks fail with
*"no package manager this line accepts has `jq`"* while `emerge --search jq` prints three
packages called jq. `Searchable::lookup` compares `p.name == name`, and emerge's parser returns
Portage's atoms. Registered as **`J8`, OPEN** — it is a design question with more than one
defensible answer, and Portage refuses the ambiguous bare name itself.

**What makes it a finding rather than a bug report is why it was invisible.** The leg scored
`pass=238 fail=0` for as long as it ran, with those five checks among the 238. Measured by
building both images on this machine and diffing the two harness runs, the only difference is one
line:

    < READY backends: appimage cargo emerge github link service web
    > READY backends: appimage emerge github link service web

**`gentoo/stage3` shipped a Rust toolchain, so the `cargo` backend was ready — and `jq` is a
crate.** The leg named for `emerge` was resolving its canary from crates.io. Removing the
toolchain removed the accidental answerer. The two halves of this round's red board are therefore
the same event seen twice: the fix that stopped an image lying about its toolchain also stopped
it lying about its package manager.

`-17.md`'s local `RESULT pass=239 fail=0` was not wrong about what it measured; it was measured
against a cached base that still had `cargo`. **A local run of a container leg names the image
digest it ran, or it is not a control.**

**Both halves were then re-asked of CI rather than assumed.** Dispatch **32037853435** on
`e892b9b`: the probe step goes from `15 passed; 1 failed` to `16 passed; 0 failed` and reports
`terminator probe: 3 binaries measured here` — the three the floor now records — and the
lifecycle step is `pass=233 fail=5` where the five are exactly the `J8` checks and nothing else.
So the leg's redness is the finding, bounded and named, rather than a leg nobody can read.

## Lessons this round paid for

- **A capability with one answer is a branch with no test.** Six mutants at four sites, one
  cause: every backend the fixture registers answers `pins_version()` and `supports_purge()` the
  same way. Look for this shape wherever a mock is *real* rather than configurable.
- **A guard that cannot be false is worse than no guard.** It survives mutation by being
  unreachable, and under two of its three mutations it converts an error into a hang — which the
  sweep reports as a timeout, i.e. as nothing.
- **Two mock managers, not one.** Batching collapses one manager's independent nodes into one
  command and one task. Every scheduling property that needs an interleaving needs a second
  backend to have one.
- **When the only observable is a log line, change the shape.** Not "add a subscriber". The
  report already existed; it simply threw away the fact it was about to announce.
- **A leg is only measuring the manager it is named for if nothing else on the image can
  answer.** `cargo` on a Gentoo image made the emerge canary green for weeks. `metacall/guix`
  measuring Debian's `apt` was the same defect, already written down, in a file three lines from
  this one — so the class was known and the instance was not. A canary wants a name **no other
  ready backend carries**, and a leg wants its READY list read at least once.
- **The nightly is not the only way to run the nightly.** `workflow_dispatch` runs every job the
  schedule runs. A confirmation that "waits for tonight" is usually a confirmation nobody
  scheduled.
- **A local container run names its image digest or it is not a control.** Two probes of the same
  `:latest` tag ninety minutes apart disagreed about whether the image had a Rust toolchain, and
  the second one only pulled because it was told to.

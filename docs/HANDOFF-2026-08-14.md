# Handoff — 2026-08-14: what an unprivileged arch image said

Picks up from `f48567e`. The round before this one made the arch integration image run its
harness as an **unprivileged user**, because that is the only condition under which `yay` and
`paru` will run at all. This round read everything that arrangement said, and it said far more
than the one defect it was pointed at.

## Where it landed

Five product defects, three harness defects, one CI gate that had never reported, and two images
that had never been run. All verified against real managers rather than argued:

| what ran | result |
|---|---|
| arch image (pacman + yay + paru, unprivileged) | `pass=395 fail=0` — from a run where 40 of 45 checks failed on two declarations |
| slackware image (slackpkg, first run anywhere) | `pass=323 fail=0` — from `322/7` |
| guix image (first run anywhere) | `pass=340 fail=0` — from `290/8`, then `328/7` |
| ubuntu image | `pass=393 fail=0` |
| host chain | build / 1853 lib + 592 suite + 22 / clippy 0 / fmt clean / `unix-check: ok` |
| shellcheck (13 scripts), actionlint | clean |

## The five product defects

**VI.6 — one package database, three clients.** `pacman`, `yay` and `paru` are three programs
over one libalpm database; `-Qe` from any of them prints the same lines. Every surface that
enumerated installed software keyed on `backend:name`, so one package was three. `adopt` turned
20 packages into 60 declarations, `uninstall jq` planned three removals, pacman took jq and the
other two were told `target not found`. `list` printed 203 packages as 609 rows; the undeclared
crawl tripled; and `uninstall --absent` wrote three **permanent** `absent:` lines, which is the
one that never recovers on its own. One table — `READS_THE_DATABASE_OF` in
`backends/capability.rs` — and three functions over it. **The claim is made before the
already-declared filter**, because filtering first is exactly what let the clients through.

**The update/upgrade lock collision.** `update` fanned out concurrently under a comment asserting
a refresh "cannot contend on a package database"; all three clients take `db.lck`. `upgrade`
partitioned sequential-vs-concurrent on `needs_root`, and the AUR helpers are where that proxy
breaks — `needs_root = false` is *correct* for them and they contend anyway.

**VI.7 — eight system managers sorted below the language managers.** `slackpkg`, `emerge`,
`eopkg`, `guix`, `macports`, `pkg`, `pkg_add`, `pkgin` were missing from `starter_order`'s SYSTEM
list and fell to the "unrecognised sorts low" branch meant for onboarder-added backends. On
Slackware, `shall install bc` became `cargo install bc`. The new gate reads `run.sh`'s own
`backend_for()`: the backend an image is driven with *is* that distro's system manager, so adding
a Solus image is what makes `eopkg` required.

**VI.8 — the lock Shall could remove, would not look at, so could not remove.** `Option<String>`
conflated *absent* with *unreadable*, and pacman's `db.lck` is mode 0000, root-owned and empty.
Wherever Shall is not root, a stale lock read as no lock: `heal` declined and the retry loop said
`Free`. Meanwhile the remover already runs `rm -f` through the **elevating** executor — the
privilege was there, the look that would authorise it was the one thing not elevated. Named the
third state: `LockFile::{Absent, Unreadable, Body}`.

**VI.9 — a `--` terminator sent to a shell script.** `argv.rs` listed `slackpkg` as terminating
under `GETOPT`, whose own text says it is *"inferred from the parser it links against"*. slackpkg
links against nothing. `slackpkg search -- bc` answers *"Ignoring extra arguments: bc"* and then
looks for `--`, exiting **0** with an empty result — so `search` returned `Ok(vec![])` and every
caller read it as *slackpkg does not carry this package*. This is the second half of VI.7 and
neither half works alone: ranking slackpkg first does nothing while it answers "not me" about a
package in its own list. `install` hid it, because it takes a *list* and drops the operand that
matched nothing.

## The three harness defects, all one shape

**A section guards a precondition and its sibling does not.** It happened three times:

- 16d asks whether the crash fixture (`pv dos2unix ncdu`) installs and softens when it does not;
  16e declares the same fixture and judges the recovery sync by its exit code without asking.
  Slackware's mirror carries none of the three.
- Section 11 softens its history checks on an image with no `git`; section 12's *"there is
  history for a rebuild to leave alone"* asserted anyway, and K14's no-commit proof **passed** by
  comparing 0 to 0 — which the comment directly above it describes as proving nothing.
- The lifecycle-gap audit could not see that a distro's own manager is lifecycled by section 5 of
  its own image; `primary_manager_image()` is the table that fixes it, and both new images needed
  a row.

**And a portability one:** `tail -c 300` with no FILE operand resolves `300` as a *filename* on
Slackware's coreutils, so six diagnostics across both harnesses printed `tail: cannot open '300'`
where the excerpt should have been — on exactly the runs where the excerpt was the only evidence.
All six now give `tail` the file and pipe into `tr`.

## The gate that had never once reported

`Mutation (the safety files, nightly)` mutates four files in one job under
`timeout-minutes: 360`, and its own comment does the arithmetic that makes that impossible —
*"one file of 125 mutants cost ~90 minutes"*. Runs `31771331606` and `31821620442` both ended
`cancelled` at six hours and sixteen seconds. **It has never produced a mutation score** while
appearing in every nightly job list as a gate that ran. It is now one job per file.

**The first completing run may be red.** Nobody has seen this gate's answer.

## Two images that existed and had never been run

`slackpkg` and `guix` are out of `UNPROVEN`; `NOWHERE_CEILING` fell 10 → 8. What each cost is
worth reading before adding an image, because neither lesson is about the manager:

- **guix installs to `/root/.guix-profile/bin` and tells you to put it on PATH yourself.** The
  canary installed correctly and was invisible, and seven checks cascaded off that one line.
- **A guix profile starts empty**, so the harness had no `git` and the removal guard had no
  protected package to refuse. Those go in at *run* time, not in a build layer: `guix install`
  builds in a sandbox that calls `personality(2)`, Docker's default seccomp blocks it, and
  `docker build` takes no `--security-opt`. Measured — the build layer failed with exactly the
  `setPersonality` error that kept this image from existing in the first place.

## Things asserted that are now measured

Two comments made empirical claims nobody had checked. Both survived, and the checking is the
point:

- `stale_lock.rs` said a `pacman` process holds the lock whichever client started it. **That list
  is what decides a lock is stale**, so a helper holding it under its own name would be a live
  lock deleted. 435 samples across `yay -Sy` and `paru -Sy`: a live `pacman` in every one.
- `yay` and `paru` were `GETOPT` guesses about a Go program and a Rust one. Both do terminate.
  `UNASKED_CEILING` 48 → 45, counting `slackpkg` — right twice and wrong once from the same
  inference.

## What is open

1. **`J2` is the owner's** — a changed `setting:` reports *"already up to date"*. Reproduced
   against the real registry; `decisions.md` has it OPEN.
2. **`J3`'s reversible half is the owner's** — where a client and the owner both hold a package,
   the owner wins the row. Written up with the alternative (attributing AUR packages to `yay` via
   `pacman -Qm`), which is a design and not a defect fix.
3. **The mutation gate's first real answer.** Sharded but never run to completion.
4. **No gate catches a row this leg used to measure going unchecked.** The probe now fails if it
   measures *nothing*, but the real regression was partial: unprivileged arch measures six of
   seven and silently drops `pacman`, whose row says `Measured` on that leg's strength. Worked
   around with `-u 0`; not gated. A gate would need to know which rows a given host owes.
5. **Dependabot** — #7 to merge, the rest to rebase, `action-gh-release` held.

## One thing to distrust in this doc

`latency_budget_tests` failed twice during this round — `shall eval` at 5.62s and `shall check
config` at 5.67s against a 5s budget — and passed on a quiet box both times it was re-run alone.
That is contention from concurrent image builds, not a regression. It is recorded because a
contention failure and a real one look identical in a log, and the message it prints says *"on an
unloaded box"* while being the one thing it cannot check.

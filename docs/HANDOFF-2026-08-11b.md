## What was found that the assessment did not name

**`@hold=true` on a manifest line was inert.** It is in `PACKAGE_OPTION_KEYS`, `validate_package`
refuses it beside `@version` as a contradiction, II.2 documents it — and the only writer of the
held set was the imperative `linix hold` command. So the declaration parsed, validated, and was
read by nothing at all. Found by W10's enumeration over the option table, which is exactly what
W10 was for: the one-at-a-time audit had done nine keys and would never have reached this one.

**And the first fix was the same mistake one size smaller.** Two readers were taught about the
declaration and a *file-level* check went green over four. `upgrade --security` copied the ledger
into a closure of its own, so it contained nothing a grep for the ledger's readers would match,
and silently remediated a package the manifest had frozen. The "holds are not enforced by a
native whole-system upgrade" note counted the ledger, so somebody whose holds were all declared
was told nothing. And `linix hold` with no arguments answered `No packages are held.` over a
manifest holding three — a read command disagreeing with the machine. The last two live in files
that already mentioned `declares_hold`, which is exactly why a check keyed on the file passed.
`app::holds::Holds` is the union now and nothing else may reach the ledger; the test is per call
site.

**`ci.yml` did not listen for tag pushes.** `on: push: branches: [main]` and nothing else, so a
`v*` tag would not have started the workflow — the release job's `if:` was gated on a ref the
workflow could never be running under. The assessment blamed the missing tag; the missing tag was
half of it. Fixed; the tag itself is still unpushed.

**A permanent sudo refusal was re-asked once per escalated command.** `SUDO_PRIMED` cached the
success and nothing cached the failure, so `update` — which deliberately continues past a failing
backend — spent the full 120-second password bound *per manager*. That is the `tools` nightly's
two 900-second wedges, which the assessment recorded as "a lifecycle failure". A 120-second bound
was working perfectly, once per backend.

**The argv terminator table was wrong about three rows, not one.** W5 named `launchctl`. The
nightly of 2026-08-11 also disagreed about `choco` and `winget` on windows-latest, and about
`stack` in the *unsafe* direction — listed as terminating, measured as swallowing the operand.
All four rows now carry the probe's own output.

**`unzip` was missing from five container images.** bun's installer needs it; `|| true` turned
`error: unzip is required to install bun` into a successful build with one manager quietly absent
from every run. The tolerance is why the dependency belongs in the package list.

## Behaviour a user would notice

Four changes are visible from outside the program. None removes a feature; each makes a
documented thing true. Flagged rather than buried, per `CLAUDE.md`.

1. **`linix watch` no longer disables the rest of the CLI.** It took the 120-second exclusive
   data lock for the life of the daemon, so the documented GitOps deployment made every writing
   command on that machine wait two minutes and then fail. It now locks per tick. `shell` and
   `run` are the same shape, one scale smaller.
2. **`@hold=true` now holds.** A declaration carrying it is skipped by `upgrade` and frozen by
   the planner, which is what II.2 has always said it does.
3. **`linix info backend:name` errors instead of denying the package** when the resolve failed —
   a `priority` that does not list the manager, a name the validator rejects. It used to print
   *"is not installed on this machine"*, a claim about the user's machine made without asking
   anybody.
4. **`--` is now passed to `winget`, `choco` and `launchctl`, and no longer to `stack`.** Four
   measured rows replacing four inferences. The `stack` change is the safety-relevant one.

## Cutting the release — what is left, and what it needs

*The work order's `W3`.*

Everything mechanical is in place. `ci.yml` now starts on a `v*` tag and the release job publishes
five named binaries; `the_review_apparatus_is_rust_tests` already asserts that the targets the
installer downloads are the ones the matrix builds.

What remains is a decision and one thing this machine cannot do:

```
git tag -a v0.8.0 -m "…" && git push origin v0.8.0
```

then, **on a machine with no Rust toolchain**, run `scripts/install.sh` and confirm it downloads
a binary rather than falling back to a fifteen-minute `cargo install`. The same for
`scripts/install.ps1`. That verification is the point of the item — the bug was never the tag, it
was that the documented install path resolved to nothing — and it needs a clean box.

Until it happens, `readme.md` says so under the install command, in a note whose last line is
*"delete this note in the commit that pushes the first `v*` tag."*

## Two numbers left deliberately loose

**`LIFECYCLE_GAP_CEILING` in `run-in-container.sh` is still 11.** Ten backends moved out of the
gap into `no_lifecycle_reason` that day, so every image's count falls — by different amounts, and
none of them measured here. The file already records what happened the last time somebody lowered
this to a number they had not measured: the `storage` job went red for a reason unrelated to
storage. The soft branch prints each image's new count; take the largest from the next full matrix
run.

**The same constant in `integration-windows.sh` was set to 0.** That one is derived rather than
measured, and stated as such in the comment: every backend the nightly named is now in one of the
two tables, so the expected count is nought. If it is wrong the nightly says so by name, which is
what the gate is for.

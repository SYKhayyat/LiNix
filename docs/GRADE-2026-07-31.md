## 5. New findings

Severity is user impact. Each carries the command, its real output, the file:line, and the sibling
sites checked — **including the ones cleared and why**.

### G-1 · `@shim` and `@sandbox` are write-once — **high**

`tests/grade6_option_edit_reaches_the_machine_tests.rs` · RED

The `Q19`/`Q20` commit landed this morning: *"a declared option that changes now changes the
machine."* It fixed seven keys. Two more in the same table, on the same `sync`, were left live —
after `Q18`'s own comment asserted *"Both are read by `sync`."*

They are read by `sync` from the **frozen state registry**, not from the manifest.

```text
$ echo 'npm:json'           > $LINIX_CONFIG_DIR/modules/starter.txt
$ linix sync -y             Installs: 1   ✓ [npm] json (21216ms)

$ echo 'npm:json@shim=true' > $LINIX_CONFIG_DIR/modules/starter.txt   # §3.5 step 2
$ linix sync -y             already up to date
$ ls ~/.local/bin | grep json                                          (nothing)

# the control — the SAME option on a FRESH install
$ npm uninstall -g json ; rm -f ~/.local/bin/json*
$ echo 'npm:json@shim=true' > $LINIX_CONFIG_DIR/modules/starter.txt
$ linix sync -y             Installs: 1
$ ls ~/.local/bin | grep json    json.exe        <-- the feature works; the EDIT does not

$ echo 'npm:json'           > $LINIX_CONFIG_DIR/modules/starter.txt   # §3.5 step 4
$ linix sync -y             already up to date
$ ls ~/.local/bin | grep json    json.exe        <-- and it cannot be withdrawn either
```

**Step 4 is the one that matters.** A shim is a stand-in on the user's `PATH`. Once declared it
cannot be taken back declaratively — the manifest stops mentioning it, `sync` says nothing to do,
and the executable stays. That is unmanaged state LiNix claims to manage, which is the exact shape
`sync` exists to prevent.

Mechanism: `spec_is_missing` (`src/app/sync/planner.rs:536`) is the whole drift check and consults
seven keys. `reconcile_all_shims` (`src/app/sync/mod.rs:594`) decides from `pkg.options` where
`pkg` comes out of the `StateRegistry`, and `StateRegistry::add` (`src/core/state.rs:195`) is that
map's only writer, called only on install.

**Family.** I enumerated every consumer of a managed package's recorded options:

| site | verdict |
|---|---|
| `sync/mod.rs:603-604` — `@sandbox`/`@shim` | **broken**, both directions |
| `verbs/plan.rs:17` — `@unverified` | **correct, cleared.** Deliberately historical: the install really did skip a verification, and editing the line later cannot un-skip it. Documented where it happens. |
| `app/run.rs:39` — `@sandbox` for `linix run` | **correct, cleared.** Resolves through `StateResolver`, so it reads the manifest, not the snapshot. |
| `app/eval.rs:101` — `@version` | cleared as cosmetic: the planner checks `@version` against the machine, so a sync still acts. |

### G-2 · a backslash in a package name is read as set math — **medium**

`tests/grade6_backslash_is_not_set_math_tests.rs` · RED

```text
$ printf 'winget:a\\b\n' > $LINIX_CONFIG_DIR/modules/starter.txt
$ linix eval
Error: Configuration error: …\modules\starter.txt:1: a module cannot use a set expression
  a module is a list of what it holds; set math is how a profile chooses between them.
```

Nothing on that line asks for set math. `looks_like_expression` fires on `\ | & (`, and
`statement.rs:509` only shields lines that open with a **statement prefix** — so `link:C:\…` and
`setting:HKCU\…` are safe and `backend:name` is not.

**This is the same bug the repo already fixed once, one line-type over.** The test
`a_prefix_whose_payload_looks_like_set_math_is_still_that_statement` was written after a Windows
registry key was handed to the expression parser. It pins `generate:` and `link:`. The plain
package line — the most common line in the language — was never covered.

Not hypothetical here: **185 of the 278 names `winget list` reports on this machine contain a
backslash** (119 `ARP\Machine\…`, 66 `MSIX\…`).

**Family checked.** A name with a *space* refuses correctly and legibly
(`` `Mozilla Firefox` is not a package name ``) — so the grammar is not simply hostile to odd
characters, it is specifically mis-classifying `\`. `generate:` and `link:` still parse. Both are
pinned as controls in the test.

### G-3 · a lifecycle's binary check passes on another manager's binary — **high (test infrastructure)**

`tests/grade6_binary_reachable_oracle_tests.rs` · RED

From the `tools` image — the widest live coverage in the repo — in one run:

```text
  PASS  cabal: hello is on PATH
  soft  go: hello already resolves to /root/.cabal/bin/hello — the removal check compares
        against that, not against absence
  PASS  go: hello is on PATH          <-- cabal's binary, scored as go's
```

The harness **computed the exact value that would have caught this.** `lifecycle()` reads
`_prepath="$(path_of "$cbin")"` before the install, announces the collision, then hands it to
`assert_binary_gone "$be" "$cbin" "$_prepath"` — and **not** to `assert_binary_reachable`, which
decides on `on_path` alone. `go: hello is on PATH` would pass if the go install had done nothing.

That is one of the three legs the **A** bar names. `CLAUDE.md` opens its "fix the whole family"
section with `assert_binary_gone` and its untouched Windows twin; this is the same pair of
functions, and the same miss, in the other direction.

**Family: 4 live call sites, both harnesses** — `integration-windows.sh:438`, `:891`;
`run-in-container.sh:444`, `:1160`.

### G-4 · the gate-parity checker compares script names; the claim is about gates — **high**

`tests/grade6_gate_parity_sees_whole_jobs_tests.rs` · RED (3 tests)

Proven by making it happen (§0.1). Two brand-new hard gates appended to `ci.yml` — a
`-Funsafe_code` build and `cargo audit --deny warnings`, neither run by any local script:

```text
$ bash scripts/harness-logic-test.sh
== every gate CI runs is also run by the local release scripts
  ok    both release scripts run all 3 gate script(s) CI runs, against the same harnesses
```

Three asymmetries are live behind that `ok` with nothing appended:

| CI | local gate | why parity cannot see it |
|---|---|---|
| `cargo test --release --no-fail-fast` | `cargo test --release` | not a `scripts/*.sh` line |
| job `storage` — btrfs/lvm/zfs on loopback, **every push** | nothing | runs `docker run` directly |
| `containers` includes `opensuse` + `void` | `DISTROS="ubuntu fedora arch alpine tools gentoo"` | matrix membership |

`--no-fail-fast` is not cosmetic — `ci.yml` carries a comment explaining that without it cargo
stops at the first failing *target* and the rest goes unmeasured. The local gate has exactly the
defect CI documented and fixed.

**Family.** `grader_gate_parity_tests.rs` (round 2's fix for the basename version) inherits the
same scope: it scans `ci.yml` for `scripts/…​.sh` and ignores every other line. Both the shell
predicate and its Rust successor share the blind spot.

### G-5 · a failed backend command pastes its whole output at the user, escapes intact — **medium**

`src/core/executor.rs:798–819`. `detail` is the entire trimmed stream, with no line cap and no
escape handling. One typo produced **~110 lines** of unrelated scoop bucket commits with raw SGR
sequences, and the sentence that mattered — `Couldn't find manifest for 'definitely-not-real-xyz123'`
— was line 4 of it.

The repo already knows: `ExitPolicy::opening()` (`src/core/exit_policy.rs:81`) strips SGR escapes
so that *detection* works, with the comment *"a manager writing to a pipe can still emit SGR
sequences — scoop's bucket update does."* The machine was protected from the escapes and the
human was not. `grep -rn "strip_ansi\|SGR" src/` finds exactly one hit, and it is that comment.

Against `READINESS` §4's rule — every failure names what failed, the thing to act on, and *exactly
one place to look* — this fails the third clause outright. No red test: the reproduction above is
verbatim and complete, and asserting on it needs a fake backend that does not exist yet.

### G-6 · `linix-failure-class:` is printed to humans — **low**

The very first command a new user runs prints:

```text
$ linix sync
linix-failure-class: permanent
Error: Configuration error: no `priority` file at …
```

`src/main.rs:266` emits it unconditionally on every failure. The contract is deliberate and good —
both harnesses read it instead of guessing by retrying — but nothing gates it on stderr being a
pipe. Internal vocabulary, first line, first run.

### G-7 · an empty fixture directory is a false coverage signal the orphan gate cannot see — **low**

`tests/fixtures/winget/` exists and contains nothing. `parser_fixture_tests.rs::every_fixture_is_read_by_some_test`
walks **files**, so a directory with no files contributes nothing and the gate is green. Its own
doc comment says *"the directory listing says fourteen backends"* — there are fifteen; the author
counted the ones with contents.

The substance behind the signal: **winget's `list` parser has no captured fixture at all**, on a
platform where it returns 278 rows of which 185 are synthetic `ARP\…`/`MSIX\…` identifiers for
software winget did not install. §2.2b, exactly: the gate verifies file reachability, and the claim
is coverage by backend.

### G-8 · `nok` scores any non-zero as "correctly refused" — **medium (test infrastructure)**

The repo's mutation gate runs one stub: a binary that exits 0. §2.1 asks for the other one. I built
it — a stub that answers `--version` and fails everything else — and ran the Windows harness:

```text
PASS survivors: 17    FAIL caught: 91
   a name repeated is refused (correctly refused)
   installing a nonexistent package fails (correctly refused)
   purge-unmanaged is refused on a machine LiNix has not adopted (correctly refused)
   reset refuses while a config repo still exists (correctly refused)
   … 12 more, all "(correctly refused)"
```

**Sixteen of the seventeen survivors are refusal checks.** `nok` (`integration-windows.sh:163`)
asserts non-zero-and-not-`never_ran` and never looks at *why*. Meanwhile LiNix has a dedicated
refusal exit — `Exit::Refused = 3` — and the harness has a `refused()` helper whose comment says
so. The most-used refusal assertion in the harness cannot tell exit 3 from exit 1, which is
precisely the distinction `E25` was about.

Credit where it is due: the harness bails loudly (`FATAL: … did not run — nothing below would be
tested`) when the binary fails even `--version`, so the naive always-fail stub is caught. It is the
second-order stub that gets through.

## 6. What I checked and cleared

Reporting these matters as much as the findings — several looked like defects and were not.

- **`info cargo:ripgrep` reporting 15.2.0, the same version pixi reports.** Both really do have
  ripgrep 15.2.0 (`cargo install --list`, `pixi global list`). Not cross-backend contamination.
  Nearly a manufactured finding of the §0.7 kind.
- **`cargo test` appearing to hang.** A child `winget list` was alive for 25 minutes while
  standalone `winget list` takes 1.3 s. It completed: 55 minutes wall, exit 0, 0 failures. Slow,
  not wedged. Reported as a fact, not a defect.
- **winget's ARP/MSIX rows reaching the manifest.** `adopt` refuses all 340 by name —
  `its manager reports a name no package line can hold` — and writes them as commented lines with
  the reason. Good defence, and it is why G-2 is medium rather than high.
- **`> 3.13.5` as a version.** That is winget's own output for `Python.Launcher`; the parser reads
  the column faithfully. Not a LiNix parser defect. (It will never satisfy a `@version=` — worth a
  line in the register, not a finding.)
- **Every `stdin` prompt.** Enumerated from the code, not from a list: 13 of 14 carry
  `is_terminal`. The one that does not is `ui/history.rs:245`, a press-enter pager that reads 0
  bytes and continues when stdin is not a terminal. Cleared.
- **The exemption lists.** All 7 exempted subcommands exist, each has a stated reason, and
  `harness-logic-test.sh:260` asserts existence. E29's class is properly closed.

## 9. The one sentence

The checks in this repo have stopped lying about *what they ran* and have not yet stopped lying
about *what they cover* — a harness that now honestly counts 25 real lifecycles still scores one of
them against another manager's binary, and a parity gate that correctly compares three scripts
still reports parity across eight jobs.

## What this round finished

### The four rulings, each shipped with its rule and its reason

**`J4` — HALF RULED. `lock` and `unlock` take a list of nine kinds, not one of three axes.**
The owner: *"i would split the things it can lock into a much more granular thing… best would be
if they can type a list of what they want locked - everything, everything minus (and list the
things they dont want) or list the things they do"*, then *"as granular as you can."*

Nine kinds in three groups (`everything`, `packages`, `scripts`), a `kind:qualifier`
sub-category below four of them, and `--except` beside the inclusion list. The same words work
on the command line and in `[lock] freeze` / `[lock] except`.

**The design argument worth keeping**, because it is what "as granular as you can" forced: the
manager scope cannot be a flag, because an exclusion is a *list* and `--except versions:cargo`
has no flag spelling; and it cannot be a bare word, because `apt:apt` is a real package on every
Debian machine, so `lock versions apt` must keep meaning the package. `--backend` was therefore
**deleted** from both verbs rather than kept beside the new grammar.

Two live bugs fell out of building it: `unlock backends:cargo` called `clear()` and would have
forgotten *every* manager's resolution; and `--list` labelled all seven approval kinds
`scripts:`, which is the conflation the vocabulary exists to undo.

**`J4`'s second half — `upgrade` no longer runs every step.** `shall upgrade curl` fired every
`@on=upgrade` step, firmware included. `@after=N` is the owner's *"only if x amount of things get
updated"*. **The judgement call to know about:** the native whole-system path reports no
per-package count, so it answers *unknown* rather than zero, and unknown runs the step. Skipping
a firmware step after the run that moves the most is the wrong direction to be wrong in.

**`J2` — ANSWERED. A `setting:` is read back.** Owner: *"yes, of course. this is a bug."* The
stated reason for not reading was that the store has no current-value command; every row in
`setting_stores.toml` carries `read`, a row whose `read` is empty is refused at load, and the
installer had been calling exactly that pair all along. `SettingBackendCore::holds` is the one
question now and both halves ask it.

**The caveat that had to ship with it:** a read counts only if it **exits clean**. That is
`probe_output`, not `run_output` — the latter deliberately keeps a non-zero reply that said
something, because *"no such package"* is a real answer from a package manager, and it hands back
`Ok("")` for a store that failed and explained itself. An empty reading compares unequal to every
value there is, so a failed read reported as drift would rewrite the key on every sync for ever.

**`J3` — ANSWERED. An AUR package is named under a manager that can put it back.** Owner: *"do
what a user would want - make it intuitive, easy, flexible and powerful."* The winner turned out
not to be a constant: pacman for a package its repositories supply, the helper for one they do
not, told apart by `pacman -Qmq` through a new defaulted `Queryable::foreign_to_repositories`.

### The family finding under `J2`, which is the transferable part

`J2` is not really about settings. **It is about the key.** A `setting:` key carries the schema
and the scope and *not the value*, so an edited `@value=` is the same key, is found in the
applied-extras ledger, and is written without ever being counted as work.

- `repo:` cannot have this bug — its subject *is* its spec, so an edited URL is a new key.
- **`schedule:` has it.** `@cron=` and `@run=` are not in its key either. It costs less there,
  because provisioning is idempotent at the OS scheduler and the machine converges, but `plan`
  still says nothing-to-do about a schedule it is about to rewrite. Closing the reporting half
  means reading a cron line back out of cron, systemd timers and `schtasks` — three adapters and
  a design, where `J2` turned out to be one function that already existed. Recorded in `V.188`
  and in the `in_effect` comment rather than left for the next person to rediscover.

While fixing it, **the control underneath it could never have fired**: `elif [ -s "$LOCKOWNER" ]`

**storage — `E: Version '255.4-1ubuntu8.16' for 'libudev1' was not found`.** The 2026-08-15
handoff called this *"a product defect of the worst kind — a machine becomes unsyncable as soon
as the archive rolls"* and guessed at the mechanism. It is not that. The cause is **three bare

A bare lock froze everything, recording the installed version of every apt package on the image;
a week later the archive dropped one and that section could never sync again. They are
`lock exec` and `lock adapters` now — `J4`'s vocabulary fixing the bug that motivated `J4`.

## 1. Verdict

**Not production ready. Three defects block it, and all three are small, localised, and have
their correct implementation already present elsewhere in this same codebase.**

That last clause is the finding behind the findings, and §9 is about it.

| dimension | grade | one-line |
|---|---|---|
| **Reliable** | **C** | The engine is right; a two-line config makes `sync`, `uninstall` and `check` all report success over a machine they did not change. |
| **Fast** | **C+** | Rust is not the problem. 200 ms of a 210 ms fixed startup tax is one eagerly-constructed clock, on every command, measured. |
| **Intuitive / consistent** | **B** | Error messages are the best thing in the repo. `lock`/`unlock` are not inverses, and "protected" behaves three different ways. |
| **Extensible / configurable** | **A−** | Custom backends work end to end, gated behind the II.12 ledger. One real gap: no `--data-dir`, so no run can be isolated. |
| **Useful** | **A−** | I could not name a package-manager feature a user would expect and not find. No `LICENSE` file. |

**What a user can rely on today:** the declarative loop (declare → plan → sync → delete line →
remove), drift detection against the real machine, the removal guard's count and OS-essential
refusals, the custom-backend mechanism, and the error messages.

**What they cannot:** anything involving `protected_packages` (**AU1**), any run they believed
`--config-dir` had isolated (**AU2**, **AU3**), or `linix path` while another LiNix holds the
data lock (**AU6**).

### What was verified green, and is

- `cargo build --all-targets` — clean.
- `cargo clippy --all-targets` — **zero warnings**, zero errors. Confirmed against the raw output,
  not a filtered summary.
- `cargo test --no-fail-fast` — **64 binaries, 1711 passed, 0 failed, 0 ignored.**
- Non-test `unwrap`/`expect`: **~48 across 88,501 lines of `src/`.** Every one was read. All are
  either guarded by a preceding check (`xbps.rs:62` re-checks `position(…is_some())`;
  `snapshot_restore.rs:310` is inside a `contains_key`) or provable invariants (regexes compiled
  from literals, `split_first` on an argv the type guarantees non-empty). **No finding here.**
  For a codebase this size that is exceptional discipline and it should be said plainly.

### One green light that was not green

`cargo test` (without `--no-fail-fast`) exited **101**, not 0 — see **AU5**. An earlier run in
this session appeared to exit 0 only because the command was piped through `tail`, which reports
its own status. That is worth recording as method: **a pipeline's exit code is the last stage's**,
and this audit made that mistake before catching it.

## 3. Reliable — *does it do what the average user expects, always?*

### AU1 — a protected package silently vanishes from the plan · **blocker**

`src/app/sync/planner.rs:430`, inside the single pass that schedules drift removals:

```rust
if self.config.is_protected(&pkg.name) {
    debug!("'{}' is protected — never scheduling removal.", key);
    continue;
}
```

`debug!` is invisible at default verbosity. The package leaves the plan and nothing says so.

**Reproduction.** In a sandbox with a custom `mytool` backend (`binary = "echo"`), package
`hello` installed and managed, and:

```toml
# preferences.toml
[guard]
protected_packages = ["hello"]
```

| command | LiNix said | what was true |
|---|---|---|
| `linix -y uninstall mytool:hello` | `already up to date`, exit **0** | **the manifest line was deleted**; the package was *not* removed |
| `linix -y sync` | `already up to date`, exit 0 | package still installed, now declared nowhere |
| `linix check` | `ok  drift  the machine matches your files` | **false** |
| `linix protected hello` | `yes — protected by config rule 'hello'` | correct — and the only surface that hints |

**Control**, to prove protection is the cause and not the presence of `preferences.toml`: with
the identical file protecting `"something-else-entirely"`, the same sequence reported
`Removals: 1` and removed the package.

**The state this leaves is permanently wedged.** The manifest does not declare the package, the
machine has it, the registry manages it, and every future `sync` will say `already up to date`
because the planner skips it again. There is no command that reports the disagreement.

**This is not a design disagreement — it is a violation of a rule this repo already wrote down.**
`docs/spec/why.md:551-557`, on the identical situation in `rebuild`:

> **Why protected packages are dropped from the scope rather than exempted in the guard.** […]
> Narrowing the scope keeps `rebuild --all` usable on a machine whose `bash` is protected while
> leaving the refusal absolute. **The skips are printed**: a rebuild that silently dropped half
> its scope would report success over a machine it never repaired, **which is the same lie
> convergence was already telling.**

`src/app/rebuild.rs:187` implements exactly that — `without_protected` pushes every dropped spec
onto `plan.skipped` with its reason, and there is a test named
`a_protected_package_is_dropped_and_reported`. The planner is the sibling that never received
the fix. The final clause of that quotation — *"the same lie convergence was already telling"* —
reads as though the convergence path was known to have this defect at the time `rebuild` was
written.

**A second, compounding inconsistency.** The planner's filter uses `Config::is_protected(name)`,
which consults only `protected_packages`. `guard::protection_of` — documented at `guard.rs:105`
as *"Everything that asks 'is this protected?' must route through here"* — additionally covers
OS-essential, undeclarable and not-a-package. The result is that one user-facing concept has
three behaviours:

| protection reason | behaviour |
|---|---|
| `protected_packages` config rule | **silent skip**, exit 0, no message ever |
| OS-essential | survives the planner, hits `guard::enforce`, **loud refusal**, exit 3 |
| the `protected` inspector | correct |

The guard's `GuardReport::message` — which builds a genuinely good refusal naming the package and
citing the rule — is unreachable from `sync` for the most common case.

**Fix.** Give the planner a `skipped` list and report it, exactly as `rebuild` does. Whether the
right answer is a refusal or a printed skip is an owner call (it touches II.10/V.26 and is
therefore out of scope for this audit to decide); **silence is not one of the options**, by the
repo's own rule.

### AU2 — a relative `--config-dir` is silently discarded, and precedence inverts · **blocker**

`linix --config-dir ./sandbox <cmd>` reads `preferences.toml` **from the sandbox** and `modules/`
**from the real repo**. Traced from the code:

1. `src/cli/args.rs:42` — `config_dir: Option<PathBuf>`, no validation.
2. `src/config/settings.rs:141` — `resolve_root` returns the flag verbatim as `RootSource::Flag`.
3. `src/main.rs:844` — `config.config_root = located.path` (the raw field), and
   `preferences.toml` is opened from `located.path.join(…)` — **so the relative path is honoured
   here.**
4. `src/config/config.rs:715` — the accessor `config_root()` returns `safe_config_dir()` for any
   path that `!is_absolute()`. `Layout` is built from the accessor, so `modules/`, `profiles/`,
   `active`, `priority` all come from the fallback.
5. `src/utils/mod.rs:31` — `safe_config_dir()` re-reads `$LINIX_CONFIG_DIR` **without an
   absoluteness check of its own.**

**Three consequences, all observed:**

- **The inspector contradicts the enforcer.** `linix --config-dir ./cfg path` printed `./cfg`
  while `linix --config-dir ./cfg init` scaffolded into `C:\Users\Administrator\AppData\Roaming\linix`.
  `guard.rs:108` warns about exactly this shape: *"an inspector that contradicts the guard is
  worse than none, because it is believed."*
- **The documented precedence inverts.** `--help` promises `--config-dir` *"Outranks
  $LINIX_CONFIG_DIR and the stored path"*. With a relative value the flag is discarded at step 4
  and the env var is picked back up at step 5 — so `$LINIX_CONFIG_DIR` **wins**. Observed:
  `LINIX_CONFIG_DIR=./cfg3 linix eval` failed naming `./cfg3\priority`, while
  `linix --config-dir ./cfg3 eval` silently used the real repo.
- **It is silent**, against P-1 *"Fail loud, never silent."*

**The fix is already written, one door over.** `src/app/locate.rs:37`, `set_root`:

```rust
if !dir.is_absolute() {
    return Err(Error::Config(format!(
        "`{}` is not an absolute path.\n  A relative path would mean a different \
         directory depending on where you ran LiNix from.", dir.display())));
}
```

`linix path --set` refuses a relative path with that message. `--config-dir` and
`$LINIX_CONFIG_DIR` do not. Validate in `resolve_root` and all three doors agree.

### AU4 — `--config-dir` does not isolate a run · high

There is **no `--data-dir` flag**. The full global flag list is `--dry-run`, `--yes`,
`--replace-existing`, `-c/--config`, `--config-dir`, `--allow-mass-removal`,
`--allow-mass-install`, `--no-progress`, `-v`, `-q`, `--no-cache`, `--timings`.
`$LINIX_DATA_DIR` is honoured by `safe_data_dir()` and used by the test fixtures, but it appears
on no help text and has no flag.

**Reproduction.** A freshly `init`-ed sandbox, absolute `--config-dir`, nothing declared:

```
$ linix --config-dir <fresh sandbox> plan
Wrote plan to linix-plan.json — 0 install(s), 7 removal(s), …
```

The seven were real entries from this machine's registry (`scoop:jq`, `choco:jq`, `pnpm:cowsay`,
`yarn:cowsay`, `pipx:cowsay`, `bun:cowsay`, `scoop:linix-nonexistent-pkg-zzq9x`). The sandbox
config was planned against the real machine's managed state.

With `LINIX_DATA_DIR` also set, the same command correctly reported
`system already matches desired state`.

Config gets a first-class flag; state gets an undocumented env var. That asymmetry is what turns
`--config-dir` from a testing affordance into a trap, and it is what made **AU2** dangerous
rather than merely wrong.

### AU5 — a load-sensitive flaky test · medium

`core::timing::tests::a_run_is_gathered_per_label_slowest_first_and_off_by_default`,
`src/core/timing.rs:275`:

```
assertion `left == right` failed
  left: "cargo install"
 right: "winget list"
```

The test sleeps 30 ms once and 5 ms twice, then asserts the 30 ms row sorts first. Windows'
timer granularity is ~15.6 ms, so under load the two "5 ms" sleeps can sum past 30 ms. It failed
once in two full-suite runs and passed 6/6 in isolation — i.e. it fails only when the rest of the
suite is loading the machine, which is precisely when a suite is normally run.

`timing.rs` is the untracked new file, so this is work in flight rather than a regression. It
still means `cargo test` on this tree is not reliably green, and the repo's own verify sequence
(`build` → `test` → `clippy`) is therefore not currently satisfiable on demand.

**Second-order:** plain `cargo test` fail-fasts, so this one lib failure abandoned the other 63
test binaries. Default the project to `--no-fail-fast`.

### AU6 — `linix path` takes the exclusive writer lock · medium

`main.rs:577`'s `READ_ONLY_COMMANDS` list omits `path`, `protected`, `policy`, `config` and
`edit`. The default is correctly the safe one (lock unless listed) and that is the right
direction — but `path` is the command documented for `cd $(linix path)`.

**Observed, not inferred:** `linix path --explain` blocked for the full 120-second
`DataLock::acquire` timeout while the test suite held the lock, then returned in **115 ms** once
the suite finished. Note also that no `linix.lock.owner` file was written by the holder, so the
diagnostic that exists to name the blocker did not name it.

## 4. Fast — *it is Rust; it has no excuse*

### AU3 — 200 ms of fixed startup on every command · **blocker**

Clean release build, quiet machine, best-of-7, `--config-dir` and `LINIX_DATA_DIR` both set:

```
--version    61 ms      (bare `cmd /c exit` baseline on this host: 59 ms)
path        272 ms
eval        272 ms
vars        277 ms
protected   276 ms
```

`--version` exits inside clap, before `load_and_merge_config` and `App::new`; it lands **at the
process-spawn baseline**, so LiNix's own start-up-to-clap cost is ~2 ms. Everything after clap
costs ~210 ms, and it is rock-solid across runs.

LiNix's own instrument agrees it is not I/O:

```
$ linix --timings path
Timings: 0.21s wall, no child commands — this run asked no package manager anything.
```

**Bisected** with temporary instrumentation: `App::new` 214 ms, of which `build_registry` is
210 ms, of which `github::register` is **200.4 ms** — repeatably, to the tenth of a millisecond.
`reg.register` was 5 µs and the reqwest client build 380 µs, so the cost was neither.

**Confirmed standalone**, outside LiNix entirely, in a scratch crate:

```
quanta::Clock::new()            200.0237ms
governor::RateLimiter::direct()      3.4µs
```

`quanta` (v0.12.6, pulled in by `governor`) performs a fixed TSC calibration on the first
`Clock::new()` in the process, and caches it globally — which is why the second construction is
microseconds, and why the cost lands on whichever call site happens to be first.

In LiNix that call site is `GithubBackendCore::new` at `backends/github.rs:152`:

```rust
let rate_limiter = if github_token.is_some() {
    RateLimiter::github_authenticated()
} else {
    RateLimiter::github()
};
```

`github::register` runs unconditionally in `create_default_registry`, which runs unconditionally
in `App::new`, which runs for every command. **Every `linix path` spends a fifth of a second
calibrating a clock for a GitHub API rate limiter it will never use** — offline, with `github`
absent from `priority`, always.

**The fix is the pattern this file's neighbours already use.** `backends/web.rs:131` and
`backends/appimage.rs:130` construct their reqwest clients *inside the function that downloads*,
and their registrations measured 2.1 µs and 5.9 µs. `github.rs` is the odd one out. Put the rate
limiter behind a `OnceCell` and startup falls to roughly 10 ms — **~25× on every invocation**.

### AU7 — the advertised overlap does not happen · medium

`app/context.rs:62-67` claims:

> `try_join!` costs nothing and takes the longest instead of the sum.

It does not, because `create_default_registry` is an `async fn` performing pure synchronous work
with no `.await` inside it. It never yields, so the other three futures in the `try_join!` cannot
be polled until it finishes. The instrumented run shows this directly:

```
PROF build_registry  210.2ms
PROF probe_snapshots   3.2ms
PROF open_journal    213.5ms
PROF load_state      213.6ms
PROF try_join TOTAL  213.6ms
```

`load_state` and `open_journal` are `spawn_blocking` file reads. They were not slow — they were
**unpolled**, and their measured duration is just `build_registry`'s. Fix **AU3** and this stops
costing anything; leave it and `try_join!` here is decoration.

### AU9 — a cap that ignores the setting · low

`app/sync/guard.rs:317` hardcodes `.buffer_unordered(8)` for the per-backend `essential()` fan-out,
which is on every removal path. Every other fan-out in the tree reads `max_parallel` or
`network_parallel`. `app/sync/planner.rs:324` states the rule verbatim:

> `max_parallel`, and a cap that ignores the setting is a cap the user cannot move.

### Not yet measurable

`linix plan` took 5.4 s and 10.2 s and tripped LiNix's own `ConfigOnly` 5 s budget warning — but
those were **debug** builds and the command genuinely queries `cargo` and `npm`. I did not
re-measure `plan` on the release binary, so I am not scoring it. The budget instrument working
and reporting on itself is a point in the design's favour either way.

Separately, `Class::ConfigOnly`'s budget being **5 seconds** for work that reads text files is a
generous ceiling for a Rust program. It is a ceiling a collapse crosses rather than a target, as
`latency.rs:23` says — but with **AU3** fixed, a much tighter number becomes defensible, and a
tighter budget is what would have caught **AU3** itself.

## 5. Intuitive & consistent

### AU8 — `lock` and `unlock` are not inverses · low, but sharp

| command | what it touches |
|---|---|
| `lock` | `locks/versions.json` + approves hooks/adapters at their current hash |
| `unlock` | `locks/bare.HOST.toml` — which *manager* an unpinned name resolved to |

Different files, unrelated jobs. A user undoing `linix lock` by typing `linix unlock` gets
backend re-resolution, and `unlock`'s own help says the consequence: *"sync uninstalls the cargo
copy, because two of the same package is what this avoids."* So the mis-paired name can cause
real package churn. Rename it (`unresolve`, `forget-backend`) or give `lock` a real inverse.

### AU11 — 61 subcommands, one flat list · low

Individually each verb is defensible and the descriptions are good. Collectively `--help` is a
wall. Grouping (`help packages`, `help state`, `help config`) costs nothing and no behaviour.

### AU10 — an empty option value is accepted · low

`cargo:ripgrep@version=` parses and yields `"version": ""` at exit 0, while `npm:` (empty name)
is correctly refused. Fail-silent on a plausible typo. The `[guard] pinned_only` check treats
empty as unpinned, so the guard does not compound it — this is a grammar nit, not a safety hole.

### The error messages are the best thing in this repo

Said without qualification:

```
starter.txt:1: `aptt` is not a backend LiNix uses
  add `aptt` to your `priority` file, or check the spelling.
  Not listed means LiNix does not use it at all.

starter.txt:1: no package name after the backend
  expected a package (`apt:curl`), one of `absent:`, `repo:`, `shim:`, … `npm:` is none of those.
```

File, line, what is wrong, what to do, and what the concept means. Exit codes match the published
contract too — 1 for config errors, 2 for a read-only command that found work, 3 for refusals.
**This audit initially misread the exit codes as broken and was wrong**; the `head` in the test
pipeline was reporting its own status.

## 6. Extensible & configurable — the strongest dimension

The custom-backend mechanism was driven end to end and behaved exactly as designed:

1. Wrote `adapters/backends.toml` defining `mytool` → **refused**, loudly:
   *"`adapters:backends.toml` (adapter definition) has never been approved. It runs code on this
   machine, and LiNix will not run what it has not seen. Review it, then run `linix lock`."*
2. `linix lock` → *"approved `adapters/backends.toml` at its current hash."*
3. `linix -y sync` → executed, `✓ [mytool] hello (38ms)`, `Status: SUCCESS`.
4. Registry recorded it with full provenance — `source: …/modules/starter.txt:1`,
   `__scopes: module:starter;profile:Main`.
5. Deleted the line → `sync` → `Removals: 1`.

The II.12 ledger covering adapter definitions (not just hooks) is the right call, and
`onboarder.rs:512` explains why in one sentence: a registered backend is reachable from `search`
and `list`, which no sync gate covers.

The schema reasoning is a cut above. From `onboarder.rs:327`:

> Every one is optional, and absent means *this backend cannot answer that* — never *the answer
> is none*. A backend that cannot list its catalogue is not one whose catalogue is empty.

Beyond that: 66 config fields across typed sections, TOML adapters for snapshot providers,
firewall, settings stores and init systems, Lua/Rhai hooks, user-defined verbs, module
parameters, generated declarations, and vars providers.

**The one real gap is AU4** — no `--data-dir`, so no run can be fully isolated from the CLI.

## 7. Useful

48 backends registered (24 live on this host per `check health`), plan/apply, snapshots,
rollback, bisect over snapshots, fleet drift over SSH, SBOM, native-manifest export
(Brewfile/requirements.txt/package.json/Aptfile), air-gapped bundles, adopt, profiles,
watch/GitOps, ephemeral `shell`/`run`, hooks that capture manual `apt install`. I could not name
a feature a user would expect from this category and not find.

`--timings` deserves specific credit: it reports overlap ratio **and** wave count, and explains
why the ratio alone misleads —

> `n` waves means the run stopped `n - 1` times to wait for an answer before it could ask the
> next question […] that is the reading everyone gets wrong.

That is better instrumentation than most shipped tools have.

## 9. The pattern behind the findings

**AU1 and AU2 are both cases where the correct behaviour already exists in this codebase, with
its reasoning written down, and the sibling site never received it.**

- **AU1**: `why.md` states *"The skips are printed"* and explains why silence would be a lie.
  `rebuild.rs` implements it, with a test whose name is
  `a_protected_package_is_dropped_and_reported`. `planner.rs` uses `debug!` and `continue`.
- **AU2**: `locate.rs:38` refuses a relative path with a message that explains exactly why one is
  wrong. `resolve_root` accepts anything.
- **AU3** is the same shape in the performance register: `web.rs` and `appimage.rs` construct
  their expensive object lazily; `github.rs` does it in the constructor.
- **AU9** is the fourth: `planner.rs` states the rule about caps in a comment; `guard.rs` hardcodes 8.

Four out of twelve findings are the same failure mode, and it is the exact one `CLAUDE.md` opens
with — *"A bug you find is a representative of a family, not a lone instance."* The discipline in
this repo is real and unusual: 1711 green tests, a clean clippy, ~48 unwraps in 88k lines, a
guard funnelled through one chokepoint, a spec that records why every rule exists. But the
mechanism catching defects is still **per-site review**, and per-site review is structurally
unable to catch a family — that is what "family" means.

The cheapest thing that would have caught three of these four is not more review. It is a
handful of *invariant* tests that quantify over sites rather than naming one:

- every code path that drops something from a plan appends to a reported list;
- every source of the config root refuses a non-absolute path;
- every fan-out cap reads a config field;
- a startup budget that fails when a no-child command exceeds it.

`tests/removal_guard_enumeration_tests.rs` and `tests/argv_drift_tests.rs` show this repo already
knows how to write that kind of test. There are four more worth writing.

## The batch shard reported, and it was red

`src/core/batch.rs`'s mutation shard was cancelled twice before it ever answered - once when its
run exhausted the clock, once by a nightly dispatched over the top of it. On the third attempt it
reported, and it found two survivors in code written that day:

```
MISSED  batch.rs:70   replace `>` with `>=` in BatchRecovery::narrows
MISSED  batch.rs:325  replace `-` with `+` in narrow_batch
```

**Neither is a crash, which is the point of running these at all.** `members > 1` becoming
`members >= 1` narrows a batch of ONE - re-asking an identical command for nothing, on the
commonest failure shape there is, since `--keep-going` produces one-package batches by design.
And `lo + (hi - lo) / 2` becoming `lo + (hi + lo) / 2` is *the same number whenever `lo` is
nought* - so every bisection test written that day missed it, because they all happened to
recurse into the LEFT half.

Both now have tests, and both tests were checked by re-applying the mutation and watching them
fail. The midpoint one panics inside `batch.rs` on an out-of-range slice, which is what the wrong
arithmetic produces the moment a recursion starts anywhere but nought.

**The general lesson, since it caught three separate things in one day:** a mutation survivor is
not usually a bug in the program. It is a branch nothing asserts, and the fix is almost always to
lift the decision into a named function and test the name.
## What the mutation shards found, which is the argument for reading them

Three survivors on the first nightly, all in that day's code:

- **`[sync] batch_recovery` could have done nothing on every machine.** Delete the field from
  `from_config` and it silently falls back to `Off`; the whole suite still passed. `continue_past`
  beside it *was* asserted in all three states, which is exactly how the gap survived review.
- **Nothing read which sentence a failed batch writes to the WAL.** Both `true` and `false` for
  the `cancelled` guard survived. A cancelled batch and a failed one are different facts to
  `heal`.

Both now have tests. The lesson generalises: **a decision buried inside a long function cannot be
asserted, so it does not get asserted.** Both fixes were the same move — lift it into a named
function and test the name.

## The method that found all of it

**Three questions per manager, not one.** An install resolves a name, an index and a version, and
a marker is safe only once all three have been asked:

1. a name that does not exist;
2. the same name under `--network none`;
3. a package that DOES exist, at an impossible version.

A backend on `capability::CANNOT_PIN_VERSION` has no third axis by construction — that is how
`nix`, `krew` and `slackpkg` are safe without one.

Question 3 is the one nobody thinks of, and it overturned an answer question 2 had just produced:
`luarocks` was given an absent marker on good evidence and had it removed again, because a real
rock at an impossible version prints the identical summary with no warning above it.

Absent-name coverage went **12 → 25 of 49**. The first pass reached 20 and was reported as
finished — it had been scoped to `builtin_backends.toml`, which is the *declarative* backends,
one table of two. **An instrument scoped to a file rather than to the thing the file describes
measures the file.** The registry is the list; `absent_marker_coverage_tests` reads it correctly.

Still uncovered and why: `guix`, `emerge`, `eopkg` need their nightly images. `yarn` answers
`https://registry.yarnpkg.com/<name>: Not found`, which puts the package name BETWEEN the two
halves that identify the sentence, so no contiguous marker matches. `conda` and `luarocks` say one
sentence for two facts. `pnpm` and `asdf` never reach a lookup on the path Shall drives.

## Working this repo without an assistant

**CI is the gate, and it is enough.** The repo is public, so Actions is free and unmetered. Every
push: build/test/clippy/fmt on three platforms, MSRV, newest-Rust advisory, shellcheck,
advisories and licences, seven cross-build targets, seven integration images. The nightly runs on
a schedule — `tools`, gentoo, guix, slackware, macOS, Windows, both install scripts, argv drift on
three OSes, thirteen `cargo mutants` shards and the harness-mutation check. Nobody has to
press anything.

**Reading it.** `gh` is installed nowhere on this machine and GitHub is reachable only from WSL.
The recipe that works:

```sh
# token
printf 'protocol=https\nhost=github.com\n\n' | git credential fill | sed -n 's/^password=//p'
# then, from WSL
curl -sS -H "Authorization: Bearer $TOK" \
  https://api.github.com/repos/SYKhayyat/Shall/actions/runs?per_page=10
```

**Read the JOBS, not the run.** A run's own conclusion lags badly; `.../runs/<id>/jobs` answers
while it is still going, and `head_sha` in the runs query needs the FULL forty-character sha —
a short one silently returns nothing.

**Do not push or dispatch twice.** `cancel-in-progress` is true for push, PR and
`workflow_dispatch`. A second push cancels the first run; a dispatch cancels a running dispatch.
That is how the `batch.rs` shard was lost. **Cancelled is not red, and it is not green.**

**Docker is the second instrument, and it answers a different question.** CI says *that*
something is red; a container says *why*. It settled the cabal root cause in four minutes when
reasoning could not, and proved a one-line harness fix in ninety seconds against a forty-minute
nightly on a broken `main`. Docker lives INSIDE WSL here — `/usr/bin/docker`, no Docker Desktop —
so its absence from the Windows PATH means nothing. `scripts/docker-restore.sh` rebuilds the
images if they have been cleared; `--check` says what is missing and changes nothing.

## Traps that cost real time on 2026-08-21

- **Two `cargo` invocations contend on the target lock.** Running two verify chains at once
  produced `LNK1104` and `failed to remove shall.exe` — two meaningless failures.
- **Two background edits to one file lose updates.** An extraction reported as applied simply was
  not in the file, because a later script had read it before the earlier one wrote. Verify an
  edit by grepping the result, not by the script's own success line.
- **`set -u` and a variable assigned on the failure path.** `LIFELOG` was set inside
  `classify_install`, which runs only when an install FAILS, and read on every path. Twelve
  integration jobs, every image. `harness-logic-test.sh` could not catch it — it *lifts*
  `classify_install` and tests it in isolation, where the variable is always assigned — and
  shellcheck sees it assigned somewhere in the file and says nothing. **Two green gates, neither
  capable of the finding.** One `docker run` of the harness would have caught it in ninety
  seconds. Point the harness at harness changes.
- **The transport eats backslashes.** Writing Rust or shell through a heredoc mangles `\` and
  line continuations; `cargo fmt` then collapses what survives. Build them with `chr(92)` or edit
  by line range, and re-read the file.
- **A profile's NAME is its filename.** `active` holds `Work.txt`, not `Work`. The error lists
  the filenames it will accept, which reads like a contradiction until you notice that.

## The last red, and why it was ours (VI.11)

Run #289 had one failing job out of twenty-seven: `Integration (storage)`, on this line —

```
FAIL  github: install of github:sharkdp/fd failed twice, unclassified
      - [github:sharkdp/fd]: API rate limit: api.github.com is rate limiting this machine
        and does not reset for 526s, past the 30s ceiling.
      shall-failure-class: unknown
```

Two independent defects meeting, and the first reading of it is wrong in both directions.

**It is not ecosystem variance, and it is not a missing `ExitPolicy`.** `Error::RateLimit` has
been classified `Transient` since classification existed, and the `github` backend raised exactly
that. The verdict was computed correctly and then **discarded by M2's own code**: with carrying on
now the default, the error a partial run raises at the end is a summary, and that summary was
built with `Error::command_failed` — the constructor whose entire meaning is *nobody looked*. So a
run in which every failure was named reported `unknown`, the harness retried it as a possible
defect, met the same rate limit, and failed the job.

The general lesson is the one M1 started and this extends by a layer: **a classification is worth
nothing at the point it is computed. It is worth something at the point it is read** — and the
only thing that reads it is the top-level error. Two more places were destroying it there, both
found by asking "what else wraps an error?":

- appending the pin advice — `Error::Transaction(format!("{}{}", e, advice))` — re-classified
  every failure it fired on, which are precisely the `Permanent` ones;
- `heal`'s "N interrupted operation(s) could not be recovered" was an `Error::Other`, the same
  aggregate as `sync`'s and unclassified the same way.

`Error::with_note` is the fix for the first and preserves the *variant*, not just the class:
`Refused` carries exit code 3 and `Differences` carries 2.

**The other half is CI's and was never Shall's.** api.github.com allows 60 requests an hour
unauthenticated, by IP, and an Actions runner shares its IP with the whole pool. Shall's own error
says what to do — "set `GITHUB_TOKEN` for a far larger allowance" — and not one harness container
had been given one. All four `docker run` sites now pass it, and the three jobs declare
`permissions: contents: read` so the token they hand to a container full of third-party package
managers is the least one that still counts as authenticated.

**The test took three attempts, and the first two were green against the broken build.** Both
failed for reasons worth knowing: a `web:` URL over plain HTTP is *refused*, and a refusal exits
before the class line is printed at all, so there was nothing to compare; adding `@allow_http` to
get past that produced a line the grammar rejects, so `sync` had nothing to do and exited 0. The
working probe is the one `a_failing_command_names_its_failure_class` already uses. **Run every
new test against the broken build before trusting it** — the discipline is cheap (`git` a
one-line revert, run the one test, restore) and it caught two useless tests in a row here.

**M4 came out of this and was ruled the same day.** `--keep-going` raises a summary over what it
carried past, and a summary was a `CommandFailed` whatever its members were — so the same refused
declaration exited **3** without the flag and **1** with it, and a fleet script retrying exit 1
would retry a refusal for ever. Raised as an OPEN decision because it changes an exit code; the
owner delegated the call the same session. **A run whose every member was refused is a refusal
and keeps exit 3**; one genuine failure among them and it stays 1, because something did fail.
`sync` and `heal` now share one `summarise` for both facts the summary carries.

**If this recurs:** the class line is the diagnostic. `shall-failure-class: unknown` on a failure
whose text plainly names a cause means something between the failure and the exit re-wrapped it.
Grep for `Error::Transaction(format!` and `Error::Other(format!` taking an existing `Error`.

## The one red dependabot PR, and why it was our code

Four of the five open bumps (petgraph 0.8, tera 2.1, governor 0.10, dashmap 6.2) are green across
the whole matrix. **#13, sha2 0.11, failed every job** — sixteen of them, builds and MSRV and
integration alike. A failure that uniform is a compile error, not a flake, and it was ours.

The first guess was the MSRV, because sha2 0.11 moved to edition 2024 and Rust 1.85. That guess
is wrong: this crate already declares `rust-version = "1.89"`. The real cause is two lines that
used APIs sha2 0.11 takes away, out of four call sites in the tree:

- `src/core/security.rs` streamed a file into the hasher with `io::copy`, which needs the hasher
  to implement `io::Write`. That impl came from digest's `std` feature, **removed in 0.11**.
- `src/backends/web.rs` rendered a digest with `format!("{:x}", …)`, which needs `LowerHex` on
  the array the digest returns. 0.11 returns a different array type, from `hybrid-array`, which
  does not implement it.

The other two call sites already used `hex::encode`, which takes `AsRef<[u8]>` and does not care
which array it is handed.

**Both are fixed here without bumping anything**, because both replacements compile against 0.10
and 0.11 alike: a hand-fed read loop, and `hex::encode`. Nothing about the dependency changed —
the code simply stopped depending on the parts of it that are going away. Dependabot rebases an
open PR when its base moves, so #13 should go green on its own next run; if it does not, the
remaining error is a *new* one and worth reading rather than assuming.

Worth keeping as a shape: **a dependency PR that fails everything is usually one or two lines of
your own code, and the fix usually belongs on main rather than in the PR.**

## A pattern worth carrying forward: the dependency nothing calls

Two instances found in one evening, both by asking the same question — *what does this dependency
do, and does any test watch it do it?*

- **`tera`.** `@template=true` is the only mode that runs it, and its one test asserted the mode
  *reads its source*, never that the source comes out rendered. So `tera 1 -> 2` — a major version
  of a template language — passed build, clippy and 2,695 tests without anything calling the
  function.
- **`governor`.** `src/core/ratelimiter.rs` wrapped it in 117 lines with **zero tests**, and this
  session took the crate from 0.6 to 0.10. Four majors, on the component that governs the very
  backend whose rate limit started the day.

Both are now covered, and the rate-limiter tests are worth reading as a shape: the ones that
matter are **mutually constraining**. `the_permit_after_the_burst_does_not_arrive_at_once` fails
on a build that limits nothing; `a_generous_quota_issues_its_burst_without_waiting` fails on a
build that blocks everything. Either alone is satisfiable by a broken limiter. And they assert in
hundreds of milliseconds rather than waiting a minute for a permit, by proving the *absence* of a
permit with a timeout.

They also write down promises that were only ever comments. The field doc on `inner` says a
per-clone cell "would silently double every limit here" — *silently* being exactly why that
belongs in a test rather than a sentence.

**How to look for more.** `Cargo.toml` lists 46 direct dependencies. For each, `grep -rln` the
crate name across `src/`; a crate used in one file, whose behaviour is the reason it exists
(parsers, engines, limiters, archive formats), and whose file has no `mod tests` — that is the
next one.

**Two candidates checked and cleared, so nobody repeats the search.** The six archive crates
(`tar`, `zip`, `flate2`, `bzip2`, `xz2`, `zstd`) all funnel through `src/utils/archive.rs`, and
`every_offered_archive_actually_round_trips` already builds and extracts **all eight** offered
extensions — `.tar.zst` and `.txz` included, which is the `F-7` bug it was written for. That is
the family rule applied properly, and it is the model for what the other files should look like.
`src/core/rhai_stdlib.rs` has two tests over 259 lines, which is thin rather than absent; worth a
look, not an alarm.

## The nightly paid for itself the same evening (`VI.12`)

Run #295 came back with one red job — `Mutation (the batch narrowing)` — reporting two survivors
in `narrow_batch`. Both were real, and neither was what the line numbers suggested.

**`batch.rs:325`, `if hi - lo == 1`** — unreachable. `work` starts at `(0, n)` with `n > 1`
guaranteed by `narrows`, and the arm that would push a one-member range answers it directly
instead, so every range popped has at least two members. An equivalent mutant is what dead code
looks like from the outside. Deleted.

**`batch.rs:278`, `&names[p..p + 1]`** — a genuine test gap, and pulling it uncovered a panic.
`run_one_command` hands `specs` to `install` and `names` to `remove`; every narrowing test in the
repo drives installs, so that slice had never been read. Writing the first removal-narrowing test
ran the code, and the code panicked: a removal carries no specs, and the per-member path clamped
only the end of its `specs` slice, so `specs[p..0]` had a start past its end. `shall sync`
narrowing two or more removals took out its own worker. Full write-up in `VI.12`.

**The chain is the point.** Shard red → mutant on an unread slice → unread because a whole
*direction* of the feature was untested → writing that test found a panic. No single instrument
in this repo finds that alone, and reading the code certainly does not: the correct version of
the same slice sits four lines away.

**A note on my own instruments, since three of them lied today.** Two drafts of the
class-survives-carry-on test and one of the `M4` exit-code test were green against deliberately
broken builds. The first draft of the removal test failed for a reason that was mine rather than
the code's — the mock returned `Permanent`, and `M3` does not narrow a permanent failure. Every
one of those was caught by running the test against a build known to be wrong. **That habit is
the cheapest thing in this document and it caught four useless tests in one session.**

**And one more instrument earned its place on the way out.** The removal test above was written
through a Python heredoc, whose `\` at end of line is a *Python* continuation — so it ate the
Rust string continuations before the file was ever written, and the assertion message reached
the source with twenty spaces in the middle of a sentence. `cargo fmt` was happy, `clippy` was
happy, and `a_wrapped_string_literal_does_not_print_its_own_indentation` failed the run and named
the file and line. That gate exists to "stop the thirty-ninth"; this was the thirty-ninth, and it
was written by the person who had the trap recorded in their own notes. Write Rust string
literals through a bash heredoc or by line range, never through an interpolating Python string.

## The dependency audit, and where it got to

One question, asked of each of the 46 direct dependencies: **what does this crate do, and does
any test watch it do it?** Five files examined, **four real gaps**, two already covered. That
hit rate is the finding — not any individual test.

| crate | file | before | after |
|---|---|---|---|
| `tera` | `backends/link.rs` | rendering never called | 2 tests |
| `governor` | `core/ratelimiter.rs` | **no tests at all** | 7 tests |
| `rhai` | `core/rhai_stdlib.rs` | 16 builtins, 2 tests, both on one of them | 7 tests |
| six archive crates | `utils/archive.rs` | already round-trips all 8 extensions | clean |
| `semver` + `version-compare` | `app/sync/resolver.rs` | `satisfies_constraint` named by no test | 2 tests |
| `cron` | `model/schedule.rs` | 18 tests already | clean |

`rhai_stdlib` is the one worth explaining. It registers sixteen functions, and what they return
becomes a resolved variable — which decides which packages get declared. The converter behind
`parse_json` is a six-arm recursion trying `as_i64` before `as_f64`; invert that order and `1`
becomes `1.0`, so every script comparing a count or an index against an integer silently stops
matching. Nothing watched it. `env`'s two arities differ only for a name that is **not set**,
which is exactly the case `W7` uses it for.

`satisfies_constraint` is the one to understand. It decides whether a version pin is already
met — so it decides whether `sync` reinstalls — and its name appeared in no test, only at its one
call site. Three tiers: a SemVer range, then literal equality, then a loose compare, the fallbacks
existing because managers ship versions SemVer cannot parse (Debian epochs, distro suffixes,
four-part numbers). The second test is the one that matters: **a constraint nothing can read must
not be treated as met**, because reinstalling a package that was already right costs one command
while skipping one that was wrong leaves the machine disagreeing with the config, silently.

**Still unexamined**: `mlua`, `dialoguer`, `indicatif`, `ratatui`, `reqwest`, `walkdir`, `which`.
About twenty minutes per crate, and it has found something in four of the six tried.

**Three of my own documented traps bit me while doing this**, which is its own finding: an
unauthenticated API poller that died on the very rate limit this session was about, a Python
heredoc that ate Rust string continuations, and `/tmp` meaning two different directories to
git-bash and Windows python. All three were already written down. Having them written down did
not stop me; the gates caught all three. That is the argument for the gates, not for the notes.

**One of those detours improved the code.** Rather than escape a Windows path twice — once for
Rust and once for Rhai — `path_exists_answers_about_the_filesystem` binds the path as a scope
variable and interpolates nothing. Prefer that shape for any test that hands a path to a script.

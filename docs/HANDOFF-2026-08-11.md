# Handoff — 2026-08-11, the session that reproduced S87

One bug, one ruling, and three siblings — but the part worth reading first is **how the register
was wrong about it**, because the wrong account is what made it look unsolvable for two sessions.

`S87` was recorded as intermittent, "two data points still don't settle it". There was no race.
There is a durability mismatch between two files that must agree, and it reproduces on demand
once you kill the run at the right moment. The old account of the field log had the two halves
exactly backwards, and reasoning from it could only ever produce contradictions.

## The bug, in one paragraph

The write-ahead log is written **per operation**, before and after each one. The ownership
registry (`registry.json`) is written **once, at the end of a run, and only when the whole
transaction succeeded**. A run killed between an install's `Completed` line and that final write
therefore leaves the package installed, closed in the log, and owned by nobody. Nothing
downstream notices, because every mechanism that could is looking elsewhere: the next sync
converges (the package *is* installed), the preview plans nothing (there is nothing to plan),
and `heal` has nothing to replay (the entry is terminal). Ownership is consulted at exactly one
moment — when something tries to remove the package — and the answer then is a command that
plans no change, prints `already up to date`, and exits 0 with the binary still on PATH.

## What the register said, and why it could not be reasoned from

The entry read: *"the two that refused to uninstall were exactly the two `heal` recovered"*, and
inferred from `SIGKILL left 2 newly-opened operation(s)` that one canary had completed normally.

Both halves are wrong.

- `_opened` is a **delta** — `_open_at_kill - _open_before`. The harness's own comment says so.
  It is not a count of how many entries are open, and it says nothing about how many `heal` then
  recovered.
- The packages `heal` recovers come back **owned**, because recovery records ownership (that was
  fixed once already, and the fix works). The orphans are the packages `heal` never looks at,
  precisely because their entries were already closed.

Every theory built on the old reading required "recovery sometimes forgets to record", which the
local rerun disproved — recovery recorded correctly for all three. Hence "two data points that
don't settle it". They settle it fine once the log is read correctly.

## How to reproduce it (and why the harness could not)

Both existing crash iterations poll the **filesystem**: `open` kills as the log opens an entry,
`midway` once a canary reaches disk. A canary reaches disk well before its entry closes, so both
always kill too early. **Twelve iterations across four rounds produced the failure zero times.**

Polling the **log** for a newly-*closed* operation produced it on the first attempt:

```
kill: sync still running=yes, open=1 done=2
[after kill]  on-disk=3/3  open=1  owned:(none)
[after heal]  on-disk=3/3  open=0  owned: ncdu
why xbps:pv          -> 'xbps:pv' is not under LiNix management.
uninstall pv rc=0    -> STILL ON PATH | already up to date
```

Two rounds later the same kill landed a tenth of a second after the process had exited — registry
written, all three removable. That is the whole of the intermittency.

Both harnesses now carry that iteration (`crash_run completed completed`), measured by what the
kill **closed** rather than what it left open — the state it aims at is one where nothing is
open at all, so the old `_opened < 1` guard would have skipped it every time it worked.

**The fix, half one — the registry is a view of the log.** `SyncEngine::reconcile_ownership`
takes back every install the log completed that the registry does not carry and the manager still
holds. Three limits are load-bearing:

- A completed **removal cancels** an earlier install, and a tie cancels it too. The entries are a
  map keyed by id, so two transitions in the same second have no order between them; the safe
  direction is to claim nothing.
- A manager that **cannot be asked** leaves its packages unclaimed. The opposite default turns
  one manager having a bad day into a registry full of packages the machine does not have, each
  of which the next sync tries to remove.
- A **preview claims nothing**.

It is called from `heal`, and `heal` is now called from `reconcile` **whether or not anything is
interrupted**. `needs_recovery` asks about entries that are still open; the records lost here
belong to entries the log already calls `Completed`, and gating on that predicate is exactly why
one orphan survived a converge sync, an idempotence sync and three uninstalls.

**The fix, half two — `Q54`.** `uninstall` fails when it ends with a package it named still
installed and no record of installing it. Asked only of names the registry did not carry when the
command started, so an ordinary removal asks no manager anything; a bare name any manager already
owns is settled from the registry alone. The preview says the same thing.

## The three siblings, one of which was mine

1. **A failed transaction never reached the final write either.** Without `--keep-going` a
   failure aborts and `if result.is_ok()` skips the registry write entirely — so successful
   installs in a failed sync were orphaned with no crash involved. The log-replay repair covers
   it; no separate change was needed.
2. **`--keep-going` recorded ownership for installs that failed.** The loop iterated
   `changes.graph.node_indices()` and recorded every node, consulting no outcome. Now nodes the
   engine reported an outright failure for are skipped. **A node the engine reported *nothing*
   about is deliberately still recorded** — silence is not evidence of failure, and treating it
   as one would recreate `S87` in a new place.
3. **The repair would have undone `linix unmanage`.** That verb drops the registry entry and the
   manifest line and leaves the package installed — which, from the registry alone, is
   indistinguishable from an ownership record a killed run never wrote. The next sync would have
   taken the package back, found it declared nowhere, and removed software the user had asked
   LiNix only to stop watching. `unmanage` now clears the package's **finished** log entries too
   (`Journal::forget`), because the log is the third record of the same relationship.
   `InProgress` and `Abandoned` entries survive it: a package being forgotten is not a reason to
   lose the evidence that its install never completed.

## Things worth knowing before you touch these files

- **`Journal::completed_installs` is the whole contract of half one.** If you add a
  `JournalAction` variant, decide there whether it can own a package. Scripts (`Exec`,
  `ExecUndo`) cannot, and there is a test that says so.
- **The reclaim window is seven days.** `cleanup_expired_logs(7)` purges terminal entries, so an
  orphan older than that is unreclaimable. In practice the repair runs at the front of the next
  sync; a machine left alone for a week keeps the orphan, and `uninstall` then says so rather
  than lying about it.
- **`unmanage` is the only verb that means "forget without removing".** If a second one is ever
  added, it has to clear the log too, or it will silently undo itself.
- **The container harness's crash section is the only place any of this is exercised end to end.**
  It now also asserts, after every crash iteration, that no canary is left installed and
  unmanaged — the property that was silently false and only surfaced three checks later as a
  cleanup that removed nothing.

## Not done, deliberately

- **`uninstall` still refuses rather than removing a package LiNix does not own.** `absent:` is
  the one thing LiNix removes without owning ("because you named it", V.7), and extending that to
  `uninstall` is a real option — it is written up at the end of `Q54` as the thing deliberately
  not ruled. It is a decision about blast radius, not about honesty, and the honest failure names
  `adopt`, which reaches the same end state through a step the user can see.
- **Ownership is still not durable per operation.** Writing the registry as each package lands
  would close the window rather than repair it, at the cost of one full serialisation per package
  on the hot path of every sync. The reasoning is in `V.186`; if the seven-day bound ever bites in
  practice, that is the change to make.
- **The tag is still not pushed** (carried over from the previous handoff).

## The part worth reading: two of my own recommendations were wrong

**L2's recommendation rested on a premise nobody had checked.** The entry proposed recording the
status quo as the rule. When the owner ruled *"fix it in the most robust way"*, the obvious reading
was to move `locks/` under the directory `DataLock` covers. **That would have removed a feature.**
`target-state.md:755` is explicit — *"`locks/` — generated. In git. Yours."* It travels with the
config to every machine that shares it, which is the whole reason `bare.HOST.toml` is per host.
Relocating it would turn a committed, shareable record into machine-local bookkeeping in order to
close a race.

**And the spec had already ruled L2, in a sentence nobody had checked against the code.** V.61:
*"the journal and the `locks/` ledgers move with it, and a lock that covers one of a set that must
agree is the same as no lock."* The ledgers are in the config root. The lock is over the data root.
The two are asserted as disjoint, by a test. The rule had been written down and never implemented,
and V.61 now says so rather than continuing to claim otherwise.

**L3's recommendation was declined, and the owner's question is why the shipped design is
different from either option.** *"Are there downsides to making it robust?"* — yes, one, and it
kills the obvious fix. A reader that takes the lock queues behind a `sync` for minutes. That trade
was made once already, with `watch`, and it ended with a bricked CLI (V.194). So a reader detects a
writer rather than excluding one: `core::stable` reads the writer generation either side of a
multi-file read and reads again if a writer committed in between.

## What shipped

### L1 — `[journal] flush_every`, default 32

One setting, not two. A `flush = "each" | "batch"` mode beside a `batch_size` would have been two
knobs needing a precedence rule, and `batch_size = 1` already *is* per-package flushing. Zero reads
as one, and the clamp lives on the journal beside the buffer it bounds rather than on the settings
struct.

The opening half of the log is untouched and not negotiable: a record that a package is about to be
touched reaches the disk before the manager is invoked. What is buffered is the *closing* half, and
what a crash in that window costs is one idempotent re-install — which `heal` does anyway, and
which the owner's own argument sharpened: most of it is re-derivable from the machine next time.

Also fixed on the way: `journalled` opened its actions in a loop of `record_start`, which is *k*
flushes for *k* actions. It uses `record_starts` now. That was a sibling of the finding the
previous round closed, and the previous round missed it.

### L2 — `LockFile::update`

Holds one data lock across the load, the change and the save. A lock around the *save* alone closes
nothing: the copy being written was read before the lock was taken.

**Held-ness is asked at runtime, not carried by a type.** `Deferred` takes and releases the lock
repeatedly, so a token proving "the lock is held" would be true when made and false when read. The
process counts its own holds — which is also what stops `update` waiting for itself, since `flock`
is per open file description and a second handle in a holding process blocks for ever.

**`save` deliberately does *not* take the lock.** It is a leaf function that cannot know its
caller's scope, and reaching for a process-wide lock there would serialise every test that writes a
ledger behind one file in the developer's real data directory. The gate is what holds the line
instead.

### L3 — `core::stable`

Applied at the registry/journal pair in `AppContext`, which every command loads at context build —
so it is every reader's exposure, not only the three-source ones. On a quiet machine it is two
reads of two tiny files and no waiting. After `ATTEMPTS` tries it returns the last answer rather
than an error.

### L4 — Part II

II.8 carries the three-scope table; II.24 was the sibling still describing `Commands::writes()` as
the exhaustive match when it is now derived from `lock_scope()`. V.194, V.195, V.196 added.
**The documentation changed and the locking code did not** — that direction is recorded in the
register, because a later reader will want to know which one was believed.

## The gates that did not exist

- **`a_finished_package_is_recorded_in_batches_tests`** — nine tests, and the one that matters is
  `what_a_crash_loses_is_a_re_run_and_not_a_record`: it uses `ManuallyDrop` as the crash, then
  re-reads the file and asserts the survivor is exactly the input `heal` is built to take. The
  claim being pinned is not that the buffer is fast but that **what it loses is recoverable**.
- **`a_ledger_is_read_and_written_as_one_step_tests`** — the eleven remaining ledger writes, each
  with the sentence that says why it is safe. **They share one reason, not eleven**: every one is
  reached from a `Writer`, which holds the lock for its whole run. That is what makes the list
  honest rather than an exemption table — and it stops being true the moment somebody reaches one
  of those paths from a `Reader`, which is exactly how `shall check` came to write
  `locks/regex.toml` under no lock at all. Plus its own non-vacuity control, because a gate whose
  correct answer is "nothing unlisted" cannot use "the walk matched something" as its control.
- Generation and re-entrancy tests in `datalock`, both written to be safe under a parallel suite:
  `HELD` is process-wide, so the only honest assertions are about this test's own lock.

## Cost, stated rather than implied

The owner asked mid-flight that none of this cause a significant slowdown. Per change:

- **L1** strictly *removes* flushes — up to `flush_every - 1` physical `sync_data` calls per wave,
  each of which used to stall the whole wave under the journal mutex. Nothing is added.
- **L2** costs an atomic load on the common path. `update` acquires a lock only when the process
  does not already hold one, which for every current caller is never — they run under `Writer`
  verbs.
- **L3** costs two reads of two tiny files either side of the registry/journal load, and retries
  only when a writer actually committed during the read. On a machine with no writer running it is
  exactly that and nothing more.

**None of it was benchmarked.** Every number above is derived from the mechanism, the same standing
gap the previous handoff names.
